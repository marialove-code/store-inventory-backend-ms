# 并发 V6 问答整理（RabbitMQ 异步锁库存）

> 压测：`POST .../order/add?version=v6`  
> 生产者：`OrderCreateConcurrencyV6`  
> 消费者：`OrderLockStockConsumer`（内部复用 V4 原子锁）  
> **逐步操作**：[`并发V6-压测步骤.md`](./并发V6-压测步骤.md)

---

## 一、定位与对照

**1. V6 解决什么问题？**

同步链路（V2/V4/V5）下，HTTP 线程要等到「锁库存 + 建单」做完才返回，高峰时 RT 高、线程占满。  
V6 把重活丢进 **RabbitMQ**，接口只负责「受理」，实现**削峰 + 解耦**。

**2. 和 V5、V4 怎么分工？**

| | V4 | V5 | V6 |
|--|----|----|-----|
| 教学点 | SQL 原子 | 分布式锁 | 异步最终一致 |
| 接口返回时 | 库存已锁 | 库存已锁 | **可能还未锁** |
| 防超锁手段 | 原子 UPDATE | Redis 互斥 | 消费者内走 V4 |

**3. 为什么消费者用 V4 而不是 V1？**

V6 练的是「异步解耦」，不是再复现超卖。多个消费者并发时，若仍用 V1 非原子，会再次超锁。  
正确性交给 V4；**幂等 / 重复消费**留给 V7。

---

## 二、实现细节

**4. 队列名是什么？**

`order.concurrency.lock.stock`（`RabbitMqConfig.QUEUE_ORDER_LOCK_STOCK`）。  
教学简化：默认交换机 + 队列名直投，无 Topic/死信。

**5. 消息体为什么单独建 DTO？**

`OrderLockStockMessage` 与下单字段对齐，避免 MQ 直接绑业务 Entity；可加 `sentAt` 便于排障。

**6. 「已受理」等于下单成功吗？**

不等于。只表示消息已发出。库存变化要看消费者日志或 `stock/result`（最终一致）。

**7. 业务失败（库存不足）会不会死循环重试？**

当前实现：业务异常打 warn 后正常结束（ACK），避免毒消息打爆库存服务。  
系统异常仍抛出，便于发现配置/网络问题。死信 / 补偿留给 V7。

---

## 三、面试口述（30 秒）

「V6 用 RabbitMQ 把下单锁库存从同步改成异步：接口发消息立刻返回，消费者再走 V4 原子 SQL 保证不超锁。代价是最终一致——返回成功时库存可能还没扣。幂等和补偿放在 V7。」
