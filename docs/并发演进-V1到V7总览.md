# 库存并发演进：V1 → V7 总览

> 场景：下单锁库存（库存 100，压测约 200 并发）  
> 生活类比：**奶茶店只有 100 杯原料，很多人同时点单**  
> 压测入口：`POST /api/order/concurrency/order/add?version=v1`（order-service:8083，仅 dev）  
> 详细压测数据见 [`并发演进.md`](./并发演进.md)

---

## 一、为什么要考虑并发？（用奶茶说清楚）

下单不是一步做完，大致是：

```text
看一眼还剩几杯 → 开小票（建订单） → 把原料划走（锁库存）
```

一个人慢慢点：店员看完再划走，没问题。

很多人**同时**喊「我要一杯」：如果「看还剩多少」和「真正划走原料」中间能被别人插队，就会出现——

- 大家都看到「还剩 5 杯」
- 大家都开了小票
- 原料却被划走了 **109 杯**，店里明明只有 **100 杯**（你们 V1 实测）

这就是超锁 / 超卖：钱货对不上，最后有人拿不到奶茶，或店里账对不平。所以要一套一套加手段。

---

## 二、怎么读这条演进线？

每个版本都按四句话看：

1. **解决了什么问题**
2. **为什么这么做 / 怎么做的**
3. **关键概念是什么意思**
4. **什么情况下又不够用了 → 下一版补什么**

记住一句总纲：

> **不是越新越替换旧的。**  
> V4 保「原料别超划」；V6 保「高峰别把柜台堵死」；V7 保「别同一单做两遍、做错了能修」。

## 三、版本演进（核心）

### V1｜无并发控制（基线：故意翻车）

| 项 | 说明 |
|----|------|
| 解决 | 不解决问题，专门**复现**超锁长什么样 |
| 为什么做 | 没有基线，后面说「修好了」没法证明 |
| 做法 | 看库存够 → 开小票 → 再非原子划原料；多人可交错 |
| 结果 | 200 并发稳定锁到 109（库存 100） |

**奶茶例子：**  
十个人同时问「还有吗？」店员都说「有」；十个人都付钱开票；原料却不够十杯——有人小票到手，奶茶没了。

**关键概念：竞态（race）**  
多个请求都看到「还有货」，都认为自己能买，最后一起加 lock。

**翻车点：** 一压测就翻车。  
**下一版：** 同一杯位同一时刻只让一个人走完「看-开票-划原料」→ **V2**。

---

### V2｜JVM 锁（ReentrantLock，按 goodsId）

| 项 | 说明 |
|----|------|
| 解决 | 单机多线程竞态 → **不再超锁** |
| 为什么做 | 最直观：同一商品排队，一次只服务一个人 |
| 做法 | 按 `goodsId` 抢一把**本机内存锁**，临界区内串行「读-建单-锁库存」 |
| 结果 | 不超锁（100/100），但同商品串行，RT 约 20s 级 |

**奶茶例子：**  
柜台前竖一块「小米奶茶专属」牌子：同一口味一次只接待一位客人，接待完再叫下一位。单店不会超卖。

**关键概念：临界区**  
必须互斥保护的那段代码（看库存 + 开票 + 划原料）。锁住整段 → 正确；代价是排队等。

**翻车点：**
1. **多店 / 多实例**：每台收银机各有一块牌子，两家店各自接待，原料池仍可能超划。
2. **慢**：爆款口味全店排队，后面的人干等。

**下一版：** 要提速 / 缩短临界区 → **V4**；多实例协调 → **V5**。

---

### V3｜线程池（任务拆分 + 异步）

| 项 | 说明 |
|----|------|
| 解决 | 在 V2 正确性上，把次要工作挪出主路径 |
| 为什么做 | 写流水、发短信不是「会不会超卖」的关键路径 |
| 做法 | 主路径仍用 goodsId 锁；写流水等丢线程池异步做 |
| 结果 | 正确性同 V2，RT 只比 V2 好约 2～3% |

**奶茶例子：**  
客人结账划原料仍必须排队；「把小票复印件塞进账本、发取餐短信」交给后厨小弟慢慢做。柜台还是慢，只是账本不堵主流程。

**关键概念：主路径 vs 旁路**  
瓶颈仍在那把锁上。异步旁路解决不了「爆款必须串行」的主矛盾。

**翻车点：** 多实例问题还在；性能提升可忽略。  
**下一版：** 真正提速 → 把「够不够」沉到数据库一次 UPDATE → **V4**。

---

### V4｜SQL 原子锁库存（正确性底座）

| 项 | 说明 |
|----|------|
| 解决 | 单机锁太慢；用数据库条件 UPDATE 保证「够才扣」 |
| 为什么做 | 数据库行更新天然串行；「判断」和「划走」合成一步，中间插不了队 |
| 做法 | `UPDATE … SET lock_stock=… WHERE stock - lock_stock >= qty`；影响行数=0 即库存不足 |
| 结果 | 不超锁；平均 RT ~14s、吞吐 ~10/s，明显好于 V2/V3 |

**奶茶例子：**  
不再先口头问「还有吗」再划账。店员直接在系统上点「扣 1 杯」：系统规定——**库存够才扣得动**；不够就点不动。两家分店同时点，数据库保证不会扣成负数。

**关键概念：条件更新（带着条件去写）**  
不先读再写，而是「够才改成功」。写失败 = 竞争失败 / 库存不足。这是生产里锁库存最常见、最稳的底座。

**翻车点：**
1. 客人连点两下「下单」→ 可能划走两杯（无幂等）。
2. 高峰时人人堵在柜台同步等结果 → HTTP 线程仍可能被占满。
3. 若业务仍是「先读再写」的老代码，多实例时还要补应用层锁（V5）；**你们锁库存应优先靠 V4**。

**下一版：** 分布式锁练手 → **V5**；削峰异步 → **V6**；防重复 → **V7**。

---

### V5 / V5r｜Redis 分布式锁

| 项 | 说明 |
|----|------|
| 解决 | 多 JVM 时本地锁失效 → 大家抢**同一把**逻辑锁 |
| 为什么做 | 把「叫号牌」放到云端（Redis），所有分店共用一个号 |
| 做法 | V5：手写 `SET NX EX` + Lua 解锁；V5r：Redisson **看门狗**续期。临界区可复用 V1 非原子，证明「只靠跨机锁也能防超锁」 |
| 结果 | 不超锁；RT ~23～25s，接近 V2、**慢于 V4**；高压下部分抢锁超时 → lockStock 可能 <100（不是超锁） |

**奶茶例子：**  
连锁三家店，原料仓只有一个。门口挂一个**共享叫号器**（Redis）：谁抢到号谁进仓划原料。比「每家店自己一块牌子」（V2）靠谱。

**关键概念：**
- **NX（Not eXists）**：只有还没人占着才能占上 → 抢锁。
- **看门狗：** 做奶茶超时了，系统自动帮你续「占用时间」，避免做到一半号牌过期、别人闯进来；做完再主动放号。
- **V4 vs V5：** 不是谁取代谁。V4 = 原料账本本身正确；V5 = 应用层跨店互斥能力（某些必须串行的业务）。

**翻车点：** 同商品仍串行干等 → 客人体感「卡住空白一会」。  
**下一版：** 柜台不想让人干等 → **V6**（真正划原料仍可靠 V4）。

---

### V6｜RabbitMQ 异步（削峰 + 最终一致）

| 项 | 说明 |
|----|------|
| 解决 | 同步锁库存把 HTTP 堵死 → **削峰、解耦、接口秒回** |
| 为什么做 | 高峰先把单子「收下」，制作/划原料放到后厨慢慢做 |
| 做法 | 生产者发消息立刻返回「已受理」；消费者再调 **V4** 原子锁 + 建单 |
| 结果 | HTTP 平均 RT **93ms**、吞吐 **258/s**；最终 lockStock=100、不超锁 |

**奶茶例子：**  
高峰不再让所有人堵在收银台等「原料划完」。收银员扫码后立刻给你一张「已接单」小票（秒回），单子进后厨队列；后厨按单用 V4 规则划原料。你刚出门查库存，可能还没锁满；过一会才到 100——这就是**最终一致**。

**关键概念：**
- **最终一致：** 返回「成功/已受理」≠ 当时已锁库存；过一小段时间才一致。前端应展示「制作中 / 查单」，别当成同步下单完成。
- **正确性不靠 MQ：** 队列只负责传单；会不会超卖，靠消费者里的 V4。
- **至少一次投递：** 同一张单可能被后厨看到两次 → 没有幂等就会做两杯。

**翻车点：** 重复消费、半成功（原料划了但小票没打上）、积压、死信。  
**下一版：** 幂等 + 补偿 → **V7**。

---

### V7｜幂等 + 补偿（可靠性收口）

| 项 | 说明 |
|----|------|
| 解决 | 重复提交 / 重复消费、中间失败导致的不一致 |
| 为什么做 | 防超卖解决的是「很多人抢」；生产更多翻车是「同一单做了两遍」和「只做了一半」 |
| 做法 | Redis 幂等键（`idempotentKey`）+ V4 建单；unlock 失败登记定时补偿 |
| 压测 | 同 key 200 并发：平均 RT ~62ms、吞吐 ~187/s，**lockStock=1**（防重复达标） |

**奶茶例子：**
- **幂等：** 你手机卡了，同一杯连点三下「下单」。系统认同一个「业务号」：只做一杯，后两次直接告诉你「这单已经有了，单号还是 xxx」。
- **补偿：** 原料已经划走，小票打印机卡纸了，当时又没能把原料退回 → 记到「待处理本」；后台定时任务再去退原料，避免账对不上。

**关键概念：**
- **幂等键粒度：** 太粗（只用「手机号」）会误伤你正常再买第二杯；太细（每次随机 UUID）等于没幂等。生产常用：前端业务单号、支付 `out_trade_no`、或合理时间窗内的业务键。
- **PROCESSING：** 同 key 并发时，后来者可能看到「处理中」而不是立刻「已完成」——属正常。
- **业务失败要清 key：** 库存不足时若一直占着「处理中」，用户无法用同一 key 合理重试。

**注意：** V7 压测看的是**同 key 只锁一次**，不是「锁满 100」。别和 V6 比 lockStock。

**翻车点：** 幂等键设计不好会误伤；补偿不是实时，需监控。  
**说明：** 并发主线到此收口。Topic / 死信 / 积压监控见下文「生产补强」。

## 五、两条升级路径（别搞混）

### 路径 A：正确性主线（别超卖）

```text
V1 超卖
  → V2 单店不超卖
  →（开分店）V5 或直接用 V4
  → V7 防同一单做两遍 / 半成功能修
```

### 路径 B：体验 / 架构主线（别堵死柜台）

```text
V2 / V5 同步太慢
  → V4 缩短临界区（更快）
  → V6 异步秒回「已接单」
  → V7 补最终一致带来的坑
```

你们 V6 消费者里复用的是 **V4**，所以正确性不靠「发消息」，靠后厨划原料时的原子 SQL。

## 六、关键概念速查（奶茶对照）

| 术语 | 人话 | 奶茶对照 |
|------|------|----------|
| 超锁 / 超卖 | 锁走的货 > 真实库存 | 只剩 100 杯原料，却开出 109 张有效划料 |
| 竞态 | 多人都基于旧信息做决定 | 同时问「还有吗」都得到「有」 |
| 临界区 | 必须互斥的那段逻辑 | 看库存到划原料之间不能插队的部分 |
| 条件 UPDATE | 带着「够才改」去写库 | 点「扣 1 杯」时系统自己判断够不够 |
| 分布式锁 | 多机共享一把锁 | 三家分店共用一个叫号器 |
| 看门狗 | 锁到期前自动续期 | 做茶超时，系统帮你续占用时间 |
| 最终一致 | 先答应，稍后才真正一致 | 已接单小票到手，原料可能稍后才划走 |
| 幂等 | 同一请求做多次 = 做一次 | 连点三下只出一杯 |
| 补偿 | 半成功之后的修补 | 划了原料但小票失败 → 事后退原料 |

## 七、生产环境还有哪些问题？如何解决？（理解向，不必动手）

> V1～V7 是面试主线；下面 8 条是**大厂常问的加分项**。  
> 目标：能口述「是什么 → 为什么 → 标准怎么做」，**不用自己搭死信/分桶**。  
> 每条结构：现象 → 奶茶例子 → 大厂标准解法 → 30 秒口述。

先看总表，再往下逐条展开：

| 问题 | 一句话 | 标准解法关键词 |
|------|--------|----------------|
| MQ 积压 | 进单比出杯快 | 扩容 + 限流 + 降级 + 监控 |
| 死信 / 毒消息 | 坏单反复失败堵队列 | 重试上限 + DLX + 人工重放 |
| 消息丢失 | 单子进队后失踪 | Confirm + 持久化 + 手动 Ack |
| 幂等存储故障 | Redis 挂了幂等失效 | Redis + DB 唯一索引双保险 |
| 补偿滞后 | 半成功不能靠人工盯 | 定时补偿 + 对账扫尾 |
| 最终一致体验 | 已受理 ≠ 已锁库存 | 状态机 + 查单/推送 |
| 热点商品 | 一行库存被打爆 | 分桶 / 预扣缓存（进阶） |
| 可观测性 | 出事找不到从哪坏 | 业务单号贯穿 + 流水 + 追踪 |

### 7.1 MQ 积压

**现象：** 队列里消息越堆越多，下单「已受理」了，很久才真正锁库存。

**奶茶：** 高峰一小时来了 1000 单，后厨只有 2 个人，单子贴满墙，出杯越来越慢。

**为什么会发生：** 生产者（收银）太快，消费者（后厨）太慢；或消费者挂了、变慢了。

**大厂标准解法（组合拳，不是只加机器）：**

1. **扩容消费者**：多开几个后厨窗口（多实例 / 提高并发消费）。  
2. **入口限流**：门口排队叫号，柜台每秒只收 N 单（Sentinel / 网关限流），避免无限堆。  
3. **降级**：队列深度超阈值 → 提示「排队火爆，请稍后」或只建意向单、暂缓锁库存。  
4. **监控告警**：盯「队列深度、消费延迟、消费速率」；深度持续上涨就报警。

```text
客人下单 ──限流──▶ 收银发 MQ ──▶ [队列积压?] ──▶ 多个后厨消费者
                      │                │
                      │                └─ 深度告警 / 降级开关
                      └─ 秒回「已受理」
```

**30 秒口述：**  
「积压本质是消费能力跟不上生产。我们会监控队列深度，先扩容消费者，同时入口限流；积压严重时降级提示排队，避免把系统拖垮。」

---

### 7.2 死信 / 毒消息

**现象：** 某条消息怎么消费都失败；若无限重试，会一直占着消费者，后面的单也卡住。

**奶茶：** 有一张单写着「做一杯不存在的口味」，后厨反复尝试、反复失败，后面正常单全堵着。

**为什么会发生：** 数据本身非法、依赖服务长期挂、代码 bug；MQ「至少一次」会反复投递。

**大厂标准解法：**

1. **有限重试**：例如最多 3～5 次，带间隔（避免立刻打爆下游）。  
2. **死信队列（DLX / DLQ）**：超过重试次数 → 扔进「问题单箱子」，**不再堵主队列**。  
3. **告警 + 人工/任务重放**：运维或对账任务看死信，修好数据后再投回。  
4. **幂等仍要有**：重放时不能又做成两杯（和 V7 同一套）。

```text
主队列 ──消费失败──▶ 重试(≤N次)
                      │
                      ├─ 成功 → 正常结束
                      └─ 仍失败 → 死信队列 → 告警 → 人工修复后重放
```

**30 秒口述：**  
「毒消息会拖死主队列。生产上必须设重试上限，失败进死信隔离，告警后人工或任务重放，重放时靠幂等防重复。」

---

### 7.3 消息丢失

**现象：** 客人显示已下单，后厨却从未收到单 → 既没锁库存，也没订单。

**奶茶：** 收银喊了一声「后厨做一杯」，纸条被风吹走了，两边都以为对方知道。

**丢在哪三截（面试常问）：**

| 环节 | 怎么丢 | 标准防丢 |
|------|--------|----------|
| 生产者 → Broker | 发了但 Broker 没收下 | **Publisher Confirm**（Broker 回执才算成功） |
| Broker 自己 | 内存队列，进程挂了没了 | 队列/消息 **durable 持久化** |
| 消费者 | 还没处理完就 Ack，然后进程挂了 | **手动 Ack**；处理成功后再确认 |

```text
收银 ──Confirm──▶ RabbitMQ(持久化) ──▶ 后厨消费成功 ──再──▶ Ack
  │                    │                      │
  └ 没 Confirm 当失败重发   挂了可恢复          没做完不 Ack
```

**注意：** 防丢会加强「至少一次」→ 更容易重复，所以必须配 **幂等（V7）**。大厂口头禅：**可靠投递 + 业务幂等** 一起上。

**30 秒口述：**  
「防丢分三段：发送要 Confirm，队列要持久化，消费要手动 Ack。这样更可能重复投递，所以业务侧必须幂等。」

---

### 7.4 幂等存储故障

**现象：** 幂等记在 Redis；Redis 挂了或 key 丢了，同一单可能再锁一次库存。

**奶茶：** 防连点的「叫号本」丢了，客人连点两下，店里又做了一杯。

**大厂标准解法：双保险（这是标准答案）**

1. **Redis**：快路径，挡绝大多数连点 / 重复消费。  
2. **DB 唯一约束**：订单表对「业务单号 / 幂等键」建 **UNIQUE INDEX**。  
   即使 Redis 全挂，第二次插入直接唯一键冲突 → 查已有单返回，**不会锁两次**。  
3. **降级策略写清楚**：Redis 不可用时，是「只靠 DB 唯一」还是「暂时拒绝下单」——团队要有预案，面试能说一种即可。

```text
同一业务单号
    │
    ├─① Redis SET NX（快）
    │      成功 → 走下单
    │      已存在 → 返回原单
    │
    └─② 写订单 UNIQUE(业务单号)
           冲突 → 当作幂等命中（兜底）
```

**和你们项目的关系：** V7 已做 Redis 幂等；生产口述时补一句「还会加订单业务单号唯一索引做兜底」。

**30 秒口述：**  
「幂等不能只靠 Redis。标准是 Redis 做快速去重，数据库业务单号唯一索引做最终兜底，Redis 故障也不会超锁。」

---

### 7.5 补偿滞后

**现象：** 半成功（例如库存已 lock，订单没落库，当时 unlock 也失败）靠定时任务修，中间会有一段时间账对不上。

**奶茶：** 原料划走了，小票没打出来，退料要等店长每 30 分钟巡一圈——这半小时账是不平的。

**大厂标准解法：**

1. **同步尽量修**：失败路径先立刻 unlock；unlock 失败再登记补偿（你们 V7 思路）。  
2. **定时补偿**：短周期重试 unlock / 关单（分钟级，视业务）。  
3. **对账扫尾（更重要）：** 不管定时有没有漏，每天/每小时扫：  
   - 「有 lock 流水、无成功订单」→ 解锁或告警  
   - 「有订单、无 lock」→ 补锁或关单  
4. **告警**：补偿队列堆积、对账差异数 > 0 要人看。

```text
业务失败
  → 立即 unlock（快路径）
  → 失败则进补偿表/Set
  → 定时 Job 重试
  → 对账任务扫差异（兜底）
```

**30 秒口述：**  
「补偿不是实时强一致，允许短暂不一致。做法是失败先尽量回滚，不行进补偿队列，再用对账任务扫『有锁无单』做兜底。」

---

### 7.6 最终一致体验

**现象：** 接口已返回成功/已受理，用户立刻查库存或订单，发现还没变 → 以为系统坏了。

**奶茶：** 收银给了「已接单」小票，客人冲去取餐口，茶还没开始做。

**大厂标准解法：别让用户以为「同步做完了」**

1. **状态机说清楚：**  
   `已受理` → `库存已锁定` → `待支付/制作中` → `完成`  
2. **前端：** 下单成功页显示「处理中」，用轮询或 WebSocket/推送刷新状态。  
3. **查单接口：** 用业务单号查当前状态，不要只靠「HTTP 200」当最终成功。  
4. **超时单：** 长时间停在「已受理」→ 展示失败/可重试，并触发补偿。

```text
用户点击下单
   → 返回：已受理（业务单号）
   → 前端轮询 GET /order/{业务单号}
         ├─ 处理中
         ├─ 锁库存成功 / 待支付
         └─ 失败（可重试）
```

**30 秒口述：**  
「异步下单必须把状态暴露给前端。我们返回业务单号和『已受理』，前端轮询或推送看是否锁库存成功，避免用户把受理当成最终成功。」

---

### 7.7 热点商品（进阶，了解即可）

**现象：** 爆款 SKU，所有请求打同一行库存，数据库行锁/更新成为瓶颈，RT 飙升。

**奶茶：** 全城只卖「联名款」一杯配方，所有分店的扣减都挤在同一本账的同一行上，会计手速再快也排队。

**大厂常见解法（知道思路即可，不必自己实现）：**

1. **库存分桶：** 100 杯拆成 10 个桶（每桶 10），请求随机/哈希打到不同桶，降低单行竞争；卖完再汇总。  
2. **缓存预扣：** Redis 先扣「可售额度」，异步再落 DB；定期对账防 Redis/DB 不一致。  
3. **排队 / 分段秒杀：** 入口排队，后端按批次放行（秒杀场景经典）。

```text
           商品库存 100
        ┌────┬────┬────┐
        │桶1 │桶2 │… 桶10│  ← 请求打散
        │ 10 │ 10 │  10 │
        └────┴────┴────┘
              ↓ 对账汇总
```

**和主线关系：** 你们 V4 已能正确不超卖；热点是「性能优化进阶」，面试提到「分桶或预扣 + 对账」就够。

**30 秒口述：**  
「热点单行更新会成为瓶颈。大厂会做库存分桶打散，或 Redis 预扣再异步落库并对账。正确性仍要对账兜底。」

---

### 7.8 可观测性

**现象：** 账对不上，日志里一堆请求，找不到是哪一单、卡在哪一步。

**奶茶：** 客人投诉「我付款了没拿到茶」，店里没有统一单号，收银小票、后厨贴条、原料本对不上号。

**大厂标准解法：**

1. **业务单号贯穿全链路**（幂等键 / orderNo）：日志、MQ 消息、库存流水都带同一 ID。  
2. **库存流水：** 每次 lock/unlock 留痕（谁、何时、多少、关联单号）。  
3. **对账报表：** 定时输出差异单列表。  
4. **链路追踪：** TraceId（SkyWalking / Zipkin 等）串起 gateway → order → inventory → MQ。

```text
业务单号=BIZ-001
  下单日志 → MQ 消息 → 消费日志 → lock 流水 → 支付回调
       ↑______________ TraceId 串联 ______________↑
```

**30 秒口述：**  
「出了不一致先靠业务单号把全链路串起来。我们要求日志、消息、库存流水都带单号，再加对账和链路追踪，才能快速定位半成功卡在哪一步。」

---

### 生产最小闭环（总背这 5 句）

1. 锁库存用 **V4 条件 UPDATE**。  
2. 高峰用 **V6 异步受理**，接受最终一致。  
3. **幂等：Redis + DB 唯一索引** 双保险。  
4. **补偿 + 对账** 修半成功。  
5. MQ：**监控积压、死信、Confirm/持久化/手动 Ack**。  

> V5 Redisson 不是锁库存必选项；更常用于必须串行的业务临界区，不能替代 V4。

---

## 八、面试口述（约 40 秒）

「库存下单要考虑并发，因为读库存和锁库存不是原子的，就像奶茶店同时问『还有吗』会超卖，我们 V1 压测就超锁了。  
V2 用单机锁修好了，但多实例失效而且很慢。  
V3 只是把次要工作异步掉，主瓶颈还在。  
V4 用 SQL 条件更新，够才扣得动，正确又更快，是正确性底座。  
V5 用 Redis 做跨 JVM 锁，像连锁店共用叫号器。  
V6 用 MQ 异步，接口立刻返回已受理，最终一致，消费者里仍走 V4。  
V7 再补幂等和补偿：同一业务号只做一次，半成功用任务修。  
生产还要加死信、积压监控、对账，以及 DB 唯一约束双保险。」
