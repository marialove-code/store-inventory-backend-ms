# 库存并发演进：V1 → V7 总览

> 场景：下单锁库存（库存 100，压测约 200 并发）  
> 压测入口：`POST /api/order/concurrency/order/add?version=v1`（order-service:8083，仅 dev）  
> 详细压测数据见 [`并发演进.md`](./并发演进.md)

---

## 一、为什么要考虑并发？

下单不是一步做完，大致是：

```text
读可用库存 → 建订单 → 锁库存
```

一个人慢慢点：没问题。  
很多人**同时**点：如果「判断还有货」和「真正锁上」中间能被别人插队，就会出现——

- 大家都读到「还有货」
- 大家都建单成功
- 锁定库存变成 **109**，但总库存只有 **100**（你们 V1 实测）

这就是超锁 / 超卖风险：钱货对不上。所以要一套一套加手段。

---

## 二、怎么读这条演进线？

每个版本都按四句话看：

1. **解决了什么问题**
2. **怎么做的**
3. **什么情况下又不够用了（翻车点）**
4. **因此下一版补什么**

---

## 三、版本演进（核心）

### V1｜无并发控制（基线）

| 项 | 说明 |
|----|------|
| 解决 | 不解决问题，专门**复现**超锁长什么样 |
| 做法 | 读库存 → 建单 → 非原子 lock；多线程可交错 |
| 翻车点 | 一压测就翻车：200 并发可锁到 109（库存 100） |
| 下一版 | 需要互斥：同商品同一时刻只让一个请求走完临界区 → **V2** |

---

### V2｜JVM 锁（ReentrantLock，按 goodsId）

| 项 | 说明 |
|----|------|
| 解决 | 单机多线程竞态 → **不再超锁** |
| 做法 | 同一商品抢一把本地锁，临界区内串行执行「读-建单-锁库存」 |
| 翻车点 | ① **多实例部署**：每台 JVM 各有一把锁，仍可能超锁；② 同商品串行，**RT 很高**（压测约 20s 级） |
| 下一版 | 要提速 / 缩短临界区 → **V4**；多实例协调 → **V5** |

---

### V3｜线程池（任务拆分 + 异步）

| 项 | 说明 |
|----|------|
| 解决 | 在 V2 正确性上，把次要工作（流水/通知等）挪出主路径 |
| 做法 | 主路径仍用 goodsId 锁；写流水等丢线程池异步做 |
| 翻车点 | 瓶颈仍在 ReentrantLock，RT 只比 V2 好一点点（约 2～3%）；多实例问题同 V2 |
| 下一版 | 要明显提速：互斥下沉到数据库原子 UPDATE → **V4** |

---

### V4｜SQL 原子锁库存

| 项 | 说明 |
|----|------|
| 解决 | 单机锁太慢；用数据库条件 UPDATE 保证「够才扣」 |
| 做法 | `UPDATE … SET lock_stock=… WHERE stock - lock_stock >= qty`；影响行数=0 即库存不足 |
| 翻车点 | ① 重复提交仍可能锁两次（无幂等）；② 同步高峰时 HTTP 线程仍被占满；③ 跨实例应用层协调叙事要补 |
| 下一版 | 分布式锁练手 → **V5**；削峰异步 → **V6**；防重复 → **V7** |

---

### V5 / V5r｜Redis 分布式锁

| 项 | 说明 |
|----|------|
| 解决 | 多 JVM 时本地锁失效 → 大家抢**同一把**逻辑锁 |
| 做法 | V5：手写 `SET NX EX` + Lua 解锁；V5r：Redisson 看门狗续期。临界区可复用 V1 非原子，证明「只靠锁也能防超锁」 |
| 翻车点 | 同商品仍串行，RT 接近 V2、**慢于 V4**；高峰时接口线程仍同步干等（你体感过的「空白一会」） |
| 下一版 | 接口不想干等 → **V6**（正确性可继续靠 V4） |

> 注意：V4 与 V5 **不是谁取代谁**。V4 = 库存行正确性；V5 = 应用层跨实例互斥能力。

---

### V6｜RabbitMQ 异步（最终一致）

| 项 | 说明 |
|----|------|
| 解决 | 同步锁库存把 HTTP 堵死 → **削峰、解耦、接口秒回** |
| 做法 | 生产者发消息立刻返回「已受理」；消费者再调 **V4** 原子锁 + 建单 |
| 翻车点 | ① 返回成功 ≠ 当时已锁库存（最终一致）；② 消息重复消费可能重复下单；③ 半成功需要对账补偿 |
| 下一版 | 幂等 + 重试/补偿 → **V7** |

---

### V7｜幂等 + 补偿（待做）

| 项 | 说明 |
|----|------|
| 解决 | 重复提交 / 重复消费、中间失败导致的不一致 |
| 计划做法 | idempotentKey / 唯一约束；失败重试；定时对账补偿 |
| 说明 | 这是生产级收口，不是再换一种「锁」。Topic 交换机、积压监控等可另作加深 |

---

## 四、一句话对照（适合背）

| 版本 | 一句话 | 什么情况逼你上下一版 |
|------|--------|----------------------|
| V1 | 无控制，稳定超锁 | 发现竞态 → 上锁 |
| V2 | 单机锁，正确但慢 | 多实例 / 要提速 |
| V3 | 异步次要工作，主瓶颈仍在锁 | 要明显提速 → SQL 原子 |
| V4 | DB 原子，正确 + 更快 | 多实例协调 / 异步削峰 / 幂等 |
| V5 | Redis 跨 JVM 锁 | 接口不想同步干等 |
| V6 | MQ 秒回，最终一致 | 重复消费与半成功 |
| V7 | 幂等 + 补偿收口 | 生产可靠性闭环 |

---

## 五、两条升级路径（别搞混）

### 路径 A：正确性主线

```text
V1 超锁
  → V2 单机不超锁
  →（部署多实例）V5 或直接用 V4
  → V7 防重复 / 补偿
```

### 路径 B：体验 / 架构主线

```text
V2 / V5 同步慢
  → V4 缩短临界区（更快）
  → V6 异步秒回
  → V7 补最终一致的坑
```

你们 V6 消费者里复用的是 **V4**，所以正确性不靠「发消息」，靠消费者里的原子 SQL。

## 六、面试口述（约 40 秒）

「库存下单要考虑并发，因为读库存和锁库存不是原子操作，V1 压测会超锁。  
V2 用单机锁修好了，但多实例失效且很慢。  
V3 只是异步次要工作，主瓶颈还在。  
V4 用 SQL 条件更新，正确又更快。  
V5 用 Redis 做跨 JVM 锁。  
V6 用 MQ 异步，接口立刻返回，最终一致。  
V7 再补幂等和补偿，防止重复消费和半成功。」
