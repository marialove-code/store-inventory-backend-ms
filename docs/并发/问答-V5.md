# 并发 V5 问答整理（Redis 分布式锁）

> 压测：  
> - 手写版：`POST .../order/add?version=v5` → `OrderCreateConcurrencyV5` + `GoodsStockRedisLock`  
> - Redisson：`POST .../order/add?version=v5r` → `OrderCreateConcurrencyV5Redisson` + `GoodsStockRedissonLock`  
> 方案：**A. 按 goodsId 的 Redis 分布式锁**，临界区复用 V1 非原子链路（与 V2 对照）  
> **逐步操作**：[`并发/步骤-V5.md`](./步骤-V5.md)

---

## 一、定位与对照

**1. V5 解决什么问题？**

V2 的 `ReentrantLock` 只在**单个 JVM** 内互斥。多实例部署时，每个进程各有一把锁，仍可能超锁。  
V5 把互斥放到 **Redis**，所有实例抢同一把逻辑锁：`inventory:lock:stock:{goodsId}`。

**2. 和 V2、V4 怎么分工？**

| | V2 | V4 | V5 |
|--|----|----|-----|
| 互斥手段 | JVM 锁 | SQL 原子 UPDATE | Redis SET NX EX |
| 单机防超锁 | 能 | 能 | 能 |
| 多实例防超锁 | 不能 | 能（同库同行） | 能（共享 Redis） |
| 教学点 | JUC | DB 并发 | 分布式锁 |

**3. 有了 V4 为何还做 V5？**

V4 已够「同库库存行」正确性。V5 练的是**应用层分布式锁**（跨实例协调、后续可接预扣/限流）。面试说「不是替代 V4，是能力扩展」。

---

## 二、实现细节

**4. 加锁命令是什么？**

`SET key token NX EX leaseSeconds`（代码里 `setIfAbsent` + TTL）。  
- NX：不存在才写入  
- EX：过期时间，防止进程崩溃死锁  
- token：UUID，解锁时校验，防误删

**5. 为什么解锁要用 Lua？**

「get 再 del」非原子：可能 get 是自己的，del 时已被别人抢走。  
Lua：`if get==token then del` 一次执行，只删自己的锁。

**6. 为什么要自旋等待，而不是抢一次失败？**

与 V2 `lock()` 阻塞语义对齐，方便 200 并发压测：后来者排队等锁，而不是大量直接失败。  
配置：`app.concurrency.v5.lock-wait-ms`（默认 30s）、`lock-lease-seconds`（默认 30s）。

**7. 租约过期了业务还没跑完怎么办？**

教学实现**没有看门狗续期**；lease 要大于临界区耗时。  
生产常用 **Redisson** 看门狗自动续期。面试主动提这一点是加分。

**8. 临界区里为什么还用 V1 非原子 lock？**

为了证明：**仅靠 Redis 互斥**就能消除 V1 那种「读-建单-非原子锁」竞态。  
若临界区已是 V4 原子 SQL，锁只是多余串行，对照意义变弱。

**9. Key 设计注意什么？**

- 前缀：`inventory:lock:stock:`（见 `RedisConstants.STOCK_LOCK_PREFIX`）  
- 维度：按 `goodsId`（同一商品串行，不同商品可并行）  
- 与登录 Token 等 Key 隔离，可同 Redis、同 database

## 三、微服务与运维

**10. 锁加在 order-service，库存在 inventory-service，合理吗？**

合理：下单编排在订单侧；锁保护的是「下单临界区」。  
库存服务内部仍可有自己的 SQL 条件（正式链路已是原子 lock）。压测 V5 刻意走非原子接口做对照。

**11. Redis 挂了怎么办？**

加锁失败 → 接口失败（或降级策略：失败快速拒绝 / 降级 V4 SQL）。  
面试答：分布式锁强依赖 Redis 可用性，要监控与降级方案。

**12. 和 Redisson 比呢？项目里怎么选？**

| | `v5` 手写 | `v5r` Redisson |
|--|-----------|----------------|
| 依赖 | Spring Data Redis | + redisson-spring-boot-starter |
| 续期 | 固定 lease（默认 30s） | 默认**看门狗**（`lock-lease-seconds: -1`） |
| 可重入 | 未做 | 支持 |
| 教学 | 原理透明 | 生产常见写法 |
| Key | `inventory:lock:stock:{id}` | `inventory:lock:stock:redisson:{id}`（前缀区分，避免混抢） |

压测时改 URL 的 `version` 即可对照，不必改代码。

**12.1 V6 / V7 会强制用 Redisson 吗？**

| 阶段 | 要不要 Redisson |
|------|-----------------|
| **V6 MQ** | **一般不用**。核心是消息队列（Rabbit/RocketMQ）；异步消费与锁实现无关。 |
| **V7 幂等+补偿** | **可选**。幂等可用 `SET NX`（手写或 Redisson `RBucket`/`trySet`）；补偿是定时对账，不依赖 Redisson。 |

结论：Redisson 是 **V5 锁的实现选型**；V6/V7 可以继续用现有 Redis/DB，不必绑死 Redisson。若以后幂等也想统一客户端，再复用 `RedissonClient` 即可。

## 四、压测与验收

**13. 压测前准备？**

1. Redis、inventory-service、order-service 已启动  
2. `POST /api/order/concurrency/stock/reset`  
3. JMeter：先 `version=v5`，再同样参数跑 `version=v5r`，body 同 V1～V4  

**14. 成功标准？**

- `lockStock <= stock`，`overLocked=false`  
- 成功订单数 ≈ 初始库存 100（与 V2/V4 同）  
- 失败多为「库存不足」或「获取锁超时」（超时应较少，若很多则加大 wait 或查 Redis）

**15. 性能预期？**

同一商品会被 Redis 锁串行，形态接近 V2（排队），一般**不会快过 V4**。  
V5/V5r 赢在「多实例语义」，不是单机吞吐冠军；v5r 相对 v5 的优势在**续期与可维护性**，不保证更快。

## 五、口述模板（30 秒）

> V1 无锁会超卖；V2 用 JVM 锁单机修好，多实例无效；V4 用 SQL 原子条件，多实例也正确。  
> V5 把锁放到 Redis：手写 `SET NX EX` + Lua；V5r 换成 Redisson，看门狗自动续期。  
> 临界区仍走读库存建单，证明跨进程互斥。V6 用 MQ，V7 做幂等补偿，不必绑定 Redisson。
