# 并发 V7 测试步骤（幂等 + 补偿）

> 前置：Redis 可用；order(8083) `dev`；inventory(8082)。  
> 压测：`POST /api/order/concurrency/order/add?version=v7`

---

## 1. 幂等冒烟（最重要）

```http
POST http://localhost:8083/api/order/concurrency/stock/reset
```

用**同一个** `idempotentKey` 连打 2～3 次：

```http
POST http://localhost:8083/api/order/concurrency/order/add?version=v7
Content-Type: application/json
```

```json
{
  "userName": "smoke-v7",
  "goodsId": "2064625692771397632",
  "goodsName": "小米17",
  "costPrice": 3999,
  "salePrice": 4399,
  "buyQty": 1,
  "remark": "smoke V7",
  "idempotentKey": "smoke-key-001"
}
```

期望：

- 第 1 次：`V7 下单成功…orderNo=…`
- 第 2、3 次：`V7 幂等命中，返回原订单号：…`（同一 orderNo）
- `GET .../stock/result` → `lockStock` **只增加 1**

不传 `idempotentKey` 应直接失败提示。

---

## 2. 补偿（理解即可）

场景：远程已 lock，本地 `save` 失败，且当时 `unlock` 也失败 → 写入 Redis Set  
`inventory:v7:compensate:unlock`，`OrderConcurrencyCompensateJob`（dev，默认 30s）会重试 unlock。

日常冒烟不必刻意造失败；面试能口述这条链路即可。

---

## 3. JMeter（同 key 高压）

Body 固定同一 `idempotentKey`（例如 `jmeter-v7-clean-002`），线程数 50 / 200，其余与 V4/V5 相同。

期望：

- 异常率 0%
- 响应里可混「V7 下单成功」「幂等命中」「处理中」——属正常
- `stock/result` → `lockStock=1`，`overLocked=false`

正式结果（2026-07-21，200 并发）：平均 RT **62ms**，吞吐 **187.3/s**，`lockStock=1`。

---

## 4. 与 V6 的关系

| | V6 | V7 |
|--|----|----|
| 主目标 | 异步秒回 | 防重复 + 半成功补偿 |
| 默认路径 | MQ | 同步 V4 + Redis 幂等（易验证） |
| 叠加 | 消息带 `idempotentKey` 时消费者也走幂等 | — |

---

## 5. 易踩坑

- `stock/reset` **不清** Redis 幂等；换 key 或手动 `DEL`
- 勿在压测中途删幂等 key 再打，否则同业务可能再锁一次
