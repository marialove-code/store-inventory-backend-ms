# 库存并发 V2 / V3 — 问答整理

> 配合：[`并发/01-压测数据.md`](./01-压测数据.md) · 代码包 `com.inventory.modules.order.concurrency.v2/v3`  
> **V4 问答**：见 [`并发/问答-V4.md`](./问答-V4.md)  
> 说明：本文只展开 **V2、V3**。**V1 定位**：在压测下 **复现** 多线程竞态导致的超锁现象，**不提供** 并发解决方案；V1 仅在对比处一笔带过。

---

## 一、V2 相关

### 并发与锁

**1. V1 为什么会超锁？它和 V2/V3 的定位有什么不同？**

**V1 定位**：复现并发问题，不解决问题——直接走正式 `createOrder`，**不加任何并发控制**，用来在 200 线程压测下 **稳定复现超锁**（如 109/200 成功）。

根因是 **多线程竞态**，不是「单线程」。多个线程同时执行「读可用库存 → 判断 → 建单 → lockStock」，read/write 之间无互斥、无 SQL 原子条件，导致 `lockStock` 超过 `stock`。

**2. `ReentrantLock` 和 `synchronized` 有什么区别？**

| 对比项 | synchronized | ReentrantLock |
|--------|--------------|---------------|
| 层次 | JVM 关键字，自动加解锁 | JUC 类，需手动 `lock/unlock` |
| 可中断 | 不支持 | `lockInterruptibly()` |
| 尝试获取 | 不支持 | `tryLock()` |
| 公平锁 | 非公平 | 可选公平/非公平 |
| 多条件队列 | 单一 wait 集 | 多个 `Condition` |

V2 选 ReentrantLock 是为 JUC 实验与后续扩展（如 tryLock）；本场景用 synchronized 包一层方法也能达到类似互斥效果。

**3. V2 为什么按 `goodsId` 加锁，而不是按订单加锁？**

超卖/超锁的冲突点是 **同一商品的库存行**，不是「订单之间」。按订单加锁等于每个请求一把锁，互不阻塞，无法解决「多人同时改同一 goodsId 库存」的问题。

按 `goodsId` 互斥：同一商品串行，不同商品可并行（压测只打一个商品，所以 200 请求全排队）。

**4. `ConcurrentHashMap<Long, ReentrantLock>` 在这里起什么作用？**

为每个 `goodsId` **懒创建**一把 `ReentrantLock`：

```java
GOODS_LOCKS.computeIfAbsent(goodsId, id -> new ReentrantLock());
```

- 线程安全：多线程同时 `computeIfAbsent` 不会建两把锁  
- 粒度：一商品一锁，而不是全局一把大锁  

**5. 什么是可重入锁？同一线程能连续 `lock()` 两次吗？**

可重入：同一线程已持有锁时，再次进入同一把锁 **不会自死锁**，内部维护重入次数。

可以连续 lock 两次（通常在同一线程调用链里），但必须 unlock 相同次数。V2 单次 `lock/unlock` 包裹一次 createOrder 即可。

**6. JVM 锁能解决多实例部署吗？为什么不行？**

不能。`ReentrantLock` 和 `GOODS_LOCKS` 都在 **单个 JVM 进程内存** 里。两台服务器各有一个 JVM，各自有一把「逻辑上的 goods 锁」，**互不相干**，仍可能双实例同时扣库存。

多实例需 **V4 SQL 原子条件** 或 **V5 Redis 分布式锁**。

**7. V2 下 200 并发为什么平均响应到 19 秒级？**

200 个请求抢 **同一 goodsId 的一把锁**，同一时刻只有 1 个在执行 createOrder，其余在 `lock.lock()` 排队。

- 先拿到锁的请求：几百 ms 级  
- 排在前面的请求：要等前面 99～199 次完整下单  
- 平均被拉很高（复测约 **19,293 ms**），最大约 **32 s**  

这是 **锁排队** 的典型特征，不是「CPU 单线程慢」。

**8. 锁排队和 GC 导致的慢怎么区分？**

| 现象 | 更像锁排队 | 更像 GC |
|------|------------|---------|
| jstack | 大量 `BLOCKED` / `WAITING` 在 `ReentrantLock` | 线程整体 STW、GC 日志长 pause |
| 响应分布 | 最小很小、最大很大、标准偏差大 | 周期性毛刺 |
| V2 压测 | 与锁串行模型吻合 | 改 V3 同步路径后 RT 几乎不变 → 说明不是 GC 主因 |

压测后可用 `jstack` 看线程是否在 `OrderCreateConcurrencyV2.createOrder` 附近阻塞。

**9. `lock()` 和 `unlock()` 为什么必须放在 `try-finally` 里？**

若 `createOrder` 抛异常而没 unlock，锁永不释放，后续请求 **永久阻塞**。

```java
lock.lock();
try {
    return orderInfoService.createOrder(dto);
} finally {
    lock.unlock();  // 无论成功失败都释放
}
```

**10. 公平锁和非公平锁是什么？V2 用的是哪种？**

- **非公平**（默认）：新来的线程可能插队，吞吐高，易饥饿  
- **公平**：按先来后到，吞吐低，更均匀  

V2/V3 使用 `new ReentrantLock()`，**默认非公平**。

### 业务与事务

**11. 下单锁库存的完整步骤是什么？**

V2 走 `OrderInfoServiceImpl.createOrder`（全同步）：

1. 查 `inventory_stock`，算 `usable = stock - lockStock`  
2. 不足则返回失败  
3. 构建 `OrderInfo`，生成订单号，算金额，状态待支付  
4. `save(order)` 插入订单  
5. `stockService.lockStock`：更新 `lock_stock`，**同步写** `inventory_flow` 流水  

**12. `@Transactional` 在 V2 里包住了哪些操作？**

在 `OrderInfoServiceImpl.createOrder` 方法上：

- 校验库存、插入订单、`lockStock`（含改 lock_stock + 写流水）  
- 任一步异常则整单回滚（实验里业务失败用 `return Result.fail` 不会触发回滚，抛异常才会）  

**13. 可用库存怎么算？**

```text
usableStock = stock - lockStock
```

- `stock`：实物/账面总库存  
- `lockStock`：已被订单预占、尚未发货扣减的量  
- 下单判断：`usableStock >= buyQty`  

**14. 什么是超锁？和超卖口语上有什么区别？**

- **超锁**：`lockStock > stock`，或成功预占数超过可售数（如 lockStock=109, stock=100）  
- **超卖**：实际卖出/发货超过真实库存  

本项目阶段更准确是 **超锁（预占超额）**；口语常混用「超卖」。

**15. 200 并发 100 库存，为什么成功数是 100 而不是 200？**

V2 保证同一时刻只有一个线程在「读+写」该商品库存。先成功的线程占满 100 件后，后续线程读到 `usable=0`，返回库存不足。故 **100 成功 + 100 失败**。

### Spring 与项目

**16. V2 为什么包一层 `OrderCreateConcurrencyStrategy`，而不是直接改 `OrderInfoService`？**

- **策略模式 + 多版本对比**：V1～V7 并存，正式接口与实验隔离  
- **不污染正式业务**：`POST /order/info/add` 仍走默认逻辑，压测走 `/order/concurrency/order/add?version=v2`  
- **文档与面试**：一条演进线清晰可述  

**17. `OrderConcurrencyFacade` 怎么根据 `version=v2` 路由？**

Spring 注入所有 `OrderCreateConcurrencyStrategy` 实现，按 `version()` 放进 Map。  
`createOrder("v2", dto)` → `ConcurrencyVersion.fromCode("v2")` → 取 `OrderCreateConcurrencyV2` Bean → 调用其 `createOrder`。

**18. 压测接口为什么只在 `dev` 环境开放？**

`OrderConcurrencyDevController` 带 `@Profile("dev")`，生产 `prd` 不注册，避免暴露 reset/实验下单接口，降低误操作与安全风险。

### 压测与验证

**19. JUnit 里 `CountDownLatch` 的 `startGate` / `doneGate` 是干什么的？**

- **startGate(1)**：200 线程先 `await`，主线程 `countDown` 后 **同时开跑**，模拟 JMeter 齐射  
- **doneGate(200)**：每个线程完成后 `countDown`，主线程 `await` 等 **全部结束** 再查库断言  

**20. JMeter 200 线程为什么样本数是 200？**

线程数 200 × 循环次数 1 = **200 个 HTTP 请求**。若显示 400，检查是否循环=2 或重复采样器。

**21. HTTP 200 和业务 `code:500`（库存不足）是一回事吗？**

不是。

- **HTTP 200**：网关/Tomcat 正常返回  
- **body 里 `code:200`**：业务成功；**`code:500`**：业务失败（如库存不足）  

JMeter「异常%」是否计入业务失败，取决于断言配置；你们复测 V2/V3 为 0% 时，通常只判 HTTP 层。

**22. 压测后如何用 `stock/result` 判断是否超锁？**

```http
GET /api/order/concurrency/stock/result?goodsId=2064625692771397632
```

看 `data.overLocked`：

- `false` 且 `lockStock <= stock` → 正常  
- `true` 或 `lockStock > stock` → 超锁  

V2/V3 期望：`stock=100, lockStock=100, usableStock=0, pendingOrderCount=100, overLocked=false`。

**23. 压测前为什么要清库？**

上次压测残留 `lockStock=109` 或大量待支付订单会导致 `usable` 为负，新压测 **全部失败**（库存不足 -9）。需删 `junit-/jmeter-` 订单并重置 `stock=100, lock_stock=0`。

## 二、V3 相关（V2 基础上追加）

### 同步 vs 异步

**24. V3 相对 V2 改了什么？没改什么？**

| 改了 | 没改 |
|------|------|
| 同步路径不写流水，改 `lockStockUpdateOnly` | `ReentrantLock(goodsId)` 防超锁 |
| 写流水 + 模拟通知进线程池异步 | 校验、建单、改 lock_stock 仍在锁内同步事务 |
| 独立 `OrderCreateConcurrencyV3SyncService` | 200 并发正确性目标（100 成功、不超锁） |

**25. V3 哪些步骤是同步的？哪些是异步的？**

**同步（Tomcat/JUnit 线程，锁内）：**

1. `lock(goodsId)`  
2. 查库存、校验  
3. 插入订单  
4. `lockStockUpdateOnly` 更新 lock_stock  
5. 事务提交  
6. `asyncExecutor.execute(...)` 仅 **入队**  
7. `return` 成功  
8. `unlock`  

**异步（`v3-async-n` 线程）：**

1. `stockService.writeFlow(...)` 写 `inventory_flow`  
2. 模拟发送通知（打日志）  

**26. `asyncExecutor.execute()` 为什么会阻塞 return？**

**不会阻塞。** `execute` 把任务放入队列后立即返回；`return Result.success` 紧跟着执行。  
写流水在 **别的线程** 稍后执行。

**27. `execute` 和 `submit().get()` 有什么区别？**

| 方法 | 行为 |
|------|------|
| `execute(Runnable)` | 提交任务，**无返回值，不等待** |
| `submit(Callable)` | 返回 `Future` |
| `future.get()` | **阻塞**直到任务完成并取结果 |

V3 用 `execute` 正是为了 **不等待** 流水写完。

**28. 异步写流水时，订单和 `lock_stock` 已经提交了吗？**

**是的。** `syncCreateOrderAndLockStock` 带 `@Transactional`，方法正常返回时事务已提交；之后才会在线程池里 `writeFlow`。

**29. 异步写流水失败会怎样？V7 为什么要补偿？**

同步已成功 → 订单存在、lock_stock 已加，但可能 **没有对应流水**。  
实验版只打 error 日志。生产需 **V7 补偿任务**（对账、重试写流水或告警人工处理），保证 **订单与流水最终一致**。

**30. 为什么线程池不能代替 `ReentrantLock` 防超锁？**

线程池只负责 **任务调度**，不保证「同一 goodsId 的读-改-写」互斥。  
若去掉 ReentrantLock，多线程仍可同时通过校验并改 lock_stock，回到 V1 竞态。  
**互斥用锁，提速用异步**——职责不同。

### 线程池

**31. V3 线程池 `core=4、max=16、queue=2000` 各表示什么？**

- **corePoolSize=4**：常驻 4 个工作线程  
- **maximumPoolSize=16**：队列满且负载高时可扩到 16  
- **queue=2000**：最多缓存 2000 个待执行任务  
- 200 并发下单会 submit 约 100 个成功单的异步任务，远小于队列容量  

**32. `CallerRunsPolicy` 是什么？队列满了会怎样？**

拒绝策略：队列满且线程数到 max 时，由 **调用者线程**（Tomcat 线程）自己执行 `Runnable`，不丢任务，但会 **拖慢 HTTP 响应**。  
正常压测不易触发。

**33. 线程名 `v3-async-1` 说明什么？**

说明 `runAsyncSideEffects` / `writeFlow` 运行在 **线程池工作线程**，不是 `http-nio-8080-exec-x`。

**34. `@PostConstruct` / `@PreDestroy` 在这里做什么？**

- `@PostConstruct initAsyncExecutor`：Spring Bean 就绪后 **创建线程池**  
- `@PreDestroy shutdownAsyncExecutor`：应用关闭时 **优雅关闭** 线程池，避免任务丢失或线程泄漏  

**35. 生产环境为什么建议 Spring `@Async` + 统一线程池？**

- 线程池参数集中配置、监控、限流  
- 与业务线程池隔离，避免实验代码硬编码  
- 便于接入链路追踪、拒绝策略、MDC 传递  

V3 硬编码 `ThreadPoolExecutor` 仅为 **演示**。

### 代码结构

**36. `OrderCreateConcurrencyV3SyncService` 为什么单独拆出来？**

- 同步核心带 `@Transactional`，边界清晰  
- 与「加锁 + 提交异步」的 `OrderCreateConcurrencyV3` 分离，职责单一  
- 便于单测同步路径、阅读对比 V2 的 `OrderInfoServiceImpl`  

**37. `lockStockUpdateOnly` 和 `lockStock` 有什么区别？**

| 方法 | 更新 lock_stock | 写 inventory_flow |
|------|-----------------|-------------------|
| `lockStock`（V2 用） | 是 | **同步写** |
| `lockStockUpdateOnly`（V3 用） | 是 | **不写**，返回 `LockStockFlowContext` 供异步补写 |

**38. `LockStockFlowContext` 是干什么用的？**

封装异步写流水所需字段：goodsId、goodsName、变动前后 lockStock、数量、订单号等。  
同步路径只改库存；异步路径用 context 调 `writeFlow`，避免异步线程再查一遍库（也可查，这里用快照传递）。

**39. `BeanUtil.copyProperties(dto, order)` 会把 `remark` 拷进订单吗？**

会。DTO 与 Entity 同名字段（含 `remark`）会复制。  
JMeter 若 Body 写 `"JMeter V1"` 而 URL 是 v3，库里 remark 仍显示 V1——是 **请求体问题**，不是代码没拷。

**40. V3 为什么在锁内 `submit` 异步任务，而不是 `unlock` 之后再提交？**

当前实现：`submit` 在锁内，但 **仅入队**，耗时极短，不包含 writeFlow。  

也可设计成 unlock 后再 submit（锁持有更短）。在锁内 submit 的考虑：

- `syncResult` 在锁内刚产生，逻辑连贯  
- 入队操作很快，对排队时间影响小  

注意：若在 unlock 后 submit，需保证 `syncResult` 数据不可变（当前对象已构建完成，可安全传递）。

### 性能与结论

**41. V3 为什么相对 V2 只快约 2～3%？**

瓶颈是 **200 请求串行过 ReentrantLock**，总时间 ≈ 100 次「锁内同步路径」累加。  
V3 每次只省略锁内 **写流水** 的几十毫秒，占单次总时间比例小，整体 RT 从约 19.3s 到约 18.9s，体感几乎无差。

**42. V3 的瓶颈主要在哪里？**

**按 goodsId 的 JVM 互斥锁排队**，不是写流水 IO，也不是线程池本身。

**43. 要明显提速，V4 打算改什么？**

- SQL 层 `UPDATE ... WHERE stock - lock_stock >= ?` **原子扣减/锁定**，缩短临界区  
- 减少「读-算-写」非原子窗口，有机会 **减小锁持有时间或去掉 JVM 锁**（视实现而定）  

**44. V3 压测后为什么要等 5～10 秒再查流水？**

流水 **异步写入**，HTTP 返回时 `inventory_flow` 可能还没写完。  
等几秒再 `COUNT(*)` 才接近 100 条。

**45. `stock/result` 和 `inventory_flow` 条数不一致一定代表失败吗？**

- **刚压完立刻查**：流水可能未写完，**不一定失败**  
- **等 10 秒仍明显少于成功单数**：可能异步写失败，需查日志 `[V3异步] 写库存流水失败`  
- **`stock/result` 的 overLocked**：看订单与 lock_stock，**不依赖流水是否写完**  

业务正确性以 `overLocked=false`、`lockStock=100` 为准；流水是 **最终一致** 副产物。

### JUnit / 工具

**46. V3 测试为什么比 V2 多一个 `Thread.sleep(5)`？**

等 `v3-async-*` 线程池写完流水，避免断言时流水条数未齐（集成测试完整性）。  
V2 全同步，不需要这段等待。

**47. `AtomicInteger` 为什么用来统计成功/失败次数？**

200 线程并发 `successCount++`，普通 `int` 会丢更新；`AtomicInteger.incrementAndGet()` **线程安全**。

**48. `@SpringBootTest` 和 JMeter 压测对环境的要求有什么不同？**

| | JUnit `@SpringBootTest` | JMeter |

| PostgreSQL / Redis | 需要 | 需要 |
| 前端 | 不需要 | 不需要 |

## 三、V2 vs V3 综合对比

**49. 用一句话说 V2 和 V3 的设计目标分别是什么？**

- **V2**：用 JVM 锁保证 **不超锁**，接受串行带来的延迟  
- **V3**：在 V2 正确性前提下，**同步/异步拆分**，缩短锁内路径，验证非核心 IO 可后置  

**50. 正确性上 V2 和 V3 应该满足什么相同指标？**

- 200 并发：成功 ≤ 100，失败 ≥ 100  
- `lockStock = 100`，`overLocked = false`  
- 待支付订单约 100 条  

**51. 性能上 V3 相对 V2 的合理预期是什么？**

同机 200 线程复测：平均 RT **小幅下降**（约 2～3%），吞吐在同一量级；**不会出现数量级提升**。  
要明显变快看 V4+。

**52. 面试时如何用压测数据讲 V2 → V3 的演进和结论？**

> V1 无锁 200 并发超锁 109。V2 对 goodsId 加 ReentrantLock，JMeter 200 线程 100 成功、overLocked false，但平均 RT 约 19s，因为锁内串行。
> V3 保留同一把锁，同步只做建单和 lockStockUpdateOnly，写流水异步化；复测 RT 约 18.9s，只快约 3%，说明瓶颈在锁排队而非流水 IO。
> 下一步 V4 用 SQL 原子更新缩短临界区。
