# 并发 V7 问答整理（幂等 + 补偿）

> 压测：`POST .../order/add?version=v7`（Body 必带 `idempotentKey`）  
> 步骤：[`并发/步骤-V7.md`](./步骤-V7.md)

---

## 1. V7 解决什么？

V4/V6 能防「多人抢库存超锁」，但防不了：

- 用户连点 / 前端重试 → **同一业务请求做两次**
- MQ 至少一次投递 → **同一消息消费两次**
- 锁库存成功、落单失败且 unlock 也失败 → **半成功残留**

V7 用 **幂等键** + **补偿任务** 收口。

## 2. 幂等怎么做的？

Redis：`SET inventory:idempotent:order:{key} PROCESSING NX EX`  
成功后再走 V4；成功后改成 `DONE:{orderNo}`。  
后来者读到 DONE 直接返回原单号，不再锁库存。

## 3. 为什么业务失败要 clear？

库存不足时若保留 PROCESSING，用户永远没法用同一 key 重试。  
失败清掉 = 允许合理重试。

## 4. 补偿任务干什么？

落单失败后立即 unlock；若 unlock 也失败，登记到  
`inventory:v7:compensate:unlock`，定时任务再调库存 unlock。

## 5. 压测怎么验收？

- Apifox：同 key 连点 → 只增 `lockStock=1`
- JMeter 200 同 key：平均 RT ~62ms、吞吐 ~187/s、异常 0%、**lockStock=1**
- 别和 V6 比「锁满 100」；V7 看的是**防重复**

## 6. 面试 30 秒

「V7 在 V4/V6 上补幂等和补偿：同一幂等键只真正下单一次；半成功用定时任务重试解锁。并发主线到此闭环。」
