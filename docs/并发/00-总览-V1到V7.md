# 库存并发演进：V1 → V7 总览

> 场景：下单锁库存（库存 100，压测约 200 并发）  
> 生活类比：**公共厕所只有 100 个坑，200 人同时冲进来抢**  
> 压测入口：`POST /api/order/concurrency/order/add?version=v1`（order-service:8083，仅 dev）  
> 详细压测数据见 [`01-压测数据.md`](./01-压测数据.md)  
> 代码根目录：`order-service/.../concurrency/v1`～`v7`；库存原子 SQL 在 `inventory-service` 的 Mapper

---

## 一、为什么要考虑并发？（用抢厕所说清楚）

下单不是一步做完，大致是：

```text
看一眼还有几个空坑 → 登记「我要用」（建订单） → 真正占上坑（锁库存）
```

一个人慢慢来：看完再占，没问题。

很多人**同时**冲进来：如果「看还有空」和「真正占上」中间能被别人插队，就会出现——

- 大家都看到「还剩 5 个空」
- 大家都登了记
- 实际却占出了 **109 个坑**，厕所明明只有 **100 个**（你们 V1 实测）

这就是超锁 / 超卖：名额对不上，有人以为占到了其实没有，或账本比真实坑位多。所以要一套一套加手段。

---

## 二、怎么读这条演进线？

每个版本都按四句话看：

1. **解决了什么问题**
2. **为什么这么做 / 怎么做的**
3. **关键概念是什么意思**
4. **什么情况下又不够用了 → 下一版补什么**

记住一句总纲：

> **不是越新越替换旧的。**  
> V4 保「坑别超占」；V6 保「高峰别把门口堵死」；V7 保「别同一人占两次、占错了能放」。

## 三、版本演进（核心）

### V1｜无并发控制（基线：故意翻车）

| 项 | 说明 |
|----|------|
| 解决 | 不解决问题，专门**复现**超锁长什么样 |
| 为什么做 | 没有基线，后面说「修好了」没法证明 |
| 做法 | 看还有空 → 登记 → 再非原子占坑；多人可交错 |
| 结果 | 200 并发稳定锁到 109（库存 100） |

**抢厕所例子：**  
十个人同时探头：「还有空吗？」都说「有」；十个人都往里冲并登了记；坑却不够十个——有人登记成功，进去发现没位。

**关键概念：竞态（race）**  
多个请求都看到「还有空」，都认为自己能占，最后一起加 lock。

**代码要点（项目实装）**  
文件：`OrderCreateConcurrencyV1SyncService#syncCreateOrderNonAtomic`

```java
// 步骤 1：先读可用库存（某一瞬间的快照）
int usableStock = inventoryStockClient.getUsableStock(dto.getGoodsId());
if (usableStock < dto.getBuyQty()) {
    throw new IllegalStateException("库存不足…");
}
// 步骤 2：先落订单
orderInfoService.save(order);
// 步骤 3：非原子锁库存（库存侧只做 lock_stock += qty，没有「够才扣」WHERE）
inventoryStockClient.lockNonAtomic(dto.getGoodsId(), dto.getBuyQty());
```

```text
线程 A：读到可用=1 ──┐
线程 B：读到可用=1 ──┤ 都觉得「还有 1」
线程 A：建单 + lock+1
线程 B：建单 + lock+1  → 超锁
```

**翻车点：** 一压测就翻车。  
**下一版：** 同一坑区同一时刻只让一个人走完「看-登记-占坑」→ **V2**。

---

### V2｜JVM 锁（ReentrantLock，按 goodsId）

| 项 | 说明 |
|----|------|
| 解决 | 单机多线程竞态 → **不再超锁** |
| 为什么做 | 最直观：门口排队，一次只放一个人进去办完手续 |
| 做法 | 按 `goodsId` 抢一把**本机内存锁**，临界区内串行「读-建单-锁库存」 |
| 结果 | 不超锁（100/100），但同商品串行，RT 约 20s 级 |

**抢厕所例子：**  
这栋楼厕所门口竖一块牌子：**同一时间只进一个人**看空位、拿号、关门。这一栋不会超占。

**关键概念：临界区**  
必须互斥保护的那段代码（看空位 + 登记 + 占坑）。锁住整段 → 正确；代价是门口排队干等。  
在代码里 = `lock.lock()` 到 `lock.unlock()` 之间那次 `syncCreateOrderNonAtomic`。

**代码要点（项目实装）**  
文件：`OrderCreateConcurrencyV2`

```java
ReentrantLock lock = lockForGoods(dto.getGoodsId()); // 本 JVM 内按商品一把锁
lock.lock();
try {
    // 临界区：仍调用 V1 那套「读→建单→非原子锁」
    String orderNo = v1SyncService.syncCreateOrderNonAtomic(dto);
    return Result.success("…V2…" + orderNo);
} finally {
    lock.unlock();
}
```

**翻车点：**
1. **多栋楼 / 多实例**：每栋楼门口各管各的，互不知道，共享那 100 个坑仍可能超占。
2. **慢**：大家都抢同一间热门厕，后面的人干等。

**下一版：** 要提速 / 缩短临界区 → **V4**；多实例协调 → **V5**。

---

### V3｜线程池（任务拆分 + 异步）

| 项 | 说明 |
|----|------|
| 解决 | 在 V2 正确性上，把次要工作挪出主路径 |
| 为什么做 | 写流水、发短信不是「会不会超占」的关键路径 |
| 做法 | 主路径仍用 goodsId 锁；写流水等丢线程池异步做 |
| 结果 | 正确性同 V2，RT 只比 V2 好约 2～3% |

**抢厕所例子：**  
「看空位 → 占坑」仍必须门口排队；「把使用记录抄进账本、发短信通知保洁」交给后勤慢慢写。门口还是慢，只是抄账不堵主流程。

**关键概念：主路径 vs 旁路**  
瓶颈仍在那把锁上。异步旁路解决不了「热门坑必须串行」的主矛盾。

**代码要点（项目实装）**  
文件：`OrderCreateConcurrencyV3`

```java
lock.lock();
try {
    // 主路径（同步）：校验 + 建单 + 只改 lock_stock
    V3SyncCreateResult syncResult = syncService.syncCreateOrderAndLockStock(dto);
    // 旁路（异步）：写流水、模拟通知 —— 不堵返回
    submitAsyncSideEffects(syncResult);
    return Result.success("…V3：流水异步写入中");
} finally {
    lock.unlock();
}
```

**翻车点：** 多实例问题还在；性能提升可忽略。  
**下一版：** 真正提速 → 把「够不够」沉到数据库一次 UPDATE → **V4**。

---

### V4｜SQL 原子锁库存（正确性底座）

| 项 | 说明 |
|----|------|
| 解决 | 单机锁太慢；用数据库条件 UPDATE 保证「够才扣」 |
| 为什么做 | 数据库行更新天然串行；「判断」和「占上」合成一步，中间插不了队 |
| 做法 | `UPDATE … SET lock_stock=… WHERE stock - lock_stock >= qty`；影响行数=0 即库存不足 |
| 结果 | 不超锁；平均 RT ~14s、吞吐 ~10/s，明显好于 V2/V3 |

**抢厕所例子：**  
不再先口头问「还有空吗」再冲进去。改成**电子门锁**：系统规定——**还有空位才开得了门**；没空就刷不开。多栋楼同时刷，数据库保证不会占成 101。

**关键概念：条件更新（带着条件去写）**  
不先读再写，而是「够才改成功」。写失败 = 竞争失败 / 没位了。这是生产里锁库存最常见、最稳的底座。

**代码要点（项目实装）**

订单侧：`OrderCreateConcurrencyV4SyncService`（先原子锁，再落单）

```java
String orderNo = OrderNoGenerator.generate(OrderPrefix.ORDER);
// 远程调库存：内部走「够才扣」原子 SQL（不是 V1 的 lockNonAtomic）
inventoryStockClient.lock(dto.getGoodsId(), dto.getBuyQty(), orderNo);
orderInfoService.save(order);
```

库存侧核心 SQL：`InventoryStockMapper.xml` → `lockStockIfAvailable`

```sql
UPDATE inventory_stock
SET lock_stock = lock_stock + #{qty},
    update_time = NOW()
WHERE goods_id = #{goodsId}
  AND stock - COALESCE(lock_stock, 0) >= #{qty};
-- 影响行数=1 → 占坑成功；=0 → 没空，抛「库存不足」
```

Java 判断：

```java
int affectedRows = inventoryStockMapper.lockStockIfAvailable(goodsId, qty);
if (affectedRows == 0) {
    throw new IllegalStateException("库存不足…");
}
```

**翻车点（展开理解）：**

1. **无幂等：连按两下可能占两个坑**  
   V4 只保证「不够就不能占」（防超卖）。同一个人连点两次 = 两次合法 UPDATE，每次都够就会各占 1 次。  
   → 防的是「很多人抢超占」，不是「同一人点两次」。要 V7。

2. **同步占满 HTTP 线程**  
   请求必须等这条 UPDATE + 建单做完才返回。人一多，工作线程都堵在等 DB，门口接待位满了。  
   → 要削峰用 V6（先回「已排队」）。

3. **「先看再占」老代码 vs 你们的 V4**  
   - 老代码：先 SELECT 再 UPDATE → 多实例仍竞态，才需要 V5 包一层。  
   - 你们 V4：条件 UPDATE 一步完成 → **锁库存优先靠 V4**，不必再用 Redis 锁替代它。V5 是练分布式锁/其它串行场景。

**下一版：** 分布式锁练手 → **V5**；削峰异步 → **V6**；防重复 → **V7**。

---

### V5 / V5r｜Redis 分布式锁

| 项 | 说明 |
|----|------|
| 解决 | 多 JVM 时本地锁失效 → 大家抢**同一把**逻辑锁 |
| 为什么做 | 把「通行证」放到云端（Redis），所有楼栋共用一个入口权 |
| 做法 | V5：手写 `SET NX EX` + Lua 解锁；V5r：Redisson **看门狗**续期。临界区可复用 V1 非原子，证明「只靠跨机锁也能防超锁」 |
| 结果 | 不超锁；RT ~23～25s，接近 V2、**慢于 V4**；高压下部分抢锁超时 → lockStock 可能 <100（不是超锁） |

**抢厕所例子：**  
三栋楼共用一个厕区。中央挂一个**共享通行证**（Redis）：谁抢到证谁才能进去看+占。比「每栋楼自己门口拦人」（V2）靠谱——大家抢的是同一张证。

**关键概念：**
- **NX（Not eXists）**：只有还没人占着才能占上 → 抢锁。
- **看门狗：** 你进去超时了还没出来，系统自动帮你续「占用时间」，避免证过期别人闯进来；用完再主动交证。
- **V4 vs V5：** 不是谁取代谁。V4 = 坑位账本本身正确（门锁规则）；V5 = 应用层跨楼互斥能力（某些必须串行的业务）。

**代码要点（项目实装）**

策略入口：`OrderCreateConcurrencyV5`（外壳和 V2 一样，锁换成 Redis）

```java
String token = goodsStockRedisLock.tryLock(dto.getGoodsId(), lockWaitMs, lockLeaseSeconds);
if (token == null) {
    return Result.fail("系统繁忙，获取商品库存锁超时（V5 Redis）…");
}
try {
    // 临界区故意仍用 V1 非原子链路，证明「只靠跨机锁也能防超锁」
    String orderNo = v1SyncService.syncCreateOrderNonAtomic(dto);
    return Result.success("…V5…" + orderNo);
} finally {
    goodsStockRedisLock.unlock(dto.getGoodsId(), token);
}
```

锁工具：`GoodsStockRedisLock`

```java
// 加锁：SET key token NX EX（不存在才写入 + 过期防死锁）
Boolean ok = stringRedisTemplate.opsForValue().setIfAbsent(key, token, lease);

// 解锁：Lua 校验「还是我的 token」再 DEL，防止误删别人的锁
// if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end
```

V5r：同样流程，锁换成 Redisson（`GoodsStockRedissonLock` + 看门狗自动续期）。

**翻车点：** 同商品仍串行干等 → 体感「门口卡住空白一会」。  
**下一版：** 门口不想让人干等 → **V6**（真正占坑仍可靠 V4）。

### V6｜RabbitMQ 异步（削峰 + 最终一致）

| 项 | 说明 |
|----|------|
| 解决 | 同步锁库存把 HTTP 堵死 → **削峰、解耦、接口秒回** |
| 为什么做 | 高峰先把人「收下登记」，真正分坑放到后台慢慢做 |
| 做法 | 生产者发消息立刻返回「已受理」；消费者再调 **V4** 原子锁 + 建单 |
| 结果 | HTTP 平均 RT **93ms**、吞吐 **258/s**；最终 lockStock=100、不超锁 |

**抢厕所例子：**  
高峰不再让所有人堵在门口等「坑真的分到你」。保安扫码后立刻给你一张「**已排队/已受理**」小票（秒回），单子进后台队列；后台用 V4 规则慢慢占坑。你刚拿到小票去查，可能还没占满 100；过一会才到 100——这就是**最终一致**。

**关键概念：**
- **最终一致：** 返回「成功/已受理」≠ 当时已占上坑；过一小段时间才一致。前端应展示「分配中 / 查单」，别当成同步占坑完成。
- **正确性不靠 MQ：** 队列只负责传单；会不会超占，靠消费者里的 V4。
- **至少一次投递：** 同一张排队单可能被后台看到两次 → 没有幂等就会占两个坑。

**代码要点（项目实装）**

生产者：`OrderCreateConcurrencyV6`（只发消息，立刻返回）

```java
OrderLockStockMessage message = new OrderLockStockMessage();
BeanUtil.copyProperties(dto, message);
rabbitTemplate.convertAndSend(RabbitMqConfig.QUEUE_ORDER_LOCK_STOCK, message);
return Result.success("V6：已受理，库存锁定处理中"); // HTTP 秒回
```

消费者：`OrderLockStockConsumer`（真正建单，走 V4）

```java
@RabbitListener(queues = RabbitMqConfig.QUEUE_ORDER_LOCK_STOCK)
public void onMessage(OrderLockStockMessage message) {
    // 若带 idempotentKey，可先走 V7 幂等（防重复消费）
    String orderNo = v4SyncService.syncCreateOrderWithSqlLock(dto); // 正确性靠 V4
}
```

```text
HTTP 线程                     RabbitMQ                    消费者
   |-- 发消息 --------------->|                            |
   |<-- 立刻「已受理」 --------|                            |
   |                          |-- 投递 ------------------->|
   |                          |                            |-- V4 原子锁+建单
```

**翻车点：** 重复消费、半成功（坑占了但登记没写上）、积压、死信。  
**下一版：** 幂等 + 补偿 → **V7**。

### V7｜幂等 + 补偿（可靠性收口）

| 项 | 说明 |
|----|------|
| 解决 | 重复提交 / 重复消费、中间失败导致的不一致 |
| 为什么做 | 防超占解决的是「很多人抢」；生产更多翻车是「同一人占了两遍」和「只做了一半」 |
| 做法 | Redis 幂等键（`idempotentKey`）+ V4 建单；unlock 失败登记定时补偿 |
| 压测 | 同 key 200 并发：平均 RT ~62ms、吞吐 ~187/s，**lockStock=1**（防重复达标） |

**抢厕所例子：**
- **幂等：** 你手抖连按三下「占坑」。系统认同一个「业务号」：只占一个坑，后两次直接告诉你「你已经有号了，还是 xxx」。
- **补偿：** 坑已经锁上了，登记本卡纸没写上，当时又没能把坑释放 → 记到「待处理本」；后台定时任务再去放坑，避免账对不上。

**关键概念：**
- **幂等键粒度：** 太粗（只用「手机号」）会误伤你正常再占第二次；太细（每次随机 UUID）等于没幂等。生产常用：前端业务单号、支付 `out_trade_no`、或合理时间窗内的业务键。
- **PROCESSING：** 同 key 并发时，后来者可能看到「处理中」而不是立刻「已完成」——属正常。
- **业务失败要清 key：** 没位了若一直占着「处理中」，用户无法用同一 key 合理重试。

**代码要点（项目实装）**

策略入口：`OrderCreateConcurrencyV7`

```java
// 1. 必须带幂等键
if (StrUtil.isBlank(dto.getIdempotentKey())) {
    return Result.fail("V7 必须传 idempotentKey…");
}
// 2. Redis 占位：空=可继续；有值=处理中或已有订单号
var hit = idempotentService.tryBegin(key);
if (hit.isPresent()) {
    if (hit.get().inProgress()) {
        return Result.fail("V7：相同幂等键正在处理中…");
    }
    return Result.success("V7 幂等命中，返回原订单号：" + hit.get().orderNo());
}
// 3. 真正建单仍走 V4；成功 markDone，失败 clear 允许重试
try {
    String orderNo = v4SyncService.syncCreateOrderWithSqlLock(dto);
    idempotentService.markDone(key, orderNo);
    return Result.success("V7 下单成功…orderNo=" + orderNo);
} catch (…业务失败…) {
    idempotentService.clear(key);
    return Result.fail(…);
}
```

幂等服务：`OrderIdempotentService`（Redis）

```java
// SET NX → value=PROCESSING；成功后再改成 DONE:{orderNo}
stringRedisTemplate.opsForValue().setIfAbsent(redisKey, "PROCESSING", ttl);
// 后来者读到 DONE:xxx → 直接返回原单号，不再锁库存
```

补偿：`OrderCompensateRegistry` + `OrderConcurrencyCompensateJob`（unlock 失败登记，定时重试放坑）。

**注意：** V7 压测看的是**同 key 只锁一次**，不是「锁满 100」。别和 V6 比 lockStock。

**翻车点：** 幂等键设计不好会误伤；补偿不是实时，需监控。  
**说明：** 并发主线到此收口。Topic / 死信 / 积压监控见下文「生产补强」。

## 四、一句话对照（适合背）

| 版本 | 一句话（抢厕所版） | 什么情况逼你上下一版 |
|------|--------------------|----------------------|
| V1 | 大家同时探头看有空，结果超占 | 发现竞态 → 上锁 |
| V2 | 本栋楼门口排队，正确但慢 | 多栋楼 / 要提速 |
| V3 | 抄使用记录交给后勤，门口仍慢 | 要明显提速 → SQL 原子 |
| V4 | 电子门锁「空才开得了」，正确又更快 | 多实例协调 / 异步削峰 / 幂等 |
| V5 | 多栋楼共用一张通行证（Redis） | 门口不想同步干等 |
| V6 | 先给「已排队」，后台再分坑 | 重复占坑与半成功 |
| V7 | 同一业务号只占一次 + 占错能放 | 生产可靠性闭环 |

## 五、两条升级路径（别搞混）

### 路径 A：正确性主线（别超占）

```text
V1 超占
  → V2 单栋楼不超占
  →（多栋楼）V5 或直接用 V4
  → V7 防同一人占两遍 / 半成功能放
```

### 路径 B：体验 / 架构主线（别堵死门口）

```text
V2 / V5 同步太慢
  → V4 缩短临界区（更快）
  → V6 异步秒回「已排队」
  → V7 补最终一致带来的坑
```

你们 V6 消费者里复用的是 **V4**，所以正确性不靠「发消息」，靠后台占坑时的原子 SQL。

## 六、关键概念速查（抢厕所对照）

| 术语 | 人话 | 抢厕所对照 |
|------|------|------------|
| 超锁 / 超卖 | 锁走的货 > 真实库存 | 只有 100 个坑，却发出 109 张「已占用」 |
| 竞态 | 多人都基于旧信息做决定 | 同时探头「有空吗」都得到「有」 |
| 临界区 | 必须互斥的那段逻辑 | 从看空位到占上坑，中间不能插队的部分 |
| 条件 UPDATE | 带着「够才改」去写库 | 电子门锁：空才开得了 |
| 分布式锁 | 多机共享一把锁 | 多栋楼共用一张通行证 |

| 幂等 | 同一请求做多次 = 做一次 | 连按三下只占一个坑 |
| 补偿 | 半成功之后的修补 | 占了坑但登记失败 → 事后放坑 |

## 七、生产环境还有哪些问题？如何解决？（理解向，不必动手）

> V1～V7 是面试主线；下面是**大厂常问的加分项**。  
> 目标：能完整口述「是什么 → 为什么 → 怎么解 → 关键名词」；**不必自己动手搭**。  
> 每条结构：现象 → 抢厕所 → 名词 → 标准解法 → **面试完整口述**（正常答题长度，不限 30 秒）。

先看总表：

| 问题 | 一句话 | 标准解法关键词 |
|------|--------|----------------|
| MQ 积压 | 进队比分坑快 | 扩容 + 限流（含漏桶）+ 降级 + 监控 |
| 死信 / 毒消息 | 坏单反复失败堵队列 | 重试上限 + DLX + 人工重放 |
| 消息丢失 | 排队条进队后失踪 | Confirm + 持久化 + 手动 Ack |
| 幂等存储故障 | Redis 挂了幂等失效 | Redis + DB 唯一索引双保险 |
| 补偿滞后 | 半成功不能靠人工盯 | 定时补偿 + 对账扫尾 |
| 最终一致体验 | 已受理 ≠ 已占坑 | 状态机 + 查单/推送 |
| 热点商品 | 一行库存被打爆 | 分桶 / 预扣缓存（进阶） |
| 可观测性 | 出事找不到从哪坏 | 业务单号贯穿 + 流水 + 追踪 |

### 7.1 MQ 积压

**现象：** 队列里消息越堆越多，下单「已受理」了，很久才真正锁库存；延迟越来越大，甚至拖垮消费端。

**抢厕所：** 高峰一小时来了 1000 人，门口疯狂发「已排队」小票，后台只有 2 个管理员分坑，墙上条子贴满，出坑越来越慢。

**关键名词：**

| 名词 | 含义 |
|------|------|
| 队列深度 | 墙上还没处理的条子数量 |
| 消费延迟 | 从发号到真正分到坑的时间差 |
| 削峰填谷 | 高峰先收下排队，空闲时再慢慢消化（V6 本身就是） |
| 限流 | 控制入口速度，避免无限往墙上贴 |
| 降级 | 撑不住时减少功能或直接拒绝一部分请求，保命 |

**大厂标准解法（组合拳）：**

1. **扩容消费者**：多开几个后台实例 / 提高并发消费。  
2. **入口限流**：网关 / Sentinel 限制每秒受理量（漏桶、令牌桶等，见 7.9）。  
3. **降级**：深度超阈值 → 提示「太火爆请稍后」，或只建意向单、暂缓锁库存。  
4. **监控告警**：盯深度、延迟、消费速率；持续上涨就报警。

```text
客人申请 ──限流──▶ 发号进 MQ ──▶ [队列积压?] ──▶ 多个后台消费者
                      │                │
                      │                └─ 深度告警 / 降级
                      └─ 秒回「已排队」
```

**面试完整口述：**  
「MQ 积压指生产速度长期大于消费速度，队列深度持续上涨，用户已经拿到已受理，但真正锁库存越来越慢。本质是削峰之后填谷跟不上。处理上我们不会只加机器：一是扩容消费者提高消化能力；二是入口限流，比如用漏桶或令牌桶把受理速率压住，避免无限往队列里堆；三是设队列深度阈值，超了就降级提示繁忙，保护下游；四是监控队列深度和消费延迟，上涨就告警。和我们项目的关系是：V6 用 MQ 做了削峰，生产上还要把积压监控和限流补上，否则最终一致的延迟会不可接受。」

---

### 7.2 死信 / 毒消息

**现象：** 某条消息怎么消费都失败；若无限重试，会一直占着消费者，后面的正常单也卡住。

**抢厕所：** 一张条子写着「去占不存在的 999 号坑」，管理员反复试、反复失败，后面正常人的条子全堵着。

**关键名词：**

| 名词 | 含义 |
|------|------|
| 毒消息 | 怎么处理都失败的那条坏单 |
| 死信队列 DLX/DLQ | 装问题单的隔离箱子，不再堵主通道 |
| 重试 | 失败后再投递几次；必须有上限 |
| 至少一次投递 | MQ 可能把同一条消息交给你多次 |

**大厂标准解法：**

1. **有限重试**（如 3～5 次）+ 间隔。  
2. **超过次数进死信**，主队列继续跑。  
3. **告警 + 人工/任务重放**。  
4. **重放必须幂等**（V7）。

```text
主队列 ──失败──▶ 重试(≤N)
                 ├─ 成功 → 结束
                 └─ 仍失败 → 死信 → 告警 → 修复后重放（带幂等）
```

**面试完整口述：**  
「毒消息是怎么消费都失败的消息。如果无限重试，消费者会被它拖死，正常消息也处理不了。生产上必须设重试上限，超过次数进入死信队列隔离，同时告警让人处理。修复数据或修 bug 后可以重放，但重放一定要有业务幂等，否则同一条业务会锁两次库存。我们项目 V6 教学里还没上完整死信，但面试要能讲清：主队列、重试、死信、告警、幂等重放。」

---

### 7.3 消息丢失

**现象：** 用户以为下单成功了，后台从未收到 → 既没订单也没锁库存。

**抢厕所：** 保安喊「后台给这人分个坑」，纸条被风吹走，两边都以为对方知道了。

**关键名词：**

| 名词 | 含义 |
|------|------|
| Publisher Confirm | Broker 回执「我收下了」，生产者才敢当成功 |
| durable / 持久化 | 队列、消息落盘，Broker 重启不易丢 |
| Ack | 消费者确认「我处理完了」；手动 Ack = 办完再确认 |
| 至少一次 | 防丢后更容易出现重复投递 |
| 可靠投递 + 幂等 | 大厂标配：先尽量不丢，重复了靠业务去重 |

**丢在哪三截 & 怎么防：**

| 环节 | 怎么丢 | 标准防丢 |
|------|--------|----------|
| 生产者 → Broker | 发了但没收下 | Confirm |
| Broker | 只在内存，进程挂了没了 | 队列/消息持久化 |
| 消费者 | 没做完就 Ack，再挂了 | 手动 Ack，成功后再确认 |

```text
发号 ──Confirm──▶ Rabbit(持久化) ──▶ 分坑成功 ──再──▶ Ack
```

**面试完整口述：**  
「消息丢失要分三段看。第一段生产者到 Broker：要用发布确认，Broker 明确收下才算发送成功。第二段 Broker 自身：队列和消息要持久化，避免重启丢。第三段消费者：要用手动 Ack，业务真正成功后再确认，避免处理到一半进程挂了消息却被当成消费完。防丢之后投递更接近至少一次，重复概率上升，所以必须配业务幂等。口头禅就是：可靠投递加业务幂等一起上。我们 V6 教学版先保证连通和 durable 队列，Confirm、手动 Ack 属于生产加深项。」

---

### 7.4 幂等存储故障

**现象：** 幂等记在 Redis；Redis 挂了或 Key 丢了，同一意图可能再锁一次库存。

**抢厕所：** 防连点的「已办业务号台账」丢了，你连按两下，系统又占了一个坑。

**关键名词：**

| 名词 | 含义 |
|------|------|
| 幂等 | 同一请求做多次，效果等于做一次 |
| 双保险 | 快路径 + 兜底路径，不能只靠一层 |
| 唯一索引 | DB 对业务单号 UNIQUE，第二次插入直接冲突 |
| 降级策略 | Redis 挂了时：只靠 DB，或暂时拒绝下单 |

**大厂标准解法：**

1. **Redis SET NX**：挡绝大多数连点 / 重复消费（你们 V7）。  
2. **订单表业务单号 UNIQUE**：Redis 全挂时第二次插入冲突 → 查已有单返回。  
3. **写清降级预案**。

```text
同一业务单号
  ├─① Redis 快路径
  └─② DB UNIQUE 兜底
```

**面试完整口述：**  
「幂等如果只放在 Redis，Redis 故障或 Key 过期丢失时，同一业务可能再次下单锁库存。生产标准是双保险：Redis 做快速去重，数据库对业务单号或幂等键建唯一索引做最终兜底。即使 Redis 全挂，第二次写库会唯一键冲突，我们把它当成幂等命中，返回原单，而不会再锁一次。同时要事先约定降级策略。我们项目 V7 已实现 Redis 幂等，面试补一句生产还会加 DB 唯一约束即可。」

---

### 7.5 补偿滞后

**现象：** 半成功靠定时任务修，中间一段时间账对不上（有 lock 无单等）。

**抢厕所：** 坑已锁上，登记本没写成，退坑要等店长定时巡检——这中间账是不平的。

**关键名词：**

| 名词 | 含义 |
|------|------|
| 半成功 | 只做完链路一半（如锁了库存、订单没落库） |
| 补偿 | 事后把系统修回一致（解锁、关单、补单等） |
| 对账 | 定期扫两边数据差异，不依赖单次补偿一定成功 |
| 最终一致 | 允许短暂不一致，之后收敛 |

**大厂标准解法：**

1. 失败路径**先立刻 unlock**；失败再进补偿队列（你们 V7）。  
2. **定时 Job** 重试。  
3. **对账扫尾**：有锁无单 / 有单无锁。  
4. **告警**：补偿堆积、差异数 > 0。

**面试完整口述：**  
「补偿滞后是说半成功不能靠人肉盯，定时任务修之前会有短暂不一致，这在分布式里是可接受的，但要可控。标准做法分三层：业务失败时先同步尽量回滚，比如落单失败立刻 unlock；unlock 也失败就登记补偿表，由定时任务重试；最后还有对账任务扫描有锁无单、有单无锁做兜底，并告警。我们 V7 已经有补偿登记和定时 unlock，生产口述时强调对账扫尾更完整。」

---

### 7.6 最终一致体验

**现象：** 接口已返回已受理，用户立刻查订单/库存还没变 → 以为系统坏了。

**抢厕所：** 给了「已排队」小票，人冲去坑位，坑还没分到。

**关键名词：**

| 名词 | 含义 |
|------|------|
| 最终一致 | 先应答，稍后数据才对齐 |
| 状态机 | 订单状态分阶段流转，不能一步当成完成 |
| 轮询 / 推送 | 前端主动查，或服务端推状态变化 |

**大厂标准解法：**

1. 状态：`已受理` → `已锁库存` → `待支付/使用中` → `完成`  
2. 前端展示「处理中」，轮询或 WebSocket。  
3. 用业务单号查单，别只看 HTTP 200。  
4. 长时间停在已受理 → 失败可重试 + 触发补偿。

**面试完整口述：**  
「用了 MQ 异步之后，返回成功只代表受理，不代表库存已经锁上，这叫最终一致。如果前端把受理当成下单完成，用户一查发现没有订单就会投诉。所以要把状态机暴露清楚：已受理、锁库存成功、待支付等。接口返回业务单号，前端轮询或推送刷新；长时间停在已受理要展示失败并允许重试。体验问题和正确性是两件事：正确性靠消费者里的 V4，体验靠状态可见。」

---

### 7.7 热点商品（进阶）

**现象：** 爆款 SKU 所有请求打同一行库存，行锁/更新成为瓶颈，RT 飙升。

**抢厕所：** 全场只认「一号 VIP 厕」同一行账，所有扣减挤在一行上。

**关键名词：**

| 名词 | 含义 |
|------|------|
| 热点行 | 数据库某一行被超高并发更新 |
| 库存分桶 | 把总量拆成多段库存，请求打散 |
| 缓存预扣 | Redis 先扣可售额度，再异步落库 |
| 对账 | 预扣/分桶后必须和 DB 对平 |

**解法思路（了解即可）：** 分桶打散、Redis 预扣 + 异步落库、秒杀排队放行。

**面试完整口述：**  
「热点商品是单行库存被打爆，即使有条件 UPDATE 正确，性能也会很差。常见优化是库存分桶，把 100 拆成多个桶降低行竞争；或者 Redis 预扣再异步落库。无论哪种都要对账，防止缓存和数据库不一致。我们主线用 V4 保证正确，热点属于性能进阶，面试提到分桶或预扣加对账就够。」

---

### 7.8 可观测性

**现象：** 账对不上，日志一堆，找不到是哪一单、卡在哪一步。

**抢厕所：** 客人投诉拿了号没分到坑，门口小票、墙上条子、占坑本对不上号。

**关键名词：**

| 名词 | 含义 |
|------|------|
| 业务单号 | 贯穿全链路的业务 ID（幂等键 / orderNo） |
| TraceId | 一次请求在网关→服务→MQ 的调用链 ID |
| 库存流水 | 每次 lock/unlock 的留痕 |
| 对账报表 | 定期输出差异单列表 |

**解法：** 业务单号贯穿日志/MQ/流水；库存流水；对账报表；链路追踪。

**面试完整口述：**  
「出了不一致，先要能定位。我们要求业务单号贯穿下单日志、MQ 消息、消费日志和库存流水；再配合 TraceId 做链路追踪，以及对账报表列出差异单。这样半成功是卡在发消息、消费还是 unlock，才能快速看出来。可观测性不是业务功能，但是生产排障的基础设施。」

### 7.9 限流补充：漏桶算法详解（复习加餐）

> 和积压强相关：入口太猛就会把 MQ 堆爆。限流常用 **漏桶**、**令牌桶**。你们有 Sentinel，面试常问原理。

#### 漏桶是什么（Leaky Bucket）

把请求想成水，系统想成一个桶：

```text
请求（水） ──灌入──▶ [ 桶 ||||||| 容量 ] ──匀速漏出──▶ 真正处理
                         │
                         └─ 满了 → 溢出拒绝 / 等待
```

| 要点 | 说明 | 抢厕所 |
|------|------|--------|
| 桶容量 | 最多积压多少请求 | 门口等候区只能站 N 人 |
| 漏出速率 | 系统**恒定**每秒处理多少 | 保安固定每秒只放行 10 人 |
| 灌入突发 | 可以一下子倒很多水 | 一瞬间来 100 人 |
| 溢出 | 桶满了，多余请求被拒绝 | 等候区满了，后面的人进不来 |

**核心特性：出口速率平滑（恒定），把不规则流量「削」成匀速。**  
很适合保护下游（DB、库存服务、MQ 消费者）不被尖峰打死。

**和削峰填谷的关系：** 漏桶本身就是一种削峰——尖峰灌进来，匀速漏出去；漏不完且桶满就拒绝。

#### 和令牌桶的对比（常一起考）

| | 漏桶 | 令牌桶 |
|--|------|--------|
| 思路 | 请求当水，匀速漏出 | 系统匀速发令牌，有令牌才放行 |
| 出口 | **更平滑**，近似恒定速率 | 有积攒令牌时，允许**短暂突发** |
| 突发 | 对下游更友好（更稳） | 对用户更友好（偶尔能冲一把） |
| 生活类比 | 漏水桶，出口细管子匀速 | 食堂发餐券，券攒多了可一小撮人连续进 |

```text
令牌桶：
  令牌生成器 ──匀速放令牌──▶ [ 令牌桶 ]
请求来了要先拿令牌；没令牌 → 拒绝/排队
```

**面试怎么选：**  
- 要死保下游稳定 → 偏 **漏桶**  
- 要允许正常突发、平均速率受限 → 偏 **令牌桶**（Sentinel 等常用）  
口述一句：「两者都限流；漏桶强调出口恒定，令牌桶允许一定突发。」

#### 漏桶面试完整口述

「漏桶算法把请求当成水倒进固定容量的桶，桶以恒定速率漏水，也就是系统以恒定速率处理请求。短时间突发可以先进桶里缓冲，桶满了就拒绝或阻塞。这样下游看到的是平滑流量，适合保护数据库和 MQ 消费者。它和令牌桶的区别是：漏桶出口更匀，令牌桶允许在有剩余令牌时出现短暂突发。和我们并发故事的关系是：V6 用队列削峰，入口再用漏桶或令牌桶限流，两层一起防止积压失控。」

---

### 生产最小闭环（总背这 5 句）

1. 锁库存用 **V4 条件 UPDATE**。  
2. 高峰用 **V6 异步受理**，接受最终一致；入口可加 **漏桶/令牌桶限流** 防积压。  
3. **幂等：Redis + DB 唯一索引** 双保险。  
4. **补偿 + 对账** 修半成功。  
5. MQ：**监控积压、死信、Confirm/持久化/手动 Ack**。  

> V5 Redisson 不是锁库存必选项；更常用于必须串行的业务临界区，不能替代 V4。

---

## 八、面试口述（约 40 秒）

「库存下单要考虑并发，因为读库存和锁库存不是原子的，就像厕所只有 100 个坑，大家同时探头看『有空吗』会超占，我们 V1 压测就超锁了。  
V2 用单机锁修好了，但多实例失效而且很慢。  
V3 只是把次要工作异步掉，主瓶颈还在。  
V4 用 SQL 条件更新，空才占得上，正确又更快，是正确性底座。  
V5 用 Redis 做跨 JVM 锁，像多栋楼共用一张通行证。  
V6 用 MQ 异步，接口立刻返回已排队，最终一致，消费者里仍走 V4。  
V7 再补幂等和补偿：同一业务号只占一次，半成功用任务放坑。  
生产还要加死信、积压监控、对账，以及 DB 唯一约束双保险。」
