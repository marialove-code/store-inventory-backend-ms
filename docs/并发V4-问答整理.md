# 库存并发 V4 — 问答整理

> 配合：[`并发演进.md`](./并发演进.md) · [`并发V2V3-问答整理.md`](./并发V2V3-问答整理.md)  
> 代码包：`com.inventory.modules.order.concurrency.v4` · `StockService#lockStockAtomically`  
> 说明：V1 仅作「复现超锁」对比；V2/V3 详见姊妹文档。

---

## 一、V4 定位与设计

**1. V4 要解决什么问题？和 V2/V3 有什么不同？**

| 版本 | 手段 | 问题 |
|------|------|------|
| V2/V3 | `ReentrantLock(goodsId)` | **正确**但不超锁；200 线程在 JVM 里 **串行排队**，平均 RT ~19s |
| **V4** | SQL 条件 UPDATE | **正确**不超锁，且 **去掉 JVM 锁排队**，平均 RT ~14s |

V4 的核心不是「再换一种 Java 锁」，而是把 **判断库存是否够** 和 **增加 lock_stock** 合并成 **一条带 WHERE 的原子 UPDATE**，交给数据库保证。

**2. V4 还用锁吗？**

- **不用** JVM 的 `ReentrantLock` / `synchronized`  
- **仍有** 数据库 **行级锁**：并发 UPDATE 同一行 `inventory_stock` 时，PostgreSQL 会对该行加锁，但持有时间远短于 V2「整段 createOrder 占着 JVM 锁」

**3. V4 为什么比 V2/V3 快？（结合实测）**

本机 JMeter 200 并发复测：

| 指标 | V2 | V3 | V4 |
|------|----|----|-----|
| 平均 RT | 19,293 ms | ~18,850 ms | **14,234 ms** |
| 吞吐 | 6.1/s | ~5.9/s | **10.3/s** |
| 最大 RT | ~32 s | ~33 s | **~19 s** |

原因归纳：

1. **无 JVM 排队**：200 线程不必等前一个在 Java 里跑完整条链路  
2. **库存不足快速失败**：`UPDATE` 影响 0 行即返回，不必排到队尾才发现没货  
3. **临界区变短**：竞争集中在一条原子 SQL + 事务内写单，而非锁内「查+判+单+流水」整包  

**4. V4 和 V3 能叠加吗（SQL 原子 + 异步流水）？**

可以，属于优化组合；当前 V4 实现为 **同步写流水**（与 V2 一致），优先验证「SQL 原子条件」单独带来的收益。若再异步流水，可参考 V3 线程池，但收益可能小于去掉 JVM 锁（V3 已验证仅 ~3%）。

## 二、SQL 原子 UPDATE

**5. V4 的核心 SQL 是什么？**

```sql
UPDATE inventory_stock
SET lock_stock = lock_stock + #{qty},
    update_time = NOW()
WHERE goods_id = #{goodsId}
  AND stock - COALESCE(lock_stock, 0) >= #{qty}
```

- **条件**：仅当 `可用库存 >= 购买量` 才更新  
- **更新**：`lock_stock` 原子 +qty  
- **返回值**：影响行数 `1` = 成功，`0` = 库存不足或商品不存在  

代码位置：`InventoryStockMapper.xml` → `lockStockIfAvailable`。

**6. 为什么 V1 的「先 SELECT 再 UPDATE」会超锁，V4 不会？**

V1 典型竞态：

```text
线程 A：SELECT usable=1 → 判断够
线程 B：SELECT usable=1 → 判断够
线程 A：UPDATE lock_stock+1
线程 B：UPDATE lock_stock+1   → 超锁
```

V4：判断与更新在 **同一条 UPDATE 的 WHERE** 里，数据库保证单行 UPDATE **原子**，第二个线程执行时条件可能已不满足，影响行数 = 0。

**7. 影响行数为 0 时业务怎么处理？**

`StockServiceImpl.lockStockAtomically`：

```java
int affectedRows = inventoryStockMapper.lockStockIfAvailable(goodsId, qty);
if (affectedRows == 0) {
    throw new IllegalStateException("库存不足，当前可用库存：" + usableStock);
}
```

`OrderCreateConcurrencyV4` 捕获后 `Result.fail(message)`，与正式接口「库存不足」语义一致。

**8. `COALESCE(lock_stock, 0)` 是干什么的？**

防止 `lock_stock` 为 NULL 时 `stock - lock_stock` 结果为 NULL，WHERE 不成立导致更新异常。NULL 按 0 处理。

**9. 乐观锁 version 字段和 V4 这种写法有什么区别？**

| 方式 | 思路 | 本项目 |
|------|------|--------|
| **条件 UPDATE（V4）** | `WHERE stock-lock_stock>=qty`，失败即 0 行 | 已实现 |
| **乐观锁** | `UPDATE ... WHERE version=?`，失败重试 | 需加 version 列，V4 文档中作对比方案 |

面试可说：V4 用 **库存约束条件** 做乐观语义，无需额外 version 字段。

**10. `SELECT ... FOR UPDATE`（悲观锁）和 V4 比呢？**

悲观锁：事务内先锁行再读再改，正确但线程在 DB 等待行锁，高并发下仍可能排队。  
V4 条件 UPDATE：一次语句完成，通常更短；本实验选条件 UPDATE 以对比 V2 的 JVM 锁。

## 三、事务与执行顺序

**11. V4 一次下单的完整步骤是什么？**

```text
1. 生成 orderNo
2. lockStockAtomically（原子 UPDATE + 写 inventory_flow）
3. 构建 OrderInfo
4. save(order)
5. 事务提交
```

均在 `OrderCreateConcurrencyV4SyncService.syncCreateOrderWithSqlLock` 的 `@Transactional` 内。

**12. 为什么先锁库存、后插订单，而不是先插订单？**

先原子锁库存，失败则 **不插入订单**，避免「有订单无库存支撑」的脏数据。  
若先插单后锁失败，虽可事务回滚，但会先产生更多无效订单插入尝试；当前顺序 **失败更快、逻辑更清晰**。

**13. 原子锁成功了，但 save(order) 失败会怎样？**

同一事务内，任一步异常 → **整体回滚**，`lock_stock` 增加与流水插入都会撤销，不会出现「锁了库存却没有订单」的提交态。

**14. `lockStockAtomically` 和 V2 的 `lockStock`、V3 的 `lockStockUpdateOnly` 分别是什么关系？**

| 方法 | 更新 lock_stock | 写流水 | 条件 UPDATE |
|------|-----------------|--------|-------------|
| `lockStock`（V2） | 是 | 同步 | 否（先查再改） |
| `lockStockUpdateOnly`（V3） | 是 | 否（异步补） | 否 |
| **`lockStockAtomically`（V4）** | 是 | 同步 | **是** |

**15. 写流水时 before/after 怎么取？**

原子 UPDATE 成功后 **再 SELECT 一次** 该行，用 `afterLockStock` 与 `after - qty` 作为流水前后值，保证与库中一致。

## 四、与 V2 / V3 对比

**16. V2、V3、V4 一张表说清楚**

| | V2 | V3 | V4 |
|---|----|----|-----|
| 防超锁 | ReentrantLock | 同 V2 | SQL WHERE 条件 |
| JVM 锁 | 有 | 有 | **无** |
| 写流水 | 同步 | 异步 | 同步 |
| 200 并发平均 RT（实测） | ~19.3s | ~18.9s | **~14.2s** |
| 多实例 | JVM 锁无效 | 同左 | **SQL 仍有效** |

**17. 「加锁就慢」在 V4 语境下怎么表述才准确？**

准确说法：**V2/V3 的 ReentrantLock 让 200 个请求在应用层串行**，所以慢。  
V4 不是「完全不锁」，而是 **去掉应用层排队**，用 **短临界区的数据库原子更新**；库存不够的线程 **不必等 199 个业务跑完**。

**18. V3 只比 V2 快 3%，V4 为什么快很多？**

V3 只把 **写流水** 挪到异步，**ReentrantLock 仍在**，排队瓶颈未动。  
V4 去掉 **JVM 锁**，改变的是 **并发模型**，不是少一次 IO 那么简单。

**19. V4 还需要 Redis 吗（V5）？**

- **单机 / 单实例**：V4 SQL 原子条件 **已够** 防超锁  
- **多实例**：V4 SQL **仍然有效**（都改同一行）  
- **V5 Redis**：可用于分布式锁、限流、缓存、Lua 原子扣减等 **扩展**；不是 V4 已做对就必须再上，面试可说「多活、跨库、复杂扣减规则时可叠加 Redis」

**20. V4 会出现死锁吗？**

- JVM 死锁（两把 ReentrantLock 互等）：V4 **无应用锁**，不涉及  
- 数据库死锁：多表、多行加锁顺序不一时可能发生；本场景主要 UPDATE **单行** `inventory_stock`，风险低。若扩展为多表更新，需统一加锁顺序。

## 五、压测与验证

**21. V4 压测接口与 Body 注意什么？**

```http
POST /api/order/concurrency/order/add?version=v4
```

Body 中 `remark` 建议 `"JMeter V4"`（仅改 URL 不改 remark 时库里会仍显示 V1）。

**22. 压测后如何确认成功？**

`GET /api/order/concurrency/stock/result` 实测示例：

```json
{
  "stock": 100,
  "lockStock": 100,
  "usableStock": 0,
  "pendingOrderCount": "100",
  "overLocked": false
}
```

**23. V4 需要像 V3 那样压测后等 5～10 秒再查流水吗？**

**不需要。** V4 流水在 `lockStockAtomically` 里 **同步写入**，与 V2 相同。

**24. JUnit 测 V4 跑哪个类？**

`OrderCreateConcurrencyV4Test`：`smoke` + `v4_concurrentCreateOrder_shouldNotOverLock`（200 线程，无额外 sleep）。

**25. V4 的 HTTP 异常 0% 是否代表 200 单全成功？**

不一定。与 V2/V3 一样，200 线程抢 100 库存时，业务上约 **100 成功 + 100 失败**；若 JMeter 只判 HTTP 状态，可能仍显示 0% 异常。以 `stock/result` 和 `overLocked` 为准。

## 七、面试综合

**26. 用 1 分钟讲 V1 → V4**

> V1 无锁复现超锁。V2 ReentrantLock 不超锁但 19 秒平均响应。V3 异步流水几乎没快，说明瓶颈在 JVM 锁。V4 用 `UPDATE WHERE stock-lock_stock>=qty` 原子锁定，去掉应用层排队，200 并发平均 14 秒、吞吐 10.3，overLocked false，且多实例仍靠数据库保证。

**27. 面试官问：「你怎么发现 V3 不够、要上 V4？」**

> 压测对比：V2/V3 RT 都在 19 秒级，V3 只快 3%，说明优化写流水没用，瓶颈在 ReentrantLock 串行。于是把并发安全下沉到 SQL 原子条件，V4 RT 降到 14 秒、吞吐从 6 到 10，验证假设。

**28. 面试官问：「V4 还有什么问题？」**

> ① 热点单行 UPDATE 仍有 DB 竞争；② 未做幂等（重复提交可能多次锁库存，靠 V7）；③ 未接 MQ/最终一致性（V6）；④ 极高 QPS 可能要分库分表、Redis 预扣等（V5）。当前版本验证的是 **正确性 + 相对 V2 的性能**，不是生产终态。

**29. 优先背诵的 5 题**

- **5**：核心 SQL 与影响行数含义  
- **6**：为何 SELECT+UPDATE 超锁、条件 UPDATE 不超锁  
- **17**：「加锁慢」的准确表述  
- **18**：V3 小提升 vs V4 大提升的原因  
- **26**：1 分钟演进口述
