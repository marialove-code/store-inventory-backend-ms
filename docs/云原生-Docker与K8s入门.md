## 1. 云原生在说什么（一句）

**云原生** ≈ 应用按「可复制的运行单元」交付（常见是**容器**），用编排管多副本/发布/自愈，而不是只靠「这台机器上手动丢一个 jar」。

你项目里已经沾边的：本机 Docker 起过 **ES、RabbitMQ**；业务服务仍多是 **java -jar / 脚本上传**。Day1 起补的是：**自己的 Spring Boot 也变成镜像**。

---

## 2. Docker 是什么？干嘛用？

### 是什么

**Docker** 是目前最常用的**容器引擎**之一。

两个核心词：

| 词 | 比喻 | 含义 |
|----|------|------|
| **镜像（Image）** | 只读的安装包 / 模具 | 里面有 JDK、你的 jar、启动命令等 |
| **容器（Container）** | 用模具印出来的一栋运行中的小房子 | 镜像的一次运行实例 |

**Dockerfile** = 怎么做镜像的说明书（装什么、拷什么、启动什么）。

### 干嘛用

- **环境一致**：「我机器能跑、服务器不能跑」变少（JDK 版本、时区、依赖都封进镜像）
- **启动方式统一**：`docker run` / `compose up`，少记一长串 `java -jar ...`
- **隔离**：和宿主机其它进程隔开一点（不是虚拟机那么重）
- **和你已有经验衔接**：`docker run elasticsearch`、`docker run rabbitmq` —— Day1 只是换成 `docker run` 你自己的 order

### 和虚拟机差在哪（面试常问）

| | 虚拟机 | 容器（Docker） |
|--|--------|----------------|
| 隔离 | 整套 Guest OS | 共享宿主机内核，进程级隔离 |
| 体积/启动 | 更重、更慢 | 更轻、更快 |
| 典型用途 | 强隔离、完整 OS | 跑应用进程（正好适合微服务 jar） |

## 3. Kubernetes（K8s）是什么？干嘛用？

### 是什么

**Kubernetes** = **容器编排平台**（编排 = 很多容器怎么部署、扩缩、升级、挂了怎么重启）。

Docker 负责「**一个容器怎么造、怎么在一台机器上跑**」。  
K8s 负责「**很多容器在很多机器上怎么管**」。

常见对象（会背名字即可）：

| 对象 | 干什么 |
|------|--------|
| **Pod** | 最小调度单元（里面常是 1 个业务容器） |
| **Deployment** | 声明「我要几个副本、怎么滚动升级」 |
| **Service** | 给一组 Pod 一个稳定访问入口（DNS / 虚拟 IP） |
| **探针** | 活着没（liveness）、能不能接流量（readiness） |

### 干嘛用

- 多副本、负载均衡、机器挂了自动调度
- 滚动发布（先起新再杀旧）
- 声明式：你写「期望状态」，K8s 去凑齐

### 我们为什么「只口述、不实装」

搭集群成本高；你目标岗位讲清概念 + 挂回 **V5 多副本要分布式锁、V7 滚动/重试要幂等** 就够。本阶段用 **Docker + compose** 演示容器化即可。

## 4. Docker 和 K8s 的区别（对照表）

| 维度 | Docker | Kubernetes |
|------|--------|------------|
| 层级 | 容器运行时 / 造镜像 | 编排平台（通常下面仍跑容器） |
| 管几台机器 | 单机为主（compose 也偏本机/单机） | 集群、多节点 |
| 你怎么用 | Dockerfile、`docker build/run`、compose | YAML 声明 Deployment/Service… |
| 本项目两天 | **要动手** | **会讲即可** |
| 一句话 | 「把 order 打成镜像并跑起来」 | 「很多 order 副本怎么滚动、怎么发现」 |

关系可以记：

```text
写 Dockerfile → docker build 出镜像 → docker run 出容器
                    ↓
         （生产可选）K8s 调度很多这样的容器
```

`docker compose`：本机用 YAML 一次起多个容器，是「轻量编排」；**不是** K8s，但面试可以说「本地用 compose，生产常见 K8s」。
