## 题 1：TCP 与 UDP 及三次握手、四次挥手

================

## 面试问题：

TCP 和 UDP 的区别？TCP 为什么需要三次握手、四次挥手？TIME_WAIT 过多会有什么问题？

## 考察点：

- 可靠传输 vs 尽力交付
- 连接建立/释放的状态机（SYN、ACK、FIN）
- 半连接、全连接队列（适度）
- 能否联系到 Feign/HTTP 底层都是 TCP

## 标准答案：

**TCP vs UDP：**

| | TCP | UDP |
|---|-----|-----|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 确认重传、有序 | 不保证 |
| 开销 | 首部 20B+、慢 | 首部 8B、快 |
| 场景 | HTTP、RPC、DB 连接 | DNS、直播、心跳 |

**三次握手（建立连接）**：

1. Client → SYN（seq=x）
2. Server → SYN+ACK（seq=y, ack=x+1）
3. Client → ACK（ack=y+1）

**目的**：双方确认 **收发能力** 与 **初始序列号**；防止 **已失效的连接请求** 突然到达服务器（历史 SYN 浪费资源）。  
两次不够：服务端无法确认客户端收到了自己的 SYN-ACK。

**四次挥手（释放连接）**：

1. Client → FIN
2. Server → ACK（半关闭：客户端→服务端方向关闭）
3. Server → FIN（数据发完后）
4. Client → ACK，进入 **TIME_WAIT**（2MSL 后关闭）

**TIME_WAIT 过多**：占用 **端口与连接表**；高并发短连接客户端常见。解决：**连接池/Keep-Alive**、调 `tcp_tw_reuse`（Linux，需理解风险）、减少不必要的短连接。

## 通俗理解：

TCP 像 **打电话**：先拨号确认对方在听（握手），说完双方挂电话还要互相确认「我说完了」（挥手）。  
UDP 像 **大厅广播**：喊一嗓子，不保证对方听到。

## 项目结合：

- **OpenFeign / RestTemplate** 调 inventory-service，底层 **HTTP over TCP**；每次新建连接 = 多一次握手开销 → 生产用 **HTTP Keep-Alive + 连接池**。
- **PostgreSQL JDBC** 长连接池（HikariCP）复用 TCP，避免每 SQL 三次握手。
- **Gateway** 作为客户端连下游、作为服务端收前端，**两端** 都要关注连接复用与超时。
- 压测 order 接口若 **TIME_WAIT 暴涨**，查是否 Feign 未开连接池或 `connection: close`。

## 面试官追问：

1. SYN 洪水是什么？SYN Cookie 了解吗？
2. 为什么挥手是四次不是三次？
3. HTTPS 握手和 TCP 握手什么关系？

## 高级回答：

- **SYN 洪水**：伪造 SYN 占满半连接队列；SYN Cookie 不立即分配资源，把信息编码在 seq 里。
- **四次**：TCP **全双工**，双方各发 FIN+ACK，不能合并成一次。
- **HTTPS**：TCP 三次握手 → **TLS 握手**（证书、密钥协商）→ HTTP。TLS 1.3 减少往返。
- 10 年答法：结合 **「Feign 超时 + 连接池 max-connections」** 说明理解 TCP 成本，不是背 RFC。

## 题 2：HTTP 协议与 REST 实践

================

## 面试问题：

HTTP 常见方法及语义？什么是幂等？GET 和 POST 区别？RESTful 设计你在项目里怎么落地的？

## 考察点：

- 方法语义、状态码
- 幂等与业务（下单、支付）
- 实际 API 设计而非教条 REST

## 标准答案：

**常见方法：**

| 方法 | 语义 | 幂等 | 安全 |
|------|------|------|------|
| GET | 查询 | 是 | 是 |
| POST | 创建/非幂等操作 | 否 | 否 |
| PUT | 全量替换 | 是 | 否 |
| PATCH | 部分更新 | 视实现 | 否 |
| DELETE | 删除 | 是 | 否 |

**幂等**：同一请求执行多次，**资源状态与一次成功执行相同**（HTTP 层 vs 业务层要区分）。

**GET vs POST**：

- GET 参数在 URL，有长度限制，**可缓存**，不应改状态
- POST 通常在 body，**不缓存**，适合创建

**RESTful 实践（ pragmatic ）**：

- 资源名复数：`/api/goods`、`/api/orders/{id}`
- 状态码：`200` 成功、`201` 创建、`400` 参数错、`401` 未登录、`403` 无权限、`404` 不存在、`409` 冲突（库存不足）、`429` 限流、`500` 服务器错
- 统一响应体 `Result<T>` + 业务 code

## 通俗理解：

HTTP 方法像 **仓库操作类型**：GET 只看货单，POST 是新入库单，PUT 是整单替换，DELETE 是删货。  
幂等像 **按同一个订单号提交两次，库里还是一笔货，不会双份**。

## 项目结合：

- **商品 CRUD**：`GET /api/goods/page`、`POST /api/goods`、`PUT /api/goods/{id}`、`DELETE /api/goods/{id}`
- **下单 POST /api/orders**：HTTP 层 **不幂等**，业务用 **clientRequestId / 订单号唯一索引** 做幂等（并发批会深挖）
- **AI 接口** `POST /api/ai/chat`：非幂等、不宜 GET（URL 泄露 prompt）
- **Gateway** 路由：`/api/order/**` → order-service，路径与动词一致便于 Sentinel 按资源限流

## 面试官追问：

1. PUT 和 PATCH 在你们项目里用哪个？
2. 为什么文件上传常用 POST multipart？
3. 204 和 200 空 body 区别？

## 高级回答：

- 进销存 **部分更新商品** 用 PATCH 或 POST `/goods/{id}/partial` 均可，团队统一即可；很多项目 **PUT 带非空字段** 当 partial。
- **multipart**：POST body 二进制，RFC 语义就是 POST；大文件用 **分片 + 断点** 另议。
- **204 No Content**：成功且无 body；删除成功常用 204 或 200+Result。
- 面试强调：**REST 是风格，不是 religion**；对外 B 端 API 文档清晰 > 动词洁癖。

## 题 3：HTTPS 与 TLS 握手

================

## 面试问题：

HTTP 和 HTTPS 区别？TLS 握手大致做什么？证书链如何验证？Spring Boot 如何配置 HTTPS？

## 考察点：

- 加密、完整性、身份认证
- 对称加密 vs 非对称加密分工
- 生产证书、Let's Encrypt、Nginx 终结 SSL

## 标准答案：

**HTTPS = HTTP + TLS（SSL 继任者）**

| 能力 | 说明 |
|------|------|
| 机密性 | 对称加密（AES）加密 body |
| 完整性 | MAC / AEAD 防篡改 |
| 身份 | 服务器证书（CA 签名），防中间人 |

**TLS 握手（简化）**：

1. ClientHello（支持的 cipher、随机数）
2. ServerHello + **证书**
3. 客户端验证证书链（CA → 中间 CA → 站点证书）
4. 密钥交换（ECDHE 等），生成 **会话密钥**
5. 后续 HTTP 用对称密钥加密

**Spring Boot HTTPS**：

- `server.ssl.key-store=classpath:keystore.p12` + 密码
- 或 **Nginx 终结 TLS**，后端 HTTP（内网），生产常见

## 通俗理解：

HTTP 像 **明信片**，路上谁都能看；HTTPS 像 **密封信+公证处盖章**，证明是 nestparts.top 官方发的，内容别人打不开。

## 项目结合：

- **nestparts.top**：Nginx 443 配 Let's Encrypt，反代 Gateway 8080；证书在 Nginx，Java 服务不直接暴露公网。
- **JWT** 在 Authorization Header 里传，HTTPS 防 token 被嗅探；**不要**把 JWT 放 URL。
- **Feign 内网 HTTP**：同机 Docker host 网络，信任边界在 **防火墙 + 不对外端口**；上 K8s 后可 **mTLS**（Service Mesh 进阶）。
- **DashScope AI API**：必须 HTTPS 调外部，API Key 走 header，不进日志。

## 面试官追问：

1. 什么是 HSTS？
2. TLS 1.2 和 1.3 区别？
3. 自签名证书能用于生产吗？

## 高级回答：

- **HSTS**：强制浏览器只用 HTTPS，防 SSL Strip。
- **TLS 1.3**：更少往返、更安全 cipher 默认、0-RTT（有重放风险要评估）。
- **自签名**：仅内网/dev；公网必须 CA 证书。
- 10 年答法：**「公网 Nginx 终结 SSL，后端内网；密钥不进 Git，宝塔/Let's Encrypt 自动续期」**。

## 题 4：DNS 解析与负载均衡

================

## 面试问题：

浏览器输入 URL 到收到响应，经过哪些步骤？DNS 解析过程？L4 和 L7 负载均衡区别？

## 考察点：

- 全链路：DNS → TCP → TLS → HTTP
- DNS 缓存层级
- Nginx / Gateway / 云 LB 分工

## 标准答案：

**全链路（HTTPS 站点）**：

1. **DNS** 解析域名 → IP（本地缓存 → 递归 DNS → 权威 DNS）
2. **TCP** 连接 443
3. **TLS** 握手
4. **HTTP** 请求 → Nginx → Gateway → 微服务
5. 响应原路返回

**DNS 记录**：A/AAAA（IP）、CNAME（别名）、TTL（缓存时间）

**负载均衡：**

| 类型 | 层级 | 依据 | 例子 |
|------|------|------|------|
| L4 | 传输层 | IP+端口 | SLB 四层、IP Hash |
| L7 | 应用层 | URL、Header、Cookie | Nginx、Gateway、ALB 七层 |

**L7 优势**：按 **路径** 路由（`/api/order` → order）、**灰度**、**限流**；L4 性能更高但不懂 HTTP。

## 通俗理解：

DNS 像 **查电话簿**：nestparts.top 对应哪个 IP。  
L4 像 **快递按地址分拣到小区**；L7 像 **按包裹上写的「订单组/库存组」分到不同部门**。

## 项目结合：

- **域名 nestparts.top** → 腾讯云 DNS A 记录 → 轻量服务器 IP → Nginx → Gateway → Nacos 发现实例。
- **Gateway** 做 **L7 路由 + JWT 校验**；若多实例 order-service，Ribbon/LoadBalancer **轮询** Feign 下游。
- **Nacos** 是 **服务发现**，不是 DNS 替代；客户端拿 **实例列表** 再负载均衡。
- 改 DNS TTL 过长：**切 IP 慢**；过短：DNS 查询多。

## 面试官追问：

1. 什么是 DNS 污染/劫持？
2. 客户端负载均衡和服务端负载均衡区别？
3. 粘性会话怎么做？JWT 还需要吗？

## 高级回答：

- **客户端 LB**：Feign + LoadBalancer 从 Nacos 拉实例自己选；**服务端 LB**：Nginx upstream。
- **粘性会话**：Cookie ip_hash 或 session sticky；**JWT 无状态** 后 **不需要** 粘性，任意 Gateway 实例可验签。
- 进销存：**Session 在 JWT**，水平扩 Gateway 无状态；WebSocket 客服若上 sticky 再议。

## 题 5：超时、重试与 Feign 配置

================

## 面试问题：

微服务调用为什么要设连接超时和读超时？重试有什么风险？Feign 超时和 Sentinel 熔断如何配合？

## 考察点：

- connect timeout vs read timeout
- 重试与幂等、雪崩
- 真实配置意识

## 标准答案：

**两类超时：**

| 类型 | 含义 | 典型值（参考） |
|------|------|----------------|
| **Connect** | 建立 TCP 连接最长时间 | 2～5s |
| **Read** | 等待响应 body 最长时间 | 5～30s（视接口） |

**不设超时的后果**：下游 hang 住 → 线程池打满 → **级联故障**（整个 order-service 不可用）。

**重试风险**：

- 对 **非幂等** POST 下单重试 → **重复订单**
- 下游已处理但响应丢失 → 客户端以为失败再试 → **双写**
- 重试风暴 → 下游更挂

**实践**：

- **GET/幂等** 可有限重试（1～2 次，指数退避）
- **POST 下单** 用 **幂等键** 再谈重试
- **Sentinel**：慢调用比例、异常比例熔断；与超时配合 **fail fast**
- **Feign**：`connectTimeout`、`readTimeout`；Spring Cloud OpenFeign 可配 `Retryer`（慎用）

## 通俗理解：

超时像 **等外卖**：联系不上商家（connect 超时）和商家做了 2 小时还没送到（read 超时）是两种问题。  
盲目重试像 **同一份外卖点了三遍**，商家真送三遍。

## 项目结合：

```yaml
# order 调 inventory 示例思路
feign:
  client:
    config:
      inventory-service:
        connectTimeout: 3000
        readTimeout: 5000
```

- **库存扣减**：read 不宜过长；失败 **不要自动重试**，返回「请稍后查询订单状态」+ **幂等查询接口**
- **AI 调 DashScope**：read 30～60s，**单独线程池/舱壁**，不与下单共用
- **Sentinel** 对 `POST /api/orders` 限 QPS，超时过多触发熔断，快速返回 503
- **Gateway** 全局 timeout 应 **大于** 最慢合法链路，但 **小于** 前端 nginx proxy_read_timeout

## 面试官追问：

1. 什么是舱壁隔离（Bulkhead）？
2. Hystrix 和 Sentinel 超时谁生效？
3. 如何排查「接口偶尔 30 秒才返回」？

## 高级回答：

- **舱壁**：下单线程池、AI 线程池分离，AI 慢不拖死下单。
- **Sentinel 生效** 在资源入口；Feign 超时先抛 `SocketTimeoutException`，再可能触发熔断统计。
- **排查**：Arthas trace、SkyWalking span、看是 **DB 慢 / Feign 慢 / GC STW**。
- 10 年答法：**「超时是契约的一部分，文档写清；非幂等默认不重试，靠业务幂等键兜底」**。

## 题 6：HTTP 长连接与连接池

================

## 面试问题：

HTTP Keep-Alive 是什么？短连接和长连接对性能有什么影响？Java 里 HTTP 客户端连接池要注意什么？

## 考察点：

- Connection: keep-alive
- 连接池 max total、per route
- HttpClient vs OkHttp vs Feign 底层

## 标准答案：

**HTTP/1.1 默认 Keep-Alive**：同一 TCP 连接上 **连续发多个 HTTP 请求**，减少握手与慢启动。

**短连接问题**：高 QPS 下 **TIME_WAIT 堆积**、CPU 与延迟上升。

**连接池参数（Apache HttpClient / OkHttp 概念）**：

- `maxTotal`：全局最大连接
- `maxPerRoute`：到同一 host 最大连接
- `validateAfterInactivity`：空闲连接是否有效
- **空闲超时** 关闭，避免拿死连接

**注意**：

- 服务端也要 Keep-Alive；Nginx `keepalive_timeout`
- **HTTP/2** 多路复用，单连接并行多个 stream（OkHttp、现代浏览器支持）
- Feign + HttpClient 需 **显式引入** httpclient 依赖才池化，否则可能 JDK HttpURLConnection 行为不同

## 通俗理解：

Keep-Alive 像 **打电话不挂，连续报多个订单号**，不用每个号都重新拨号。

## 项目结合：

- **order → inventory** 高频 Feign：开连接池，`maxPerRoute` 与 Tomcat 线程数 **匹配**，避免「线程 200、连接 20」排队。
- **Gateway → 下游** Spring Cloud Gateway 基于 Netty，**异步非阻塞**，连接模型与 Tomcat 阻塞不同，但下游仍是 HTTP 客户端池。
- **Redis Lettuce**：也是长连接 + 连接池，别和 HTTP 混为一谈但 **思想相同**。
- 压测时若 **connect timed out** 而 CPU 不高，先查 **连接池耗尽** 而非堆内存。

## 面试官追问：

1. HTTP/2 和 HTTP/1.1 Keep-Alive 区别？
2. 连接池泄漏怎么发现？
3. 为什么有些响应头 Connection: close？

## 高级回答：

- **HTTP/2**：二进制分帧、头部压缩 HPACK、单连接多路复用，队头阻塞缓解。
- **泄漏**：池里 borrowed 连接长期不归还，线程 dump 看 hang 在 io；Micrometer 若有 httpclient 指标更好。
- **Connection: close**：服务端主动关，或 HTTP/1.0；负载均衡 **摘节点** 前 drain 连接。
- 进销存：**内外 HTTP 都默认 Keep-Alive**，除非 debug 抓包要 close。

## 题 7：TCP 粘包/拆包与 Netty（Gateway 视角）

================

## 面试问题：

什么是 TCP 粘包和拆包？NIO 和 BIO 区别？Spring Cloud Gateway 为什么用 Netty？

## 考察点：

- TCP 字节流 vs 消息边界
- 阻塞 IO vs 多路复用
- 网关高并发模型（不必写 Netty 源码）

## 标准答案：

**粘包/拆包**：TCP 是 **字节流**，没有「一条消息」边界；应用层需 **定长、分隔符、或长度头** 组帧。HTTP 靠 **Content-Length / Chunked** 定界。

**BIO**：一连接一线程，阻塞 read；线程数受限，C10K 问题。

**NIO（Java NIO）**：**Selector** 多路复用，少量线程管多连接；Netty 封装 NIO + 零拷贝等优化。

**Gateway 用 Netty**：

- **高并发、IO 密集**（转发、鉴权、限流）
- **非阻塞** 等下游时不占线程（Reactor 模型）
- 与 Tomcat **Servlet 阻塞** 模型互补：Gateway Netty，业务服务 Tomcat/WebMvc 常见

**Reactor 模型（简化）**：

- Boss 接受连接，Worker 处理 IO
- 业务逻辑应 **非阻塞**；阻塞调用（JDBC）在 Gateway 过滤器里要 **谨慎**（或用 WebFlux 全链路 reactive，Gateway 侧一般轻量）

## 通俗理解：

粘包像 **多封信粘在一个信封里** 一次送来；拆包像 **一封信分两个包裹** 寄到。HTTP 在信封上写了「这封信多长」。  
BIO 像 **每个客户配一个专属客服**；NIO 像 **一个客服轮询看多路电话**。

## 项目结合：

- **Gateway 路由 JWT 校验**：过滤器里只做 **解析 token、Redis 查黑名单（宜快）**，不要 Feign 调重业务。
- **Feign 是阻塞 HTTP 客户端**（默认），order-service 调 inventory 占 **Tomcat 线程**；高并发靠 **线程池 + 连接池 + Sentinel**，不是 Netty。
- 若面试问 **WebFlux 进销存**：可以说 **业务仍以 MVC 为主**，Gateway 异步转发足够；全面 Reactive 改造成本高、收益看场景。
- **WebSocket 客服**（若扩展）：长连接，Netty/Gateway 对 WS 有专门支持。

## 面试官追问：

1. Epoll 和 Select 区别？
2. Netty 的 EventLoop 线程能跑阻塞代码吗？
3. HTTP 为什么基于 TCP 而不是 UDP？

## 高级回答：

- **Epoll**：Linux 高效 IO 多路复用，O(1) 就绪事件；Select 有 fd 上限与线性扫描。
- **EventLoop 忌阻塞**：阻塞 JDBC 会卡整个 loop；应丢业务线程池或换 reactive driver。
- **HTTP 要可靠有序**：TCP 合适；QUIC/HTTP3 基于 UDP 但自带可靠层，是演进方向。
- 10 年答法：**「我服务是 Tomcat 阻塞模型，网关 Netty；调优连接池和线程，不强行 WebFlux 全栈」**。

## 题 8：Nginx 反向代理与全链路排查

================

## 面试问题：

Nginx 反向代理做了什么？常见配置项有哪些？用户说「网站打不开 / 接口 502」，你如何分层排查？

## 考察点：

- 反向代理 vs 正向代理
- proxy_pass、upstream、超时、header 转发
- 与宝塔、Docker、Gateway 联调经验

## 标准答案：

**反向代理**：客户端只认识 Nginx，Nginx 代你访问 **内网 Gateway/后端**，隐藏真实端口与拓扑。

**常见配置**：

```nginx
upstream gateway {
    server 127.0.0.1:8080;
    keepalive 32;
}
server {
    listen 443 ssl;
    server_name nestparts.top;
    location /api/ {
        proxy_pass http://gateway;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
    }
}
```

**502 Bad Gateway**：Nginx 作为网关 **连不上/upstream 无效响应**（后端 down、超时、崩溃）。  
**504 Gateway Timeout**：**read timeout** 内后端没返回。  
**401/403**：多为 **应用层** JWT/权限，Nginx 已转发成功。

**分层排查**：

1. **DNS**：ping / nslookup 域名
2. **Nginx**：`nginx -t`、error.log、502 时看 upstream 是否通
3. **Gateway**：端口、路由、JWT 过滤器
4. **Nacos**：实例是否 healthy
5. **业务服务**：日志、Feign 下游、DB
6. **容器**：`docker ps`、OOMKilled、host 网络

## 通俗理解：

Nginx 像 **公司前台**：访客只找前台，前台转接订单部/库存部（Gateway → 微服务）。502 是前台 **转接时对方电话没人接**。

## 项目结合：

- **nestparts.top + 宝塔**：443 Nginx → Gateway → order/inventory；静态前端 `location /` 走 dist。
- **X-Forwarded-For**：Gateway 取真实 IP 做 **操作日志 / 限流**；Trust 只信 Nginx 一跳，防伪造。
- **CD 部署后 502**：先 `curl localhost:8080/actuator/health`（若开）再查 Nginx upstream 端口是否改错。
- **Gitee Go 探活**：脚本 ping order 接口，与 Nginx 层探活 **互补**。

## 面试官追问：

1. 正向代理和反向代理区别？
2. 如何做 WebSocket 反向代理？
3. 为什么需要 X-Forwarded-Proto？

## 高级回答：

- **正向代理**：帮 **客户端** 访问外网（VPN）；**反向代理**：帮 **服务端** 接流量。
- **WebSocket**：`proxy_http_version 1.1`、`Upgrade`、`Connection "upgrade"`。
- **X-Forwarded-Proto**：后端知道原始是 https，生成链接/Secure Cookie 正确。
- 10 年答法：**「我从外到内 curl 分层缩小范围；502 先看 upstream 活没活，再看 JVM；个人项目在宝塔+Nginx+Docker 上完整走过」**。
