## 题 1：竞态条件与超卖（V1 基线）

================

## 面试问题：

什么是线程安全？什么是竞态条件？为什么「先查库存再下单」会超卖？请用生活例子说明。

## 考察点：

- 读-改-写非原子
- 临界区概念
- 能对应项目 V1 压测数据（200 并发锁到 109）

## 标准答案：

**线程安全**：多线程并发访问共享数据时，程序行为仍 **正确**（不超卖、不丢单、不乱序）。

**竞态条件（Race Condition）**：多个线程的执行结果依赖 **交错时序**；「先看空位再占坑」中间可被插队，结果错误。

**超卖根因**：`getUsableStock()` 与 `lockStock()` **不是原子操作**，多个线程都读到「还有 1 个空坑」，都建单并锁库存，最终 **占坑数 > 100**。

## 公共厕所生活类比：

厕所只有 **100 个坑位**。200 人同时冲进来：

1. 十个人 **同时探头**：「还有空吗？」——都看到「还剩 1 个！」
2. 十个人 **都去登记处拿号**
3. 十个人 **都登记成功**，实际坑位只有 1 个

这就是 **登记数 > 真实空位** = 超锁 / 超卖。

## Java 代码解释（项目 V1）：

文件：`OrderCreateConcurrencyV1SyncService#syncCreateOrderNonAtomic`

```java
// 步骤 1：读快照（某一瞬间还有几个空坑）
int usableStock = inventoryStockClient.getUsableStock(dto.getGoodsId());
if (usableStock < dto.getBuyQty()) {
    throw new IllegalStateException("库存不足");
}
// 步骤 2：先登记（建订单）
orderInfoService.save(order);
// 步骤 3：非原子占坑（没有「够才占」条件）
inventoryStockClient.lockNonAtomic(dto.getGoodsId(), dto.getBuyQty());
```

```text
线程 A：读到可用=1 ──┐
线程 B：读到可用=1 ──┤ 都以为还有空
线程 A：建单 + lock+1
线程 B：建单 + lock+1  → 超锁到 109（库存 100，200 并发压测）
```

## 出现的问题：

- **超锁**：`lock_stock` 超过物理库存
- **订单与库存不一致**：有单无坑、有坑无单
- **压测入口**：`POST /api/order/concurrency/order/add?version=v1`

## 解决方案：

| 层次 | 做法 | 对应版本 |
|------|------|----------|
| 应用串行 | 门口只进一人办完 | V2 JVM 锁 |
| 数据库原子 | 电子门锁：够才开 | **V4 条件 UPDATE** |
| 跨实例协调 | 中央通行证 Redis | V5 |
| 削峰 | 先给小票后台占坑 | V6 MQ |
| 防重复 | 同一业务号只占一次 | V7 幂等 |

## 项目中的库存场景：

进销存 **order-service** 专门保留 V1 作为 **故意翻车对照组**；面试口述：**「我压测复现过 200 并发锁 109，证明竞态真实存在，再讲 V4 原子 SQL 修复」**。

## 面试官追问：

1. 加 `synchronized` 在 Controller 上能解决吗？
2. 数据库隔离级别调高能解决吗？
3. 为什么生产绝不能用 V1？

## 高级回答：

- **Controller synchronized**：只锁单 JVM 的一个入口，Service 多层调用、多实例仍失效。
- **RR 快照读**：普通 SELECT 不加锁，两个事务仍可同时读到「有库存」。
- 10 年答法：**「超卖本质是 check-then-act 非原子；要么锁临界区，要么 SQL 一条 UPDATE where qty>=，我项目 V4 是生产底座」**。

## 题 2：synchronized 与 ReentrantLock（V2）

================

## 面试问题：

`synchronized` 和 `ReentrantLock` 区别？为什么 V2 用 ReentrantLock 按 goodsId 分段锁？多实例为什么仍不够？

## 考察点：

- 互斥、可重入、公平锁
- 单机 vs 分布式
- 性能代价（串行 RT ~20s）

## 标准答案：

| | synchronized | ReentrantLock |
|---|--------------|---------------|
| 释放 | 自动 | 必须 finally unlock |
| 尝试/超时 | 不支持 | tryLock / lockInterruptibly |
| 公平 | 非公平 | 可选公平 |
| 条件队列 | wait/notify | Condition |

**V2 按 goodsId 锁**：不同商品（不同厕区）不互斥；同一热门 SKU 仍串行。

## 公共厕所生活类比：

**V2** = 这栋楼 **热门厕区门口竖牌**：「同一时刻 **只进 1 人** 完成看空位→拿号→占坑」。  
这一栋楼 **不会超占**（压测 100/100）。  
但 **三栋楼各管各的牌子**（三个 order 实例），共用一个 **100 坑的中央厕区** → 仍可能超占 → 需要 V5 中央通行证或 **V4 数据库门锁**。

## Java 代码解释（项目 V2）：

```java
// 本 JVM 内：ConcurrentHashMap<goodsId, ReentrantLock>
ReentrantLock lock = lockForGoods(dto.getGoodsId());
lock.lock();
try {
    // 临界区：仍调用 V1 非原子链路，但串行后不会交错
    String orderNo = v1SyncService.syncCreateOrderNonAtomic(dto);
    return Result.success("V2…" + orderNo);
} finally {
    lock.unlock();  // 必须释放，否则后面的人永远进不了厕所
}
```

## 出现的问题：

1. **多实例失效**：每 JVM 一把锁，互不可见
2. **性能差**：热门商品 RT ~20s，吞吐低
3. **锁粒度**：锁整个 V1 流程，临界区偏大

## 解决方案：

- **多实例**：Redis 分布式锁（V5）或 **直接 V4 SQL 原子**（更优）
- **性能**：缩短临界区 + V4 条件 UPDATE，不必长时间占 JVM 锁
- **死锁预防**：按 goodsId **排序** 拿多把锁；tryLock 超时返回「系统繁忙」

## 项目中的库存场景：

V2 是 **教学中间态**：证明「互斥能修正确性，但慢且不能跨机」。压测对比 V1→V2→V4 RT，是面试 **最有说服力** 的数据故事（见 `并发/01-压测数据.md`）。

## 面试官追问：

1. synchronized 锁的是对象还是代码？
2. 什么是可重入？同一线程两次 lock 会怎样？
3. StampedLock 了解吗？

## 高级回答：

- **synchronized**：monitorenter 关联 **对象头 Mark Word**；静态方法锁 Class 对象。
- **可重入**：同线程可再次获得锁，计数 +1；ReentrantLock 同理。
- **StampedLock**：读写锁优化读多写少；库存扣减 **写多**，不适合乐观读。
- 10 年答法：**「JVM 锁我用来理解临界区；生产锁库存靠 SQL 原子，Redis 锁做别的串行业务」**。

## 题 3：volatile 与可见性（厕所状态板）

================

## 面试问题：

`volatile` 能保证线程安全吗？它解决什么问题？与 `synchronized` 有什么不同？

## 考察点：

- 可见性、有序性（禁止指令重排）
- 不保证复合操作原子性
- happens-before 入门

## 标准答案：

**volatile**：

- 保证 **可见性**：一线程修改，其他线程 **立即可见**（内存屏障，不走 CPU 缓存脏读）
- 保证 **禁止特定重排**
- **不保证** `i++` 等读-改-写 **原子性**

**synchronized**：互斥 + 可见性（释放锁 flush，获锁 refresh）。

## 公共厕所生活类比：

厕所门口 **电子显示屏** 写「剩余空位：3」：

- **volatile** = 显示屏 **实时联网更新**，任何楼的人抬头看到的数字一致（可见性）
- 但如果两个人 **同时看到 3，各自减 1 写回**，没有互斥，仍可能写错成 2 或 1（**非原子**）
- **synchronized** = 更新显示屏时 **只允许一个人进管理室改数**

## Java 代码解释：

```java
// ❌ 错误：以为 volatile 能防超卖
private volatile int emptySlots = 100;

public void occupy() {
    if (emptySlots > 0) {      // 读
        emptySlots = emptySlots - 1;  // 改-写，非原子！
    }
}

// ✅ 复合操作用原子类或锁
private final AtomicInteger emptySlots = new AtomicInteger(100);

public boolean occupy() {
    int prev = emptySlots.decrementAndGet();  // CAS 原子减
    if (prev < 0) {
        emptySlots.incrementAndGet();  // 回滚
        return false;
    }
    return true;
}
```

## 出现的问题：

- 误用 volatile 做计数 → **仍超占**
- **DCL 单例** 需 volatile 防半初始化对象（经典考点）

## 解决方案：

- 仅 **状态标志** 用 volatile：`volatile boolean shutdown`
- 计数、库存用 **AtomicInteger / LongAdder** 或 **锁 / SQL**
- 进销存 **boolean 降级开关**「AI 服务是否可用」可用 volatile

## 项目中的库存场景：

库存数字 **权威在 DB**（V4 UPDATE），不在 JVM volatile 变量。Redis 预扣可用 **Lua 原子** 或 **INCR**，也不是 volatile。面试：**「volatile 管可见性不管抢坑原子性；抢坑靠 DB/Redis 原子操作」**。

## 面试官追问：

1. happens-before 规则说几条？
2. LongAdder 和 AtomicLong 区别？
3. 双重检查锁为什么要 volatile？

## 高级回答：

- **happens-before**：程序次序、monitor 规则、volatile 写先于读、线程 start/join 等。
- **LongAdder**：高并发累加 **分段**，比 AtomicLong 争用少；统计 **排队人数** 可用，扣库存仍用 DB。
- **DCL**：`instance = new Singleton()` 可能重排，其他线程看到 **未初始化完** 的对象；volatile 禁止。
- 10 年答法：**「volatile 我用来理解 JMM；业务库存不赌内存变量，赌数据库行锁」**。

## 题 4：线程池与异步旁路（V3）

================

## 面试问题：

线程池核心参数有哪些？拒绝策略怎么选？V3 为什么只提升 2～3% RT？

## 考察点：

- core/max/queue/RejectedExecutionHandler
- 主路径瓶颈 vs 旁路优化
- 线程池隔离（AI vs 下单）

## 标准答案：

**ThreadPoolExecutor 参数**：

| 参数 | 含义 |
|------|------|
| corePoolSize | 核心线程数 |
| maximumPoolSize | 最大线程 |
| keepAliveTime | 非核心空闲存活 |
| workQueue | 任务队列（ArrayBlockingQueue / LinkedBlockingQueue） |
| handler | 拒绝策略 |

**拒绝策略**：Abort（抛异常）、CallerRuns（调用者跑）、Discard、DiscardOldest。

**V3 提升小**：瓶颈在 **goodsId 锁 + 同步占坑**（门口排队），异步写流水像 **后勤慢抄账**，不缩短排队时间。

## 公共厕所生活类比：

门口 **占坑** 仍要 **一次一人**（V2 锁还在）。  
「把使用记录抄进账本、通知保洁」交给 **后勤线程池** 慢慢写——你拿到「占坑成功」稍快一点点，但 **门口队伍长度几乎不变**。  
200 人抢 100 坑，**决定快慢的是占坑规则**，不是抄账快 50ms。

## Java 代码解释（项目 V3）：

```java
lock.lock();
try {
    // 主路径（同步）：校验 + 建单 + 锁库存 —— 仍堵在门口
    V3SyncCreateResult syncResult = syncService.syncCreateOrderAndLockStock(dto);
    // 旁路（异步）：写流水、模拟通知 —— 线程池执行，不阻塞 HTTP 返回
    orderConcurrencyExecutor.execute(() -> {
        writeOrderFlow(syncResult);
        notifyMock(syncResult);
    });
    return Result.success("V3：流水异步写入中");
} finally {
    lock.unlock();
}
```

```java
// 线程池配置示例（生产要命名、监控）
@Bean("orderConcurrencyExecutor")
public ThreadPoolTaskExecutor orderConcurrencyExecutor() {
    ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(4);
    ex.setMaxPoolSize(16);
    ex.setQueueCapacity(500);
    ex.setThreadNamePrefix("order-side-");
    ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    ex.initialize();
    return ex;
}
```

## 出现的问题：

- 线程池 **无界队列** → OOM（排队的人无限堆积）
- 旁路任务 **丢异常** 无人知 → 流水缺失
- 异步任务 **拿不到事务** → 流水与订单可能不一致，要 **afterCommit** 或独立事务

## 解决方案：

- **有界队列** + 合理拒绝策略；下单池与 **AI 池隔离**
- `AsyncUncaughtExceptionHandler` 打日志 + 告警
- 旁路写 **操作日志** 用 `@TransactionalEventListener(AFTER_COMMIT)`

## 项目中的库存场景：

V3 说明 **「先找对瓶颈」**：真正提速靠 **V4 SQL** 和 **V6 MQ**，不是多开几个后勤线程。AI 调用放 **独立线程池**，避免占满 Tomcat 线程导致 **厕所门口接待员不够**（HTTP 线程耗尽）。

## 面试官追问：

1. Tomcat 线程和线程池关系？
2. ForkJoinPool 和业务线程池能混用吗？
3. 如何优雅 shutdown 线程池？

## 高级回答：

- **Tomcat maxThreads**：处理 HTTP；业务线程池做 **异步；总线程数 < CPU×合理倍数**，防 context switch 爆炸。
- **ForkJoinPool.commonPool()**：parallelStream 默认；与下单业务 **隔离**。
- **shutdown + awaitTermination + shutdownNow**；Spring `@PreDestroy` 里 graceful。
- 10 年答法：**「线程池我按业务分池、有界队列；V3 教会我异步旁路解决不了锁瓶颈」**。

## 题 5：SQL 原子占坑（V4 生产底座）

================

## 面试问题：

为什么「一条 UPDATE 带条件」能防止超卖？与乐观锁、悲观锁怎么选？V4 还有什么局限？

## 考察点：

- 当前读 + 行锁
- affectedRows 判断
- 与 Redis 锁分工

## 标准答案：

**原子 UPDATE**：

```sql
UPDATE inventory_stock
SET lock_stock = lock_stock + #{qty},
    update_time = NOW()
WHERE goods_id = #{goodsId}
  AND stock - COALESCE(lock_stock, 0) >= #{qty};
```

- **判断 + 占用** 在 DB **一行锁** 内完成，中间无「先读再写」缝隙
- `affectedRows = 0` → 没空位，业务抛「库存不足」

**乐观锁**：`version` 字段 CAS 式更新，冲突重试。  
**悲观锁**：`SELECT ... FOR UPDATE` 再 UPDATE，RT 更长。  
**条件 UPDATE**：库存扣减 **最常用**，简洁且稳。

**V4 局限**：

1. **不防重复提交**（同一人连点两次占两坑）→ V7
2. **同步阻塞 HTTP** → V6 削峰
3. 跨服务：order 调 inventory Feign，**各自本地事务**

## 公共厕所生活类比：

**V4 = 电子门锁规则**：  
刷卡时系统 **当场判断**「是否还有空位」——有则 **门开且计数 -1**，没有则 **门不开**。  
200 人同时刷 **同一套中央系统**（数据库），不会出现 101 人占 100 坑。  
不再依赖「先口头问阿姨还有没有空」（SELECT 快照）。

## Java 代码解释（项目 V4）：

订单侧：先锁库存，再落单

```java
String orderNo = OrderNoGenerator.generate(OrderPrefix.ORDER);
// Feign 调 inventory：内部走 lockStockIfAvailable
inventoryStockClient.lock(dto.getGoodsId(), dto.getBuyQty(), orderNo);
orderInfoService.save(order);
```

库存侧：

```java
int affectedRows = inventoryStockMapper.lockStockIfAvailable(goodsId, qty);
if (affectedRows == 0) {
    throw new IllegalStateException("库存不足，抢坑失败");
}
```

## 出现的问题：

- **分布式事务**：order 保存失败但 inventory 已锁 → 需 **解锁补偿**
- **热点行**：同一 goods_id 行 **串行**，DB 成为热点
- **连点两次**：两次 UPDATE 都成功 → 占两坑（非超卖，是 **重复占**）

## 解决方案：

- **解锁接口 + 定时对账**（V7 补偿）
- 极热点 SKU：**Redis 预扣 + DB 异步**（进阶）
- **幂等键** 防重复（V7）

## 项目中的库存场景：

面试金句：**「V4 是防超卖底座；V5 Redis 锁是跨机互斥练手，锁库存优先 V4 不是 V5；压测 V4 RT ~14s 优于 V2 ~20s」**。

## 面试官追问：

1. UPDATE 没走索引会怎样？
2. 间隙锁会导致什么问题？
3. Feign 调 inventory 失败怎么回滚？

## 高级回答：

- **无索引**：可能锁表或锁大量行 → 必须 **goods_id 主键/唯一索引**。
- **间隙锁**：RR 下范围锁，死锁风险 → 单行 PK 更新通常 **行锁** 即可。
- **Feign 失败**：order 未 save 则 inventory 需 **unlock**；或 **先锁后单** 设计下失败调补偿 API。
- 10 年答法：**「我口述从 V1 翻车到 V4 一条 SQL；生产默认这种，不 SELECT 再 UPDATE」**。

## 题 6：Redis 分布式锁（V5）

================

## 面试问题：

Redis 分布式锁如何实现？为什么解锁要用 Lua？Redisson 看门狗解决什么？V5 为什么比 V4 慢？

## 考察点：

- SET NX EX
- 误删别人锁、锁过期
- 与 V4 分工，不是替代

## 标准答案：

**加锁**：

```redis
SET lock:goods:1001 <uuid-token> NX EX 30
```

- **NX**：只有 key 不存在才成功（抢中央通行证）
- **EX**：过期防 **持锁者崩溃** 死锁

**解锁 Lua**（原子校验 + 删除）：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

防止 **线程 A 的锁过期，线程 B 获得锁，A  finally DEL 删掉 B 的锁**。

**看门狗（Redisson）**：业务执行超过 lease，**自动续期**，避免干到一半锁过期别人闯进来。

**V5 慢于 V4**：V5 临界区故意跑 **V1 非原子 + 串行 Redis 锁**，RT ~23s；V4 无应用层长锁，~14s。

## 公共厕所生活类比：

三栋楼共用一个 **100 坑中央厕区**（V2 每栋楼自己门口拦人不够）。  
**Redis = 中央发证处**：全城只有一张「进入厕区通行证」；拿到证才能进去 **看+登记+占坑**（V5 里仍用 V1 流程，但串行所以不超占）。  
**看门狗** = 你进去修管道久了，系统自动 **延长通行证**，不会修到一半证过期下一批人闯进来。  
**Lua 解锁** = 交证时必须验 **还是你的证**，不能错交把别人的证删了。

## Java 代码解释（项目 V5）：

```java
String token = goodsStockRedisLock.tryLock(goodsId, waitMs, leaseSeconds);
if (token == null) {
    return Result.fail("系统繁忙，获取库存锁超时（V5）");
}
try {
    // 故意 V1 非原子，证明「跨机锁 + 串行」也能不超锁
    String orderNo = v1SyncService.syncCreateOrderNonAtomic(dto);
    return Result.success("V5…" + orderNo);
} finally {
    goodsStockRedisLock.unlock(goodsId, token);  // Lua 校验 token
}
```

Redisson 版（V5r）：`RLock lock = redisson.getLock(key); lock.lock();` 看门狗自动续期。

## 出现的问题：

- **锁过期业务未完成** → 超占风险（看门狗缓解）
- **Redis 主从切换** 极端丢锁（RedLock 争议，面试知即可）
- **串行等待** → tryLock 超时，部分请求 **没占坑但不是超卖**（lockStock < 100）

## 解决方案：

- **锁库存**：优先 **V4 DB 原子**，Redis 锁用于 **必须串行的非 DB 场景**
- lease 合理 + 看门狗；**finally 解锁**
- 超时返回 **可重试** 提示，配合 Sentinel 限流

## 项目中的库存场景：

V5 是 **分布式锁教学**：手写 NX+Lua vs Redisson。面试：**「锁库存我不靠 Redis 锁替代 SQL；Redis 锁我用来理解 NX、过期、误删」**。

## 面试官追问：

1. RedLock 为什么有争议？
2. Zookeeper 锁和 Redis 锁区别？
3. 锁粒度 goodsId 还是 orderId？

## 高级回答：

- **RedLock**：多 master  quorum；Martin Kleppmann 质疑时钟与 fencing token。
- **ZK**：临时顺序节点，强一致慢一些；Redis 快，AP 模型要接受极端。
- **粒度**：库存竞争按 **goodsId**；订单幂等按 **idempotentKey**（V7）。
- 10 年答法：**「生产扣库存 V4；Redis 锁知道原理和坑，压测对比过 RT」**。

## 题 7：MQ 削峰与最终一致（V6）

================

## 面试问题：

为什么用 MQ 削峰？什么是最终一致？V6 如何保证不超卖？重复消费怎么办？

## 考察点：

- 异步解耦、背压
- 消费者仍用 V4
- 至少一次投递 + 幂等

## 标准答案：

**削峰**：HTTP 线程 **只发消息立即返回**「已受理」；后台消费者按能力 **慢慢占坑**，门口不堵死。

**最终一致**：用户拿到小票时 **坑可能还没占到**；几秒后查单才变「已锁库存」。≠ 强一致。

**不超卖**：正确性 **不靠 MQ**，靠消费者里 **V4 原子 SQL**。

**重复消费**：MQ **至少一次**，同消息两次 → 无幂等占两坑 → **必须 V7**。

## 公共厕所生活类比：

早高峰 200 人冲厕所，门口不再让人 **干等分坑**（同步 V4 堵 HTTP 线程）。  
保安 **扫码即发「已排队小票」**（93ms 返回），名单进 **后台叫号队列**（RabbitMQ）。  
后台按 **V4 电子门锁规则** 一个一个占坑，最终 **100 坑占满 100 人**，不会 109。  
你刚拿到小票去查，可能显示「分配中」——这就是 **最终一致**。  
同一张小票若被 **复印投递两次**（重复消费），没有幂等就会 **同一人占两坑**。

## Java 代码解释（项目 V6）：

生产者（HTTP 秒回）：

```java
OrderLockStockMessage message = new OrderLockStockMessage();
BeanUtil.copyProperties(dto, message);
rabbitTemplate.convertAndSend(RabbitMqConfig.QUEUE_ORDER_LOCK_STOCK, message);
return Result.success("V6：已受理，库存锁定处理中");
```

消费者（V4 占坑）：

```java
@RabbitListener(queues = RabbitMqConfig.QUEUE_ORDER_LOCK_STOCK)
public void onMessage(OrderLockStockMessage message) {
    OrderCreateDTO dto = toDto(message);
    // 正确性：V4 原子锁 + 建单
    v4SyncService.syncCreateOrderWithSqlLock(dto);
}
```

```text
HTTP 线程          RabbitMQ              消费者
  |-- 发消息 ------>|                      |
  |<-- 已受理 -------|                      |
  |                 |-- 投递 -------------->|
  |                 |                      |-- V4 UPDATE 占坑
```

压测：HTTP RT **93ms**、吞吐 **258/s**；最终 lockStock=100。

## 出现的问题：

- **消息积压**：消费者慢，队列堆满 → 监控 depth、扩容 consumer
- **重复消费** → V7 幂等
- **半失败**：坑占了单没建成 → **补偿任务** unlock
- **前端误解**：「成功」当「已占坑」→ UX 要「处理中」

## 解决方案：

- 消费者 **手动 ack**（处理完再 ack）
- **死信队列** DLQ 处理 poison message
- **V7 idempotentKey** + Redis SETNX
- 定时 **对账** 订单状态 vs 库存 lock

## 项目中的库存场景：

V6 是 **高并发入口形态**：秒杀/大促口述模板。个人项目 RabbitMQ 可能未常开，面试：**「代码与压测跑通过；生产无 MQ 时 V4+Sentinel 限流也可」**。

## 面试官追问：

1. RabbitMQ 如何保证消息不丢？
2. 顺序消费需要吗？
3. Kafka 和 RabbitMQ 选型？

## 高级回答：

- **不丢**：生产者 confirm、队列持久化、消费者 manual ack。
- **顺序**：同一 goodsId 进 **同一队列分区** 或单 consumer；否则乱序一般可接受。
- **Kafka**：高吞吐日志流；**RabbitMQ**：路由灵活、延迟队列；进销存订单量 Rabbit 够。
- 10 年答法：**「MQ 解决门口拥堵，不超卖仍靠 V4；重复消费必须幂等」**。

## 题 8：幂等与补偿（V7 可靠性收口）

================

## 面试问题：

什么是幂等？幂等键如何设计？V7 如何实现？补偿任务解决什么问题？

## 考察点：

- 防重复提交 vs 防超卖
- Redis SETNX / DB 唯一索引
- 最终一致下的失败恢复

## 标准答案：

**幂等**：同一 **业务请求** 执行多次，效果与执行一次相同（只占一个坑）。

**幂等键设计**：

- 前端生成 **clientRequestId / 业务单号**，随下单传入
- 粒度：一次用户意图一次 key；不要用 **每次随机 UUID**（等于没幂等）
- 存储：Redis `SET idempotent:{key} NX EX 86400` 或 DB **唯一索引**

**V7 压测**：同 idempotentKey 200 并发 → **lockStock=1**，RT ~62ms。

**补偿**：占坑成功但 **登记失败** / unlock 失败 → 记 **待补偿表**，定时任务释放或补单。

## 公共厕所生活类比：

**防超卖（V4）**：100 坑不会变成 109 个——解决 **太多人抢**。  
**幂等（V7）**：你 **手抖连按三下「占坑」**，系统认你的 **业务号** abc123：  
- 第一次：占坑成功，返回 orderNo  
- 第二、三次：「你已经占过了，还是 xxx」，**不会占三个坑**  

**补偿**：坑已经锁了，登记本 **卡纸没写上** 或 **释放失败** → 写到 **「待处理本」**，保洁定时来 **放坑或补登记**，避免账和坑对不上。

## Java 代码解释（项目 V7 思路）：

```java
public Result<String> createOrderV7(OrderCreateDTO dto) {
    String key = dto.getIdempotentKey();
    // 1. 幂等：同一业务号只占一次坑
    if (!idempotentService.tryAcquire(key, Duration.ofDays(1))) {
        String existing = idempotentService.getResult(key);
        return Result.success("重复请求，返回已有结果: " + existing);
    }
    try {
        // 2. 仍用 V4 原子占坑 + 建单
        String orderNo = v4SyncService.syncCreateOrderWithSqlLock(dto);
        idempotentService.saveResult(key, orderNo);
        return Result.success(orderNo);
    } catch (Exception e) {
        idempotentService.release(key);  // 失败释放，允许重试
        throw e;
    }
}

// 消费者 V6 + V7：先幂等再 V4
@RabbitListener(...)
public void onMessage(OrderLockStockMessage msg) {
    if (!idempotentService.tryAcquire(msg.getIdempotentKey())) {
        return;  // 重复消息直接跳过
    }
    v4SyncService.syncCreateOrderWithSqlLock(toDto(msg));
}
```

补偿任务（定时）：

```java
@Scheduled(fixedDelay = 60_000)
public void compensateFailedUnlock() {
    for (CompensateRecord r : compensateMapper.selectPending()) {
        try {
            inventoryStockClient.unlock(r.getGoodsId(), r.getQty(), r.getOrderNo());
            r.markDone();
        } catch (Exception e) {
            log.warn("补偿失败，下次再试: {}", r.getId());
        }
    }
}
```

## 出现的问题：

- **幂等键太粗**：用户 legit 下两单被误杀
- **先占坑后幂等**：仍可能重复占 → 幂等要在 **占坑前**
- **释放 key 过早**：用户重试时 key 已删又占第二坑 → 失败才 release，成功保留 TTL

## 解决方案：

- 幂等键 = **用户一次点击意图**（前端 UUID 或 订单草稿号）
- DB **order_no / client_request_id 唯一索引** 双保险
- 补偿 **指数退避 + 最大重试 + 人工告警**

## 项目中的库存场景：

**演进总纲**（面试 60 秒）：

```text
V1 翻车(109/100) → V2 JVM锁(100/100慢) → V4 SQL原子(快+稳)
→ V5 Redis锁(多实例练手) → V6 MQ(秒回+最终一致) → V7 幂等+补偿(生产收口)
```

**不是越新越替换**：V4 保不超占；V6 保不堵门；V7 保不重复。

## 面试官追问：

1. 幂等和去重有什么区别？
2. 支付回调幂等怎么做？
3. Seata 和 V7 补偿怎么选？

## 高级回答：

- **去重** 偏消息层；**幂等** 偏业务语义一致。
- **支付**：`out_trade_no` 唯一 + 状态机「已支付不再扣款」。
- **Seata AT**：强一致成本高；进销存 **TCC/Seata 口述 + V7 补偿务实落地**。
- 10 年答法：**「我项目用 V1～V7 讲清竞态、锁、原子 SQL、MQ、幂等；生产最小集 V4+限流+幂等键」**。
