## 版本说明

| 版本 | 方案 | 状态 |
|------|------|------|
| V1 | 无并发控制基线（**复现**多线程竞态超锁，**不解决**问题） | 基线 |
| V2 | JUC 基础并发（ReentrantLock 按商品互斥） | 已压测（JMeter），单机不超锁 |
| V3 | 线程池（任务拆分 + 异步） | 已压测（JMeter），正确性同 V2，RT 小幅优于 V2 |
| V4 | SQL 并发控制（`WHERE stock-lock_stock>=qty` 原子锁定） | 已压测（JMeter），不超锁，RT/吞吐明显优于 V2/V3 |
| V5 | Redis 手写锁（`version=v5`，SET NX + Lua） | 已压测（JMeter），不超锁；同商品串行，RT 接近 V2 |
| V5r | Redis Redisson 锁（`version=v5r`，看门狗） | 已压测（JMeter），正确性同 V5，性能与 V5 同量级 |
| V6 | MQ 最终一致性（RabbitMQ 异步锁库存，`version=v6`） | 已压测（200 并发等效 JMeter），不超锁，HTTP 秒级返回 |
| V7 | 幂等 + 补偿机制（生产级） | 待做 |

#### V1 vs V2 性能对比（JMeter，200 并发，本机）

| 指标 | V1 | V2 | 说明 |
|------|----|----|------|
| 业务成功 / 失败 | 109 / 91 | **100 / 100** | V2 正确；V1 超锁 9 单 |

| HTTP 异常 % | 0% | 0% | 均 200 OK；失败为业务 body |
| 平均响应 | ~4867 ms | **~21162 ms** | V2 请求在 ReentrantLock 上排队 |

## JMeter HTTP 压测（dev）

### 测试计划结构

```
测试计划
 └── 线程组（线程数 200，Ramp-Up 1 秒，循环 1）
      ├── HTTP信息头管理器
      ├── HTTP请求
      ├── 汇总报告（推荐）
      └── 查看结果树（调试用，线程多时会卡）
```

### HTTP 信息头管理器

| 名称 | 值 |
|------|-----|
| `Content-Type` | `application/json` |
| `Authorization` | `Bearer {accessToken}`（登录接口获取，过期需重新登录） |

### HTTP 请求（必为 POST）

| 项 | 值 |
|----|-----|
| 方法 | **POST**（用 GET 会报 `Request method 'GET' is not supported`） |
| 协议 | `http` |
| 服务器 | `localhost` |
| 端口 | `8080` |
| 路径 | `/api/order/concurrency/order/add?version=v1` |

**Body Data（消息体数据）：**

```json
{
  "userName": "jmeter-t${__threadNum}",
  "goodsId": "2064625692771397632",
  "goodsName": "小米17",
  "costPrice": 3999,
  "salePrice": 4399,
  "buyQty": 1,
  "remark": "JMeter V1"
}
```

V2 压测：路径改为 `?version=v2`，Body 中 `remark` 建议改为 `"JMeter V2"`。

V3 压测：路径改为 `?version=v3`，Body 中 `remark` 建议改为 `"JMeter V3"`（便于 SQL 区分版本；仅改 URL 不改 remark 时订单表会仍显示 V1）。

### 压测前必做：清理 + 重置（否则 usable=-9，全部「库存不足」）

上次 JUnit/JMeter 若已超锁（lockStock=109），**不清理直接再压** 会返回：

```json
{"code":500,"message":"库存不足，当前可用库存：-9"}
```

说明 **POST 与 Token 已正常**，只是库存处于超锁残留状态，不是认证失败。

**方式 A：SQL（推荐，最干净）**

```sql
-- 1. 删除压测订单
DELETE FROM order_info
WHERE goods_id = 2064625692771397632
  AND (user_name LIKE 'junit-%' OR user_name LIKE 'jmeter-%');

-- 2. 重置库存
UPDATE inventory_stock
SET stock = 100,
    lock_stock = 0,
    update_time = NOW()
WHERE goods_id = 2064625692771397632;
```

**方式 B：HTTP 重置（需 Token，不删订单时 lockStock 仍可能不准）**

```
POST http://localhost:8080/api/order/concurrency/stock/reset?goodsId=2064625692771397632&stock=100&lockStock=0
Header: Authorization: Bearer {token}
```

**压测后核对：**

```
GET http://localhost:8080/api/order/concurrency/stock/result?goodsId=2064625692771397632
```

期望起点：`stock=100, lockStock=0, usable=100, overLocked=false`。

### 常见报错对照

| 现象 | 原因 | 处理 |
|------|------|------|
| `Request method 'GET' is not supported` | HTTP 方法仍是 GET | 改为 **POST** |
| `code: 1102` / Token 相关 | Token 过期或无效 | 重新登录换 Token |
| `code: 10500` 系统繁忙 | 服务端未捕获异常 | 看 IDEA 控制台栈信息 |
| `库存不足，当前可用库存：-9` | 未清理上次超锁数据 | 执行上方 SQL 后再压 |
| `code: 200` 且 msg 含「订单创建成功」 | 正常成功 | — |

> 说明：业务失败时 `code` 可能为 **500**（`ResultCode.FAIL`），与 HTTP 状态码不同；成功为 **code: 200**。

#### V3 实现说明

| 项 | 说明 |
|----|------|
| 入口 | `POST /api/order/concurrency/order/add?version=v3` |
| 并发安全 | 与 V2 相同：`ReentrantLock(goodsId)` |
| 同步路径 | 校验库存 → 保存订单 → `lockStockUpdateOnly`（只改 lock_stock） |

#### V4 实现说明

| 项 | 说明 |
|----|------|
| 入口 | `POST /api/order/concurrency/order/add?version=v4` |
| 并发安全 | **无 JVM 锁**；`UPDATE inventory_stock SET lock_stock=lock_stock+? WHERE goods_id=? AND stock-lock_stock>=?` |
| 事务 | 原子锁库存 + 写流水 + 插入订单，同一 `@Transactional` |

#### V2 / V3 / V4 性能对比（JMeter 复测，200 并发，本机）

| 指标 | V2 | V3 | V4 | 说明 |
|------|----|----|-----|------|
| JVM ReentrantLock | 有 | 有 | **无** | V4 靠 SQL 条件 UPDATE |
| 业务结果 | 100/100 | 100/100 | 100/100 | 均 `overLocked=false` |
| 平均响应 | 19293 ms | ~18850 ms | **14234 ms** | V4 较 V2 约 **-26%** |
| 最小 / 最大 | 290 / 32053 | ~314 / ~32607 | **2433 / 19289** | V4 最大明显低于 V2 |
| 吞吐量 | 6.1/sec | ~5.9/sec | **10.3/sec** | V4 较 V2 约 **+69%** |

**结论：** V4 去掉 JVM 锁排队，用 `WHERE stock - lock_stock >= qty` 原子锁定；库存不足的请求快速失败，成功的并发竞争缩短为数据库行级 UPDATE。**正确性同 V2/V3，性能显著优于 V2/V3**；多实例场景 SQL 原子条件仍有效（V5 Redis 用于跨节点协调等扩展场景）。

#### V5 / V5r 实现说明（Redis 分布式锁，2026-07）

| 项 | `v5` 手写 | `v5r` Redisson |
|----|-----------|----------------|
| 代码 | `OrderCreateConcurrencyV5` + `GoodsStockRedisLock` | `OrderCreateConcurrencyV5Redisson` + `GoodsStockRedissonLock` |
| 加锁 | `SET ... NX EX` | `RLock.tryLock(wait, -1, …)` 看门狗 |
| 解锁 | Lua 校验 token | `unlock()`（仅当前线程持有） |
| 临界区 | 均为 V1 非原子链路 | 同左 |
| 压测 URL | `?version=v5` | `?version=v5r` |

**压测结果（JMeter，200 并发，本机，2026-07-19）：**

| 版本 | 工具 | lockStock | usable | 超锁 | 平均 RT | 吞吐 | 备注 |
|------|------|-----------|--------|------|---------|------|------|
| v5 | JMeter | 88 | 12 | **否** | ~23646 ms | 6.4/s | 手写 SET NX；有「获取锁超时」；HTTP 异常 % = 0 |
| v5r | JMeter | 76 | 24 | **否** | ~24482 ms | 6.4/s | Redisson 看门狗；同样有抢锁超时；与 v5 同量级 |

| 指标 | V4 | V5 | V5r | 说明 |
|------|----|----|-----|------|
| overLocked | false | **false** | **false** | 均不超锁 |
| 平均响应 | ~14234 ms | **~23646 ms** | **~24482 ms** | Redis 锁串行 + 网络，接近 V2 |
| 吞吐量 | ~10.3/s | **~6.4/s** | **~6.4/s** | 与 V2（~6/s）同量级，低于 V4 |
| 多实例 | SQL 条件仍有效 | **跨 JVM 有效** | **跨 JVM 有效** | V5/V5r 锁在 Redis，不在单机内存 |

> 说明：`stock/reset` 只重置库存，不清理历史待支付单，故 `pendingOrderCount` 会偏大，**不以它当本轮成功数**；以 `overLocked` + `lockStock` 为准。高压下同商品抢一把锁，部分请求会在 `lock-wait-ms`（30s）内超时放弃，故 lockStock 可能 < 100，属预期，**不是超锁**。

**结论：** V5/V5r **正确性达标（不超锁）**，适合多实例叙事；性能接近 V2（串行代价），**明显慢于 V4**。手写与 Redisson 吞吐/RT 接近，Redisson 优势在可重入与看门狗续期，而非压测数字碾压。

**口述对照：** V2 = 单机锁；V5/V5r = 跨 JVM 锁；V4 = SQL 原子。V6/V7 **不强制** Redisson。

#### V6 实现说明（RabbitMQ 异步锁库存，2026-07）

| 项 | 说明 |
|----|------|
| 压测参数 | `?version=v6` |
| 生产者 | `OrderCreateConcurrencyV6`：校验 → `RabbitTemplate.convertAndSend` → 立即返回「已受理」 |
| 消费者 | `OrderLockStockConsumer`：`@RabbitListener` → 复用 `OrderCreateConcurrencyV4SyncService` |
| 队列 | `order.concurrency.lock.stock`（`RabbitMqConfig`，durable） |
| Broker | 本机 Docker：`rabbitmq:3-management`（5672 / 15672，guest/guest） |
| 一致性 | **最终一致**：HTTP 返回时库存可能尚未变化 |
| 正确性 | 消费者内走 V4 原子 SQL，避免多消费者并发超锁；幂等留给 V7 |

```text
HTTP 线程                     RabbitMQ                    消费者线程
   |                             |                            |
   |-- 发 OrderLockStockMessage ->|                            |
   |<-- 立刻 Result 已受理 -------|                            |
   |                             |-- 投递 -------------------->|
   |                             |                            |-- V4 原子锁库存 + 建单
```

**压测结果（200 并发等效 JMeter：RunspacePool 同时发 HTTP，参数同历史 JMeter，2026-07-20）：**

| 项 | 结果 |
|----|------|
| HTTP | 200/200 成功（均为「已受理」） |
| 平均 / 最小 / 最大 RT | **~4 ms** / ~1 ms / ~41 ms |
| 吞吐（按发完墙钟） | **~526/s**（墙钟约 0.38s） |
| 最终库存 | stock=100，**lockStock=100**，usable=0，**overLocked=false** |
| 消费收敛 | 发完后约 30s 内 lockStock 从 0 爬到 100（最终一致可见） |

| 指标 | V5（同步 Redis 锁） | V6（MQ 异步） | 说明 |
|------|---------------------|---------------|------|
| HTTP 平均 RT | ~23.6 s | **~4 ms** | V6 只发消息即返回 |
| 吞吐 | ~6.4/s | **~526/s** | 不可直接当「业务吞吐」比：V6 HTTP 成功≠当时已锁库存 |
| 最终 lockStock | 本轮未锁满（抢锁超时） | **100** | V6 消费者走 V4，锁满库存 |
| 超锁 | 否 | **否** | 正确性达标 |

**结论：** V6 练的是**异步解耦 / 削峰**与**最终一致**；HTTP RT 相对 V5 **数量级下降**。正确性不靠「发消息」，而靠消费者内的 V4。重复消费、死信、补偿见 V7。

## 判定标准

- **超锁**：成功订单数 > 100，或 `锁定库存 > 100`，或可用库存被抢成负数逻辑
- 压测前：将该商品 `锁定库存` 归零，清理测试订单（可选）
