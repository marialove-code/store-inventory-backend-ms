## 一、是什么

### 1.1 一句话

**Sentinel** 是阿里开源的**流量防护**组件：对「资源」做限流、熔断降级、热点、系统保护等，避免服务被打垮或被下游拖死。

### 1.2 和 Hystrix / Resilience4j

| | Sentinel | Hystrix（已停更） |
|--|----------|-------------------|
| 重心 | 流量控制 + 熔断 + Dashboard | 偏熔断隔离 |
| 规则 | 可动态调、可接配置中心 | 相对静态 |
| 生态 | Spring Cloud Alibaba 标配 | Netflix 老栈 |

### 1.3 核心概念

| 概念 | 含义 |
|------|------|
| **资源（Resource）** | 被保护的单位：方法名、URL、Feign 调用等 |
| **规则（Rule）** | 对该资源怎么拦：QPS、异常比例等 |
| **BlockException** | 被规则拦住时抛出（流控 `FlowException`、熔断 `DegradeException` 等） |
| **blockHandler** | 专门处理「被 Sentinel 拦住」 |
| **fallback** | 多处理「业务方法自己抛异常」（与 block 分工） |
| **Dashboard** | 控制台：看 QPS、点选配规则（默认推到客户端内存） |

### 1.4 五大规则类型（面试地图）

```text
Sentinel
├── 流控（Flow）        ← 管「量」——你们重点做过
├── 熔断降级（Degrade） ← 管「质」——你们重点做过
├── 热点参数（Param）   ← 按某个参数值限流 —— Dashboard 常考
├── 授权（Authority）   ← 按调用来源允许/拒绝 —— 了解
└── 系统（System）      ← 按负载/CPU/入口 QPS 等 —— 了解
```

## 二、有什么用

| 场景 | 用哪类 | 价值 |
|------|--------|------|
| 秒杀 / 接口被刷 | 流控 | 保护自己，多余请求快速失败 |
| 库存服务挂了还狂下单 | 熔断 | 调用方快速失败，给下游喘息，保护线程 |
| 某个商品 ID 被刷爆 | 热点 | 只限热 key，其它正常 |
| 入口总流量过大 | 系统规则 / 网关限流 | 全局保护 |
| 只允许网关调某内部接口 | 授权 | 来源控制（用得相对少） |

**限流 vs 熔断（必背）：**

| | 限流 | 熔断 |
|--|------|------|
| 看什么 | 流量多少（QPS / 并发线程） | 调用质量（慢/异常） |
| 典型 | 人太多 | 下游挂了、超时多 |
| 你们例子 | `orderCreate` QPS | `inventoryUsable` 异常比例 |

## 三、怎么用（原理 + 配置细节）

### 3.1 接入方式（代码侧）

1. 依赖：`spring-cloud-starter-alibaba-sentinel`  
2. 配置 Dashboard：`spring.cloud.sentinel.transport.dashboard`（我们用 **8858**）  
3. 资源埋点：  
   - `@SentinelResource(value, blockHandler)`  
   - Web 默认还可按 **URL** 埋点（控制台里常见 `/create` 这种）  
4. 规则来源：  
   - 代码 `FlowRuleManager.loadRules` / `DegradeRuleManager.loadRules`  
   - 或 Dashboard 推送（内存）  
   - 生产：Nacos 等持久化（我们未做）

**项目注意：**  
`csp.sentinel.dashboard.server` 最好在 `main` 里提前设置；`eager: false`，避免心跳早于地址注入。

### 3.2 流控规则（Dashboard「流控规则」细节）

| 配置项 | 含义 | 口述要点 |
|--------|------|----------|
| **资源名** | 要保护的资源 | 与 `@SentinelResource` 或 URL 一致 |
| **针对来源** | `default` = 不区分来源 | 可按调用方应用名区分（进阶） |
| **阈值类型** | **QPS** 或 **并发线程数** | QPS=每秒次数；线程数=同时执行数 |
| **单机阈值** | 阈值数字 | 单机维度；集群另说 |
| **是否集群** | 一般不勾 | 集群限流要另配 |
| **流控模式** | 直接 / 关联 / 链路 | 学习用 **直接** 即可 |
| **流控效果** | 快速失败 / Warm Up / 排队等待 | 见下表 |

**流控模式（了解）：**

| 模式 | 含义 |
|------|------|
| **直接** | 看本资源自己的流量 |
| **关联** | 关联资源超了，限本资源（如写库太忙限制读） |
| **链路** | 只统计从某入口进来的调用 |

**流控效果（常考）：**

| 效果 | 行为 | 和算法的关系（口述级） |
|------|------|------------------------|
| **快速失败** | 超阈值立刻拒 | 最常见；偏「计数超限就拒」 |
| **Warm Up** | 冷启动，阈值逐渐升到设定值 | 防服务刚启动被打满 |
| **排队等待** | 匀速通过，超时再拒 | 接近**漏桶**「匀速出水」思想 |

**漏桶 / 令牌桶（面试对比，不必实现）：**

| | 漏桶 | 令牌桶 |
|--|------|--------|
| 直观 | 出口匀速，桶满则拒 | 按速率发令牌，有令牌才过 |
| 突发 | 较弱 | 桶内令牌可支撑一定突发 |
| 和 Sentinel | 「排队等待」更像漏桶平滑 | 很多网关用令牌桶；Sentinel 以规则效果为主理解即可 |

### 3.3 熔断降级（Dashboard「熔断规则」细节）

**状态机（必背）：**

```text
关闭 Closed ──(指标超阈值)──► 打开 Open ──(timeWindow 结束)──► 半开 Half-Open
     ▲                                                              │
     └──────────── 探测成功 ─────────────────────────────────────────┘
                   探测失败 → 回到 Open
```

| 配置项 | 含义 |
|--------|------|
| **熔断策略** | 慢调用比例 / 异常比例 / 异常数 |
| **最大 RT** | 慢调用：超过算「慢」（慢调用比例时用） |
| **比例阈值** | 如 0.5 = 50% |
| **最小请求数** | `minRequestAmount`，太少不算，防误熔断 |
| **统计时长** | `statIntervalMs` |
| **熔断时长** | `timeWindow`（秒），Open 持续多久再半开 |

**三种策略：**

| 策略 | 何时用 |
|------|--------|
| **慢调用比例** | 下游没挂但很慢，拖线程 |
| **异常比例** | 大量失败（我们 `inventoryUsable` 用的） |
| **异常数** | 按失败次数绝对值 |

**被熔断后：** 抛 `DegradeException` → `blockHandler`；方法体不执行。

### 3.4 热点参数（Dashboard 常考，我们未落地）

**是什么：** 对方法**某个参数的具体值**单独限流。  
**例子：** `goodsId=热门商品` QPS=2，其它商品不限或更宽。

| 要点 | 说明 |
|------|------|
| 埋点 | `@SentinelResource` + 热点参数索引 |
| 规则 | 参数索引、阈值类型、单机阈值；可针对特定参数值例外 |
| 和普通流控 | 普通流控管整个资源；热点管「某一个 key」 |

**口述：** 防「热 key」打爆，而不是一刀切限死所有请求。

### 3.5 授权规则（了解）

按 **origin（调用来源）** 做白名单 / 黑名单。  
例如只允许 `gateway` 调某资源。实际项目里鉴权更多在网关/Token，授权规则用得相对少。

### 3.6 系统规则（了解）

按整机指标保护，例如：

- 入口 QPS  
- CPU 使用率  
- 系统负载 load  
- 平均 RT、并发线程数  

偏「系统快撑不住了，先挡入口」。

### 3.7 blockHandler vs fallback

| | blockHandler | fallback |
|--|--------------|----------|
| 触发 | `BlockException`（限流/熔断等） | 业务异常、超时等（按配置） |
| 签名 | 原参数 + `BlockException` | 原参数 + `Throwable`（常见） |
| 我们项目 | 下单/取消、库存门面都写了 blockHandler | 演示未强调 fallback |

### 3.8 规则存在哪

| 方式 | 特点 |
|------|------|
| 代码 loadRules | 启动就有，适合学习/保底 |
| Dashboard 推送 | 改完马上生效，**默认内存，重启易丢** |
| Nacos 等持久化 | 生产推荐；启动拉取 + 动态推送 |

## 四、有什么问题（我们踩过 + 面试常问）

| 编号 | 问题 | 现象 |
|------|------|------|
| P1 | Dashboard 看不到应用 | 左侧无应用；日志 `Dashboard server address not configured` |
| P2 | 规则不生效 | 连点也不限流 / 不停库存也不熔断 |
| P3 | Dashboard 规则重启丢失 | 重启 order 后控制台规则没了 |
| P4 | 端口冲突 | Dashboard 占 8080，和 Gateway 撞车 |
| P5 | 只有 Feign 503，没有 DegradeException | 停库存连点下单一直 503 |
| P6 | 同类调用注解失效 | 挂在 `getUsable`，实际走 `getUsableStock → this.getUsable()` |
| P7 | 业务限流太狠 | QPS=2 导致正常点单也被拦 |
| P8 | URL 资源 vs 注解资源 | 控制台 `/create` 与代码 `orderCreate` 不是同一个资源 |

## 五、怎么解决

| 编号 | 解决 |
|------|------|
| P1 | `eager: false` + `main` 里提前 `csp.sentinel.dashboard.server=127.0.0.1:8858`；重启后先访问几次接口 |
| P2 | 查资源名是否一致；规则是否被 `loadRules` 清空；开关是否打开 |
| P3 | 学习阶段接受内存；生产做 **Nacos 持久化**；重要规则也可写进代码保底 |
| P4 | Dashboard 用 **8858** |
| P5 | 下单先查库存：熔断要挂在真实入口；停 inventory 后先失败再熔断 |
| P6 | **注解挂在外部调用的入口方法**；避免依赖 `this.xxx()` 触发 AOP（与 `@Transactional` 同类坑） |
| P7 | 业务默认 QPS 放宽（如 20）；演示再调低 |
| P8 | 讲清：Web 默认 URL 资源 + `@SentinelResource` 自定义资源，规则要对准名字 |

## 六、高频口述题（可直接背）

### Q1. Sentinel 是什么？你们怎么用的？

流量防护组件。我们在 order-service 接了 Sentinel：下单/取消做 QPS 流控；查可用库存/锁解锁做异常比例熔断；探活接口保留作限流熔断演示；Dashboard 在 8858。

### Q2. 限流和熔断区别？

限流管量（人太多）；熔断管质（下游差）。限流看 QPS/线程数；熔断看慢调用/异常比例/异常数，有关闭-打开-半开。

### Q3. 熔断状态机？

关闭正常统计 → 超阈值打开快速失败 → 过熔断时长半开放探测 → 成功关闭 / 失败再打开。

### Q4. blockHandler 和 fallback？

blockHandler 处理被 Sentinel 拦住；fallback 处理业务异常。我们重点用了 blockHandler。

### Q5. 规则为什么要持久化？

Dashboard 默认改内存，重启丢失。生产用 Nacos 等存规则，保证重启后一致、可动态刷新。

### Q6. 漏桶和令牌桶？

漏桶匀速出水、抑制突发；令牌桶按速率发令牌、允许一定突发。Sentinel 的排队等待更接近漏桶平滑思想；快速失败是超限即拒。

### Q7. 热点参数限流是什么？

对资源某个参数的特定值单独限流，解决热 key，而不是一刀切。

### Q8. 为什么同类 this 调用 Sentinel 不生效？

`@SentinelResource` 靠 Spring AOP 代理；`this.method()` 不经代理。我们把熔断挂在 `getUsableStock`（下单真正调用的入口）才验证成功。

### Q9. Sentinel 和网关限流关系？

可在 Gateway 做入口限流，服务内再对核心资源限流/熔断，多层防护。我们目前在服务内演示，Gateway 侧未接 Sentinel。

### Q10. 和 Seata 区别？

Sentinel 管流量与稳定性；Seata 管分布式事务。不是一类东西。
