## 题 1：单体 vs 微服务 — 何时拆、何时不拆

================

## 面试问题：

什么是单体、什么是微服务？为什么要拆？一定比单体好吗？你们进销存怎么拆的？

## 考察点：

- 边界清晰、独立部署、故障隔离
- 分布式代价诚实
- 集群（多实例）≠ 微服务（多服务）

## 标准答案：

**单体**：一个进程承载登录、商品、库存、订单等，通常 **一个 jar、一个端口**（如 `store-inventory-backend:8080`）。

**微服务**：按 **业务边界** 拆成多个可独立部署的服务，各自进程、独立扩缩与发布。

| 收益 | 说明 |
|------|------|
| 独立演进 | 改库存不必整站发版 |
| 独立扩容 | 下单高峰只加 order/inventory |
| 故障隔离 | 库存挂了，登录仍可能可用 |
| 团队边界 | 大团队按服务分工 |

**代价**：分布式调用、超时、一致性、注册发现、链路排查、运维成本上升。

**不是一定更好**：人少、流量小、边界不清时，**单体更合适**。面试：**按痛点选型，不为微服务而微服务**。

**区分**：

```text
微服务拆分：order-service ≠ inventory-service（不同职责）
集群多实例：inventory-A 与 inventory-B（同一服务两份进程）
```

金风时期 **两台服务器跑同一 Eureka 注册的应用** = **集群 HA**，不一定是「已拆多个微服务」。

## 通俗理解：

单体像 **一家店前后台全在一个铺面**；微服务像 **连锁：收银、仓库、客服分门店**，但要电话协调、对账更麻烦。

## 项目结合：

| 服务 | 端口 | 职责 |
|------|------|------|
| gateway-service | 8080 | 统一入口、路由、鉴权 |
| platform-service | 8081 | 认证、商品、RBAC、看板 |
| inventory-service | 8082 | 库存、内部 lock API |
| order-service | 8083 | 订单、并发 V1～V7 |
| ai-service | 8084 | Spring AI |

- 家里生产仍可用 **单体** `store-inventory-backend`；学习仓 **ms** 验证拆分
- 实验：停 Gateway 全站不通；只停 inventory，登录仍可用 → **隔离**

## 面试官追问：

1. 你们按什么原则划服务边界？
2. 分布式事务怎么处理？
3. 微服务数量多少合适？

## 高级回答：

- **边界**：按 **变更频率、团队、数据主权**（库存表归 inventory）；避免按技术层拆「DAO 服务」。
- **事务**：本地事务 + 最终一致/补偿；Seata 口述即可（见题 7）。
- 10 年答法：**「个人项目 4～5 个服务够演示；金风是大域拆分，进销存是小域验证全流程」**。

## 题 2：注册中心 — 为什么需要、核心流程

================

## 面试问题：

微服务为什么需要注册中心？注册、发现、调用分别是什么？没有 Nacos 行不行？

## 考察点：

- 动态 IP、扩缩容
- 与配置、DNS、K8s Service 的关系
- 为 Eureka/Nacos 对比铺垫

## 标准答案：

**问题**：order 调 inventory，地址 **随部署变化**（换机器、加实例、Docker/K8s 漂移），写死 `localhost:8082` 不可维护。

**注册中心**：服务启动 **注册**（服务名 → IP:端口列表）；消费者 **发现**（按名拉实例）；**调用** 时 LoadBalancer 选一个实例。

| 步骤 | 含义 | 进销存例子 |
|------|------|------------|
| 注册 | 提供者上报 | inventory 向 Nacos 报 8082 |
| 发现 | 消费者查列表 | order 问 inventory-service 有哪些实例 |
| 调用 | HTTP/RPC | Feign + LB 发真实请求 |

**没有注册中心也可以**：

- 写死 URL、Nginx upstream 手工维护
- **K8s Service + DNS**（集群内发现）
- **配置中心** 配地址列表

Spring Cloud 教程默认注册中心；上 K8s 后 **发现可交给集群**，Nacos 可 **偏配置**。

## 通俗理解：

注册中心像 **公司内部分机总机**：仓库搬家（换 IP）自己报新分机号，订单部按「库存部」三字拨号，总机转接，不用记每个人手机。

## 项目结合：

```yaml
spring:
  application:
    name: inventory-service
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
```

- Feign：`@FeignClient(name = "inventory-service", path = "/api")`
- Gateway：`lb://inventory-service` 路由
- 心跳延迟：进程 kill 后 Nacos **短暂仍显示**，需看健康检查与端口

## 面试官追问：

1. 客户端缓存实例列表多久刷新？
2. 注册中心挂了会怎样？
3. 多环境如何隔离？

## 高级回答：

- **缓存**：LoadBalancer 定期从 Nacos 拉；短暂不一致可接受，配合 **重试换实例**。
- **Nacos 集群**：生产 3 节点；客户端有 **本地缓存** 可短期容错。
- **namespace**：dev/test/prod 隔离；本机 `public`。
- 10 年答法：**「我项目 Nacos 2.5.2；能画 register → discover → Feign 三角」**。

## 题 3：Eureka vs Nacos 专题对比（重点）

================

## 面试问题：

你金风用过 Eureka，进销存用 Nacos。请对比两者：**架构形态、功能、一致性模型、优缺点、适用场景**。为什么国内新项目多选 Nacos？

## 考察点：

- 真实经历（Eureka 2020 前后）+ 当前项目（Nacos + SCA）
- AP vs CP、自我保护、配置中心
- 不贬低 Eureka，说清 **时代与场景**

## 标准答案：

### 3.1 架构形态

| 维度 | **Eureka**（Netflix / Spring Cloud Netflix） | **Nacos**（阿里 / SCA） |
|------|---------------------------------------------|-------------------------|
| 部署 | 常是 **自建 Eureka Server**（Spring Boot 应用）+ Client | **独立中间件**（解压/Docker，8848） |
| 生态 | Spring Cloud **Netflix** 套件（Ribbon 老、Hystrix 停更） | **Spring Cloud Alibaba**（Sentinel、Seata 等） |
| 维护 | Netflix **2.x 停更**，社区维护弱 | 国内活跃，与 Boot 3 / SCA 同步 |

### 3.2 功能对比

| 能力 | Eureka | Nacos |
|------|--------|-------|
| 服务注册发现 | ✅ 核心能力 | ✅ |
| **配置中心** | ❌ 需另配 Spring Cloud Config | ✅ **同一产品** |
| 健康检查 | 客户端心跳 | 心跳 + 可选 TCP/HTTP 探活 |
| 元数据/权重 | 基础 | 较丰富（权重、集群名） |
| 控制台 | Eureka Dashboard 简洁 | Nacos 控制台（服务+配置） |
| DNS | 不支持 | 支持 |

### 3.3 一致性模型（面试高频）

| | Eureka | Nacos |
|---|--------|-------|
| 默认模式 | **AP**（可用性优先） | 注册发现默认 **AP**；配置可 **CP** |
| 典型行为 | **自我保护**：大量心跳丢失时不轻易剔除实例，防网络抖动误杀 | 可切换持久化与一致性策略 |
| 含义 | 宁可 **返回可能过期的实例列表**，也要保证注册中心可用 | 配置发布等场景可强一致 |

**Eureka 自我保护（生活化）**：

> 早高峰厕所总机突然收不到很多分机「我还活着」的信号——可能是 **网络抖了一下**，不是真全挂了。Eureka **暂不把它们从通讯录划掉**，避免订单部以为库存部全灭。代价：列表里可能有 **已死实例**，调用方要自己 **快速失败 + 重试下一台**。

**Nacos**：网络分区时可配置策略；配置中心写配置常用 **CP**（Raft），避免配置丢失。

### 3.4 优缺点总结

**Eureka 优点**：

- 与 **Spring Cloud Netflix** 集成成熟（当年标准答案）
- 客户端 **本地缓存**，注册中心短故障 **仍可发现**（AP）
- 概念简单，**只做注册发现**，边界清晰
- 适合 **2018～2021** 前后 Spring Cloud 技术栈

**Eureka 缺点**：

- **不再积极演进**，Boot 3 / 新 JDK 生态弱
- **无内置配置中心**，Config Server + Git 另搭
- 与 **Ribbon/Hystrix** 老组件绑定，迁移成本
- 控制台与 **多环境、权重、配置** 不如 Nacos 一站式

**Nacos 优点**：

- **注册 + 配置** 一体，运维一个组件
- **国内文档、社区、SCA 绑定** 紧
- 支持 **命名空间、分组、权重、灰度** 等
- 与 **Sentinel、Seata** 等同栈

**Nacos 缺点**：

- 多能力一体，**概念比 Eureka 多**（namespace/group/dataId）
- 独立中间件，要 **运维集群、升级、备份**
- 若只用发现，有人觉得 **比 Eureka 重**（但国内普遍接受）

### 3.5 为什么进销存选 Nacos

1. **新项目 2025+**，跟 **SCA + Boot 3** 主线  
2. **配置与发现** 一个控制台（数据库、Feign、AI Key 等）  
3. 与 **Sentinel** 限流同一生态，面试叙事统一  
4. 金风 Eureka 经验 **可迁移概念**（注册/发现/心跳），换实现成本低  

### 3.6 口述模板（60 秒）

> 金风 2020 前后拆分用过 **Spring Cloud + Eureka**，主要是 **服务注册发现**，两台机器同应用那是 **多实例 HA**。Eureka **AP 模型 + 自我保护**，注册中心短时故障客户端还能用缓存，适合当时 Netflix 栈。  
> 进销存个人项目用 **Nacos + SCA**，除了发现还有 **配置中心**，和 Gateway、Sentinel 一套。新项目国内 **Nacos 更主流**；若公司已 K8s，发现也可交给 **Service**，注册中心偏配置。  
> 两者 **不是谁碾压谁**，是 **时代与配套** 不同；我理解 Eureka 原理，生产按团队栈选型。

## 项目结合：

| 经历 | 技术 | 你该怎么讲 |
|------|------|------------|
| 金风 2020 前后 | Eureka + Spring Cloud | 「参与拆分与联调，理解注册发现」 |
| 进销存 ms | Nacos 8848 + Discovery | 「platform/inventory/order/ai 注册，Feign 按名调用」 |
| 家里单体 | 无注册中心 | 「生产简单，学习仓验证微服务」 |

```text
# Eureka 时代（概念）
inventory-server  →  register →  Eureka Server
order-server      →  fetch    →  Eureka Server  →  Ribbon 选实例

# 进销存 Nacos（当前）
inventory-service →  register →  Nacos :8848
order-service     →  Feign    →  LoadBalancer → inventory 实例
```

## 面试官追问：

1. Eureka 和 Consul、Zookeeper 怎么比？
2. Nacos 1.x 和 2.x gRPC 区别？
3. 从 Eureka 迁移 Nacos 要改什么？

## 高级回答：

- **Consul**：CP 可选，健康检查强，多数据中心；**ZK**：CP，曾作 Dubbo 注册，不适合当配置中心大规模写。
- **Nacos 2.x**：客户端 gRPC 长连接，推送更快，心跳压力小。
- **迁移**：依赖换 `nacos-discovery`；`eureka.client` 改 `spring.cloud.nacos`；Ribbon 换 **LoadBalancer**；配置从 Config Server 迁 Nacos Config。
- 10 年答法：**「Eureka 懂 AP 和自我保护；Nacos 懂发现+配置；K8s 懂 Service 替代发现」** — 三句显得有宽度。

## 题 4：Gateway、Feign 与调用链

================

## 面试问题：

Gateway 和 Feign 分别干什么？外部请求和服务间调用路径有何不同？`lb://` 是什么？

## 考察点：

- 边缘网关 vs 内部 RPC
- path、context-path 坑
- 完整链路口述

## 标准答案：

**Gateway（Spring Cloud Gateway）**：

- **统一对外入口**（8080）
- 路由：`/api/order/**` → order-service
- 全局 Filter：JWT、CORS、限流、日志 traceId
- 基于 **WebFlux + Netty**

**OpenFeign**：

- **服务间声明式 HTTP**
- order **内部** 调 inventory，**不绕 Gateway**（少一跳、内网信任边界）

**`lb://inventory-service`**：LoadBalancer 协议，从 Nacos 拿实例列表再选一个。

**完整链路**：

```text
浏览器 → 前端代理 → Gateway:8080
       → Nacos 查 platform/order/…
       → LB 选实例 → 业务 Controller

下单锁库存：
order-service → Feign inventory-service
             → Nacos → LB → inventory:8082/internal/lock
```

## 通俗理解：

Gateway 像 **公司大门前台**（外人只找前台）；Feign 像 **部门之间内线**（订单部直接打仓库分机，不必出大门再进来）。

## 项目结合：

- Gateway 路由表 + JWT 白名单 `/api/auth/login`
- Feign：`InventoryFeignClient`，`path="/api"` 对齐 context-path
- **不调 Gateway 的原因**：性能、内网、避免双重鉴权（可按需传递 Header）

## 面试官追问：

1. Gateway 过滤器顺序？
2. Feign 超时和 Gateway 超时谁更短？
3. 为什么弃 Ribbon 用 LoadBalancer？

## 高级回答：

- **Ribbon 停更**；LoadBalancer 官方替代，可自定义 ReactorLoadBalancer。
- **超时**：整条链路 **最外层 Gateway read timeout ≥ 内部 Feign 之和**。
- 10 年答法：**「外走 Gateway，内走 Feign；name 与 spring.application.name 一致」**。

## 题 5：服务拆分边界与内部 API

================

## 面试问题：

你们如何划分 order 和 inventory？内部 API 怎么设计？为什么库存扣减放 inventory 服务？

## 考察点：

- 数据主权、领域内聚
- internal API vs 对外 API
- 安全（internal 不暴露公网）

## 标准答案：

**划分原则**：

- **inventory-service** 拥有 `inventory_stock`、`inventory_flow` 表 **写主权**
- **order-service** 拥有订单表；扣库存 **只能调 inventory 命令 API**，不直连库存表

**内部 API 示例**：

```text
POST /api/inventory/internal/lock
POST /api/inventory/internal/unlock
GET  /api/inventory/internal/usable?goodsId=
```

- **internal** 前缀：Gateway **不路由到公网** 或 IP 白名单 + 内部 Token
- 对外：商品列表在 platform；库存 **列表/预警** 在 inventory 对外 Controller

**为何扣减在 inventory**：

- **单一真相源**，避免 order 与 inventory 各写半张库存表
- V4 原子 SQL 集中在 **inventory Mapper**
- 并发演进 V1～V7 压测在 order，**执行扣减在 inventory**

## 通俗理解：

订单部 **不能自己改仓库账本**，只能填 **领料单** 交给仓库系统扣数——这就是 Feign 调 internal lock。

## 项目结合：

- P1 迁入 StockService + internal API（见 `微服务拆分-起步.md`）
- order 并发包：`/api/order/concurrency/order/add?version=v4`
- 拆分后 **Feign 失败** 要业务异常码，不能 500 糊墙

## 面试官追问：

1. 共享数据库反模式怎么说？
2. platform 和 inventory 都有商品怎么办？
3. BFF 层需要吗？

## 高级回答：

- **共享库**：拆服务但共库 = **伪微服务**；进销存逐步 **分库** 可口述目标。
- **商品**：platform 管 **商品主数据**；inventory 管 **库存数量**，goodsId 关联。
- **BFF**：前端聚合多服务时可加；个人项目 **Gateway 够用**。
- 10 年答法：**「数据跟谁写归谁；internal API 是服务契约」**。

## 题 6：Sentinel 限流熔断与治理

================

## 面试问题：

Sentinel 解决什么？和 Hystrix 比如何？和 Eureka/Nacos 什么关系？项目里怎么用？

## 考察点：

- 限流、熔断、降级
- Netflix 栈 vs Alibaba 栈
- 与注册中心正交

## 标准答案：

**Sentinel**：**流量治理** — QPS 限流、并发线程数、慢调用比例熔断、降级返回。

| | Hystrix（老） | Sentinel |
|---|---------------|----------|
| 状态 | 停更 | 活跃，SCA 集成 |
| 模型 | 线程池/信号量隔离 | 链路、热点、集群限流 |
| 控制台 | 弱 | **Dashboard** 规则推送 |

**与注册中心关系**：**正交**。Nacos 告诉你在 **哪**；Sentinel 管 **能不能打、打多少**。

**进销存**：

- 下单接口 QPS 限制
- Feign 调 inventory **慢调用熔断**
- 与 Redis `@RateLimit` **互补**（应用精确计数 vs 治理规则）

## 通俗理解：

Nacos 是 **电话簿**；Sentinel 是 **「库存部今天最多接 100 通电话，再多请稍后再拨」**。

## 项目结合：

- 见 [`面试题-Sentinel.md`](./面试题-Sentinel.md)、[`Sentinel最小限流-五步学习.md`](./Sentinel最小限流-五步学习.md)
- 并发 V6 MQ 削峰 + Sentinel 限流 **双层**
- 金风若用过 **Hystrix**，口述：**「老栈熔断，新栈 Sentinel，思路都是 fail fast」**

## 面试官追问：

1. 限流和熔断区别？
2. 热点参数限流？
3. 规则存在哪？

## 高级回答：

- **限流**：主动拒；**熔断**：错误/慢调用达阈值 **暂时开路**。
- **热点**：同一 goodsId 秒杀限 QPS。
- **规则**：Nacos 持久化 / Sentinel Dashboard 推送。
- 10 年答法：**「治理三件套：发现 Nacos、入口 Gateway、流量 Sentinel」**。

## 题 7：分布式事务与最终一致

================

## 面试问题：

下单调库存跨两个服务，怎么保证一致？Seata AT 了解吗？你们项目怎么做的？

## 考察点：

- 2PC/TCC/ Saga 概念
- 诚实：Seata 未全落地
- V4 + 补偿 + V7 幂等

## 标准答案：

**问题**：order 本地事务提交后，Feign 调 inventory **失败** → 有单无锁；或 inventory 成功 order **失败** → 有锁无单。

**方案谱系**：

| 方案 | 思路 | 适用 |
|------|------|------|
| **Seata AT** | 代理数据源，全局 TC 协调 | 强一致诉求，运维 TC |
| **TCC** | Try-Confirm-Cancel 业务侵入 | 金融级 |
| **本地消息表 / MQ** | 可靠消息 + 消费者 | 最终一致 |
| **Saga** | 正向链 + 补偿 | 长流程 |
| **业务幂等 + 对账** | 实用主义 | 多数互联网 CRUD |

**进销存务实做法**：

- inventory **V4 原子 lock** 为扣减真相
- order 设计 **状态机**（待锁库 → 已锁库 → 完成 / 取消）
- 失败 **补偿 unlock**（V7 补偿任务）
- **幂等键** 防重复下单（V7）
- Seata：**口述原理**，个人项目 **未生产全量 AT**

## 通俗理解：

跨店扣库存像 **A 店登记、B 店留坑**，任何一步卡纸都要 **有「待处理本」晚上对账**，不能假装一步永远成功。

## 项目结合：

```text
理想顺序（可辩论）：
  1. inventory lock 成功
  2. order 落单
  3. 任一步失败 → unlock / 标记异常订单
```

- Feign 超时 ≠ 失败，需 **查单接口** 幂等查询
- 与 **并发批 V6** 最终一致叙事一致

## 面试官追问：

1. Seata AT 和 XA 区别？
2. TCC 空悬挂？
3. 为什么很多公司不用 2PC？

## 高级回答：

- **AT**：自动 undo_log；**XA**：数据库层锁，性能差。
- **2PC**：阻塞、协调者单点；互联网多用 **最终一致**。
- 10 年答法：**「我项目 V4+幂等+补偿；Seata 知道 AT 流程，按业务选不强上」**。

## 题 8：部署、CI/CD 与微服务运维

================

## 面试问题：

微服务怎么部署？你们 order Docker + Gitee Go 怎么配合 Nacos？单机宝塔跑多个 jar 注意什么？

## 考察点：

- 容器化、CI/CD 已落地
- 环境变量、健康检查
- Eureka 时代 WAR/jar 部署 vs 现在 Docker

## 标准答案：

**部署形态演进**：

| 阶段 | 形态 | 注册发现 |
|------|------|----------|
| 金风 Eureka 时代 | 多机 **jar/war** + Eureka Server | Eureka |
| 进销存学习 | 本机多 jar + Nacos | Nacos |
| 进销存生产 | **order Docker** + 脚本/CD | Nacos 或固定 host 网络 |

**Gitee Go（项目已跑通）**：

- **Order-CI**：push `ms/dev` → Maven 编译
- **Order-CD**：手动确认 → 主机组 `inventory-prd` → `deploy-order-docker.sh`
- 镜像 `order-c`，`--network host`，探活

**运维要点**：

- 每服务 **独立 JVM 堆**，算 **宿主机总内存**
- Nacos 先起，业务再起（或 retry 注册）
- **日志**：每服务独立 log，**traceId** 串联 Gateway→order→inventory
- **配置**：`/opt/inventory-ms/env.sh`，不进 Git

## 通俗理解：

Eureka 时代像 **每分店自己电话报号给总机**；现在 Docker 像 **标准化集装箱**，CD 流水线把集装箱吊到指定码头（服务器）。

## 项目结合：

- `nestparts.top`：Nginx → Gateway → Nacos 实例
- 仅 **order 容器化** 里程碑 v3.7；其它服务可 jar
- Eureka → Nacos：**不是部署方式变化**，是 **发现与配置组件升级**

## 面试官追问：

1. 健康检查 liveness vs readiness？
2. 滚动发布怎么做？
3. 微服务日志怎么排查一条请求？

## 高级回答：

- **readiness**：能否接流量；**liveness**：进程是否死要重启。
- **滚动**：先起新实例注册 Nacos → 健康后摘旧实例（K8s 标准；脚本 CD 类似）。
- **排查**：Gateway traceId → order log → Feign span → inventory log。
- 10 年答法：**「金风 jar+Eureka；进销存 Nacos+Gateway+order Docker CD；能讲清一条下单链路」**。
